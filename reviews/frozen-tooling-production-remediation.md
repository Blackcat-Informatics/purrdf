# S1 full-gate failure under frozen tooling

VERDICT: the stale projection row has a legitimate fallible-API adaptation; the six new helper groups do not have a demonstrated API-only, semantics-preserving consolidation. The complete gate remains failed, and the required capacity-panic census remains independently unmet. Read-only review of `recovery-published-host-fullgate.log` on clean `eb43e0b5452f`, `validation.md` at its final-gate entry, the named functions, and the existing `helpers-ledger.toml` row. No Cargo, forge, source, ledger or tooling edit was made.

The unchanged full gate passed strict workspace/consumer compilation and library/test checks, then stopped in `check-shared-helpers.py` with six unsanctioned body/shim groups and one stale `[[distinct]]` row. Later gate stages did not run. The failure is real; changing whitespace, expression spelling, function names, visibility or test output to change a fingerprint would not remove a duplicated job.

| Group | Source relationship and bounded remediation judgment |
| --- | --- |
| Six `Error::source` impls (`ColumnarError`, `GradeError`, `SegmentedError`, `ChaseError`, `ExprSelectorError`, `ExactParseError`) | Each returns its `StorageError` cause and `None` for other variants. The typed cause must remain reachable. A common production macro/function could centralize that policy only with a new shared abstraction spanning these crates; no existing `variant_from!` or `message_error!` invocation generates this `source` impl. Merely restating the same match differently is fingerprint evasion. A warranted shared production helper is permitted in principle but is not established by this bounded review. |
| `PipelineBundle` / `PipelineViewBundle::pin_handle` | The methods share `BundleCore::verify_pin` but each computes its own graph digest from a different carrier, then conditionally inserts its own handle. A generic pin operation could be designed around a digest callback/trait, but that changes production carrier ownership and public failure sequencing, rather than adapting a fallible caller. A one-line forwarding wrapper would retain duplicated shims. No bounded API-only fix is established. |
| `HnswRelation` / test `CountingTextRelation::open` | Both are the `PropertyFunction` trait's resident wrapper around their own `open_admitted`, not duplicate HNSW kernels. The test adapter counts opens and can attach refusals/evidence through its distinct admitted implementation. Importing HNSW behavior into that fixture or changing its answer to defeat the census would invalidate the test. No shared production job is missing at this wrapper. |
| `SegmentedOperation` / `SegmentedSession::reserve_workspace` | Both call `ready()` then the existing common `reserve_workspace(&state, &budget, &base, bytes)` home. The physical admission implementation is already shared; the duplicated bodies are owner-specific readiness wrappers. Moving these through another common trait would expand the session/operation API and risks the sticky first-fault boundary. Changing one wrapper's order or error mapping merely to change its body is not a fix. |
| `RdfDataset` / `SegmentedStackQuery::triple_term_nesting_bound` | Both report the same validated `purrdf_events::MAX_TERM_NESTING_DEPTH`; this is a required certificate on two distinct `DatasetView` implementors. A default trait answer would be unsound for other views (the trait currently defaults to `None`), and changing one certificate would lie about accepted terms. No API-only consolidation is sound. |
| `LedgerDataset` / host-identity fixture `capabilities` | Both honestly report quoted-triple support over `plain_rdf()`. The fixture intentionally proves host triples, while the ledger's production capability must match its resolved terms. Reusing one through the other is a false dependency; a changed flag would change behavior. No production implementation is duplicated beyond the required trait declaration. |

The existing `[[distinct]]` row at `helpers-ledger.toml:2062` names benchmark `push_iri` and crate-private production `push_iri_triple` because the benchmark can only use the public builder API. The production helper now returns `Result<(), ProjectionError>` and uses `?` at each fallible `intern_iri`/`push_quad`. The benchmark helper still unwraps each operation inside its body. A legitimate adaptation is to make the benchmark helper itself return its actual public builder error, use `?` for those four operations, and have its **existing benchmark call sites** assert/expect success after the helper call. That keeps the same successful graph and failure behavior of this controlled fixture, routes fallibility at the caller boundary, and naturally restores the structural four-operation body the distinct row was written for. The exact helper-census result must be observed; do not alter the benchmark workload or force a match through syntax-only changes. Directly calling crate-private `push_iri_triple` from the benchmark is unavailable and would defeat the ledger's layering reason.

The projection benchmark adaptation is the only *benchmark/tooling-side* change here with a concrete API rationale. Warranted shared production abstractions remain generally authorized; the bounded inspection above does not establish one for the six other groups, and necessary distinct trait implementations/fixtures cannot be falsified to change census output. Ledger or checker machinery remains frozen under the stated tooling restriction. This review recommends neither a covert ledger edit nor speculative carrier rewrites. The separately required **enforced Rust capacity-panic census** is still absent and cannot be counted as passed by manual auditing or this helper hygiene run. Consequently even a successful projection adaptation would not unblock the complete #490/#495 delivery.
