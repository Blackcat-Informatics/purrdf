# Count measurement plan review

VERDICT: PASS

Reviewed on 2026-10-07 against `plan.md`'s Current measurement contract and the sole writer's bounded implementation design. This is a plan-scope verdict, not executable measurement acceptance, source completion, a repository gate or integration PASS. The user's latest instruction replaces the preceding qualification with instruction/allocation counts. The 1.20 value below is a newly selected instruction-overhead criterion; it asserts no equivalence between instructions and elapsed execution. No source edit, build, test, native counter invocation or measurement was performed by this reviewer.

## Design and source basis

The existing acknowledged native control body lives in `scripts/hash-workloads.rs:260–287`: it writes the command and verifies the complete acknowledgement before proceeding. Its workload initializes and warms before enabling the counter and disables before reporting. Promoting this one body to a Linux-gated testkit bench home and routing both hash and governor tooling through it is coherent. Remove the former body; do not copy it into another target or include source across crates. Count mode must require the controller; the hash helper's optional environment lookup must not become silent counter-free success in the new instruction target. Explicit functional smoke may validate answers without making a count claim.

`crates/testkit/src/bench/stats.rs` supplies the existing median/MAD, seeded 95-percent bootstrap and outlier retention. `bench/mod.rs` exposes Estimates and the existing one-percent comparison rule; `bench/store.rs` has the shared path/record writer, while `bench/estimates.rs` currently fixes unit ns. Reuse those homes through a narrow public collector/record API. The old `--test` route runs a selected body once while fixture/guard setup still executes, so a whole-process perf total for that route is a harness count. It is not the proposed production-query window.

`crates/alloc-probe/src/lib.rs` specifies WholeProcessWindow for parallel work and reports successful allocation/reallocation calls, requested bytes, retained live-byte delta and peak working-byte span separately. Its figures are allocator layout demand, not RSS. CurrentThreadWindow cannot cover these Rayon query lanes. A dedicated counting target/process with one active window preserves the existing automatically isolated physical witness rather than weakening its protection.

## Implementation criteria

1. Initialize fixtures, prepared query, engine/pool and workload warm-up before counting. An instruction sample contains exactly five real prepared production query calls through their returned materialized results and receipts. Preallocate result retention outside the window, retain the products through counter disable, then check all typed values and receipts. An allocation sample contains one corresponding query and closes with that result alive. Record these distinct fixed-work/boundary conventions and use them identically across variants.
2. Count retired user-mode instructions on the caller and every participating worker. The broadcast calibration must exercise the actual pool workers created before counter enable, rather than merely proving inheritance on freshly created threads. Validate its returned work and coverage. Preserve an empty-region/control sample so controller/driver instructions are visible and are not mislabeled as dataset/query setup. Missing counters, unsupported events, absent/malformed acknowledgements, incomplete worker coverage and partial PMU counting must fail actionably; do not silently scale or substitute another metric.
3. Each native sample must come from a fresh counter window or a verified difference between explicit counter snapshots. Ten cumulative readings must not be presented as ten independent sample counts. Retain exact raw counts and calls per sample, then normalize per query through the shared statistics. Keep every sample and report variability. Control/driver overhead and any subtraction must be stated; negative or invalid derived counts are an error, not zero.
4. Use the normal allocator for instruction passes and a separate CountingAllocator/WholeProcessWindow target for allocation passes. Shared fixtures, query definitions and full typed guards have one home. This separates allocator instrumentation instructions from the production instruction claim. Pool/setup, validation, JSON/statistics and result formatting happen outside the measured regions. Results are destroyed outside both regions as designed; query-owned cleanup before return remains part of the actual query call.
5. Extend the shared collector/store with explicit instructions, allocation calls and byte units while preserving existing ns record parsing/writing and existing callers. Do not encode counts as ns or create a second bootstrap/JSON/path implementation. Baseline comparisons must reject mismatched units, normalization/fixed work, fixture/query identity or worker configuration. Distinct count namespaces prevent accidental reuse of historical records. A public collected-samples entry point should delegate to the existing private store; baseline builds must not require copied private implementations.
6. Build the same count harness, counter controller, collector and fixture/guard code against unchanged main, the explicitly recorded normal-chunk experiment and the candidate, with the same compiler/profile/event/worker configuration. Apply only a tooling overlay to the baseline projection: new bench targets/shared fixture code and required first-party testkit/alloc-probe support. Keep baseline shipping evaluator/numeric code unchanged. Record the overlay separately from the shipping diff and use consistent first-party dependency paths; no local source path may silently resolve to a different variant. The normal-chunk experiment remains an experiment, not a historical source or correctness oracle. Bind each record to its source, overlay and executable identities.
7. Retain full ordered row bindings or canonical result bags for FILTER/BIND and every one of the 5,000 numeric group/SUM values, together with Complete/trip status, all consumed dimensions and relevant expression-error counters. Checks run after counter disable/window close. Existing source-order/refusal/error, stop-once, ghost-mint/resume, physical peak/work, corpus, caller, portability and finalization requirements remain unchanged. No measurement-only governor engine or production semantic feature is needed.

## Count acceptance

- Numeric: metered/plain median instructions per query at most **1.20** at both **4 and 32 workers**, with the full-value guard and raw samples/uncertainty reported. This is the selected instruction criterion, not a throughput or execution-time claim.
- Rows: at **32 workers**, stop-only and fuel-plus-stop FILTER/BIND reduce instructions against unchanged main and meet the attributable normal-chunk control; plain controls have no regression under the existing testkit comparison rule. Report the **1/4-worker** neighbors. Use the existing one-percent practical threshold consistently rather than inventing a tolerance after seeing counts.
- Allocation: compare all four separate quantities for each lane against the same baseline, identify every increase for remediation, and preserve the independently derived physical peak and phase-separated bounded-work assertions. Do not blend allocation traffic, retention and peak into one favorable number.

The amended plan supplies clear count boundaries, dependencies and acceptance. Its shared controller/store design is feasible in the existing homes and preserves first-party/layer/portability constraints. Source implementation and actual count receipts remain to be reviewed within this affected scope; no larger audit or new gate is required by this plan verdict.
