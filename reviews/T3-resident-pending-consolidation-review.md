# #531 resident pending guard consolidation — source review, 2026-10-13

VERDICT: PASS for the inspected source consolidation only. No build or test was run for this review; focused compilation, census and root's final gate remain separate.

`eval.rs::ResidentPending<C>` is one generic stack guard holding the already-created pending child and `&mut EvalCtx`. Its `Drop` calls that child's `ResidentAbort` while `child: Some`, before the pending child and its immutable prepared-pattern owner are dropped. `LateralPending::abort` still unwinds substitution frames, then restores substitution scope and ledger in that order. `ExistsPending::abort` still unwinds substitution frames and then restores the correlated scope. Both consume these options, so the explicit `finish` call and a later guard drop cannot restore twice. The resident adapters in `binop.rs` and `expr.rs` retain the child inside the guard across `eval_evaluated`; on normal return they take it and call its original finish, whose first action restores the child scopes before propagating the evaluation error or publishing evidence/memo results. Panic before `take()` runs the same abort via `Drop`, while the owner remains live. This preserves the prior child-before-owner and child-before-parent ordering in the inspected resident paths.

The consolidation removes two parallel guard-drop bodies. It adds no heap allocation, dynamic dispatch or alternate evaluator: `ResidentAbort` is a generic static trait call, and pending children are still created only by their existing admitted entry paths. The distinct LATERAL and EXISTS restoration bodies remain at their original pending-child homes rather than being copied into the guard. No material source defect found in this delta.
