# #531 independent linked-path root-cause review

**Disposition: neither tested extraction corrects #531. No further source correction is justified by the current frame evidence.** This review is read-only against clean N checkout `330c55f8c2d99300b8375a545ef255095e23a830`. Its installed optimized module is the *reverted* FILTER no-inline candidate, SHA-256 `1a28fd0bdc806e04c7459da3b0c7071a38981385af1a8a29df2db8b18178671a`; it is not acceptance evidence for current source. I verified that module hash. No source, build, floor, or tool was changed here.

The original Node floor tests on that linked candidate exited 1: right-nested LATERAL answered 234 levels where the test requires at least 281, and WALK `FILTER NOT EXISTS` answered 133 where it requires at least 180. The same module's production `queryGovernedAsync` high-water controls at depths 2/4/8/16/32 show 4,080 bytes per added LATERAL level and about 7,136 bytes per added WALK level. The earlier complete EXISTS branch-split module (`0cef94454eed5c5eefebfa06f7ec69d9afa0553687aed40ab2d15afc5996360a`) also failed at 234/133, with 4,080/approximately 7,104 bytes per level. The 32-byte WALK-slope difference is not a qualified improvement: both original floors remain failed, and the builds differ. Receipts: `tasks/T3-531-filter-lifetime-failed-qualification.md`, `tasks/T3-531-exists-full-branch-disposition.md`, and their original-floor/stack-byte logs.

The nested WALK re-entry is **not** `expr::eval_filter`'s earlier `eval_evaluated(inner)` call. In `expr.rs`, `eval_filter_sequence`'s sequential row loop calls `linked.filter(expr, &row, &schema, ctx)` after admitting the row. `vm::Linked::filter` calls `ebv` then `term`; `term` retains its program counter and VM while resolving `Suspend::Exists`, which invokes `exists_recorded`. That function first checks `ctx.deferred_exists`: a placeholder goes to `exists_deferred`, while an ordinary site goes to `exists_prepared`. In the deferred merged-env arm, the next nested graph evaluation is `binop::eval_substituted`, **bypassing `exists_prepared`**; only empty/layered deferred arms re-enter the prepared path. The enclosing sequence still needs its checkpoint, schema, `Linked`, current row, and output builder to settle the predicate, evidence, refusal barrier, and output after the child returns. `Linked` owns four inline slot/constant cells and other buffers; its value stack is already a heap `Vec`, so moving that value stack to the heap again is no explanation. The source establishes these lifetimes, not their optimized byte totals or which deferred arm this exact fixture repeatedly selects. The WASM forked row loop is disabled by `may_fork_row_loop`, so fork-only extraction cannot address this linked path.

Changing only `eval_filter_sequence` from `#[inline(always)]` to `#[inline(never)]` may change where the live sequence state resides, but the sequence still calls `linked.filter` at every recursive level. It cannot make that state dead across the recursive edge. The measured unchanged floors and slope are consistent with this explanation; they do not independently identify a compiler frame. Likewise, the complete EXISTS patch placed `exists_definition` and `exists_memoized_probe` out of line with `#[inline(never)]`, so the failure cannot be dismissed as those new helpers simply being inlined. The ordinary definition helper still owns memo, witness, ledger and post-child completion state while it calls `eval_correlated`. More critically, the repeated nested placeholder may take `exists_deferred`'s merged arm and bypass both extracted helpers entirely. The linked measurements reject the split as a fix, without proving whether it missed the repeated path, merely relocated live state, or both.

The separate raw **bench-profile** artifact (`tasks/T3-531-bench-frame-readback.md`) reserves 3,952 bytes in `exists_prepared` and shows a call to `eval_correlated` while that reservation is active. This is useful evidence that an *ordinary* EXISTS definition can carry a large frame. It does not show that `exists_prepared` repeats at every level of this deferred-placeholder fixture; it may occur only at the top site. It is also an unlinked, differently optimized artifact: its prologues cannot be summed into, or assigned as, the release `wasm-opt`/`wasm-link` module's 7,104–7,136-byte slope. The earlier omission of the inner inequality FILTER reduced a slope, but it also removed a graph-plan Filter node at every level; it does not isolate an expression or `eval_filter_sequence` frame.

LATERAL has a different re-entry: `binop::eval_application` processes a left row, then `evaluate_application_row_with` enters the right operand via `eval_substituted_delivered`; the supplied control nests that *right* operand. The unchanged 4,080-byte slope and 234-level floor cannot be attributed to the WALK filter or prepared EXISTS frame. Main-based hosted evidence predates #470 and already fails these original floors (`reviews/issue-531-versus-470-stack-floor-classification.md`), so this is established #531 debt rather than a demonstrated new numeric defect. Exact floor differences among main, #365, and N builds are not attributable without matched linked artifacts.

The next bounded computation, when execution resumes, is path and frame attribution on the **exact linked optimized module and unchanged Node query shapes**: establish how often each depth takes ordinary `exists_prepared` versus `exists_deferred` merged/empty/layered, then identify the repeated call sequence and shadow-stack pointer deltas at sequential `linked.filter`/EXISTS descent and right-nested LATERAL descent, with source and linked artifact hashes recorded. Separate caller frames that remain live from callee frames and from heap allocations; compare baseline and one correction on the same path. Only then is a lifetime/representation correction warranted at the frame proven to dominate. It must retain ordered row admission, original row/evidence ownership, memo and ledger windows, first operational error, typed stack refusal, and answer multiplicity. After that, the original floors and complete package gate still need to pass. No current candidate satisfies them.

## 2026-10-13 addendum: named-chain strength and limit

I independently counted **52** function imports in the rejected bench diagnostic's `tasks/T3-531-current-bench-map-pkg/optimized-mapped.wasm` and read its retained `T3-531-current-bench-function-map.log`. After subtracting that module's own 52 imports, its named sequence is `eval_node → eval_filter → Linked::filter → Linked::term → exists_recorded → eval_substituted_delivered → eval_evaluated_with → eval_evaluated_inner_with → closure → eval_node`. The unnamed release diagnostic's 53-import-normalized direct-call sequence has the same topology and corresponding frame-reservation sizes. Current production source also contains precisely this feasible recursive route: the sequential filter loop suspends its VM on EXISTS, a deferred merged site evaluates a substituted graph, and the evaluated node dispatches to the next filter. This is **strong source-path evidence** that those homes participate and is sufficient to focus further investigation there.

It is **not an exact Rust-symbol assignment to each release WAT function**. The bench module is `profile.test:true`, includes test exports, and failed the shipping linker; its functions and monomorphs can differ from the release `profile.test:false` build. Matching topology and frame sizes can arise from the same inlined source regions under different containing functions, and neither release module carries the named symbol map used by the bench. The two temporary trap sites anchor refusal *source regions*, but they do not label every repeated release frame or show the live local values within it. A release-artifact symbol/line map tied to the same hash, or individually anchored source-to-function probes at the relevant repeated edges with evidence that their instrumentation did not change those identities or frame accounting, is still needed for a frame-specific source correction. The uninstrumented linked module must then confirm the actual byte change and unchanged original answers/floors. No release function name or fix is promoted from the bench isomorphism here.

The LATERAL probe narrows one point further. Its `unreachable` was inserted in `eval.rs::eval_evaluated_with`'s low-stack branch for a VALUES node, and the pre-link trace's top frame is absolute `3696`, defined WAT `$3643` after the verified 53 imports. Thus `$3643` **contains the compiled `eval_evaluated_with` refusal site** in this exact instrumented release artifact. The named bench's corresponding 336-byte frame is `eval_evaluated_with`, making that Rust identity a strong inference. Since the source function lacks a `#[inline(never)]` boundary, the probe may be inlined into a containing monomorph; this anchor does not prove that the whole `$3643` body is exclusively `eval_evaluated_with` or that its 336 bytes are that function's local state. The NOT EXISTS `stack::check` helper is explicitly `#[inline]`, so its trap top frame likewise identifies an inlining caller, not a separate stack-check frame. Same-hash release symbols/line locations or uniquely anchored entry/exit mapping, plus a live-local/frame analysis at the recursive call, remain the exact proof needed before assigning a byte-saving correction to those source functions. This is a stricter question than whether the code path visits their source regions, which the probes do support.
