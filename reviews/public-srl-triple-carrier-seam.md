# #492 public SPARQL RL triple-carrier seam — 2026-10-13

Read-only recommendation; no source edit or runtime claim.

The actual public SPARQL 1.2 RL entry is `shapes::srl::infer(document, &RdfDataset, options)` in `srl/document.rs`. It returns `srl::Inference`, whose `dataset()` and `inferred_dataset()` are `Arc<RdfDataset>`. That entry projects the base into `ShaclData`, and `eval::evaluate_shape` immediately calls `data.core_arc()`, then later builds the result with `RdfDatasetBuilder`. Thus merely using `RuleShape<3>` under that entry would still hold and return quad storage. `purrdf-entail` does not depend on Shapes; its OWL/RDFS materialization is a different consumer. The plan should name the existing public SRL path explicitly rather than imply a new Shapes dependency in entail.

The smallest coherent public route is a carrier-typed sibling entry such as `srl::infer_triple(document, &TripleDataset, options) -> Result<Inference<TripleDataset>, SrlError>`, with the existing `infer` and its concrete return type preserved by a default `Inference<C = RdfDataset>` parameter. Both entries should perform the same document well-formedness/stratification/error mapping and enter **one** `eval::evaluate_shape`/Datalog/guard body, selecting arity 4 for the old entry and 3 for the triple entry. A small closed carrier interface at the existing SRL/rules home can supply original base triples and final graph construction; `Inference`'s common inferred rows, explanations, contract hash and rendering remain shared. Carrier-specific output construction uses the respective original builders, not an RdfDataset intermediary. It must reproduce asserted, reifier and annotation rows with original blank scopes and classify new reifier/annotation facts under the same `rules::reifier_subjects` law. The inferred-only dataset method must also return the selected carrier, while legacy callers retain `Arc<RdfDataset>` through the default type.

`RuleSetDocument::rule_set()` always creates `IrRuleBody::Elements` with empty `expected_predicates` and a stratified schedule. The only guard needing `Engine::view`/mutable SHACL `ShaclData` is `GuardImpl::Producer`, which these documents cannot create. `Filter` and `Assign` call the existing `empty.sparql_view()` and do not read the changing rule model; `FreshBlank`, `SameTerm`, `MatchTriple` and `BuildTriple` operate on bound lexical terms. `Hooks::assume` returns before `Engine::view` when expectations are empty; retract/finish inspect decoded model facts. Therefore keep the existing quad SHACL view owner only for a source set that can contain Producer/expected-shape work, and make the triple document branch fail explicitly if that invariant is ever violated. Do not implement `ShaclRead` or an infallible `DatasetView` for `TripleDataset`: `ShaclRead` requires `ReadError = Infallible`, while the public triple query authority is the fallible `TripleRead` session. Base term conversion should reuse the existing bottom-up `term_ref_to_native` computation after separating its resolver obligation from `ShaclRead` at that original home; do not write a second recursive term converter.

The current `TripleDataset` exposes `triples()`, `reifiers()`, `annotations()` and `resolve()`, and `TripleDatasetBuilder` has corresponding direct intern/push/freeze operations. These are the physical ingress/egress seams. The public triple entry must exercise them on nonempty RDF 1.2 statement data and ordinary recursion, compare model/explanations with the existing all-default quad oracle while preserving the intentionally distinct triple contract hash, and show no retained quad tables. No such public triple call or result exists yet, so this is a **missing #492 contract**, not a passing implementation or a reason to open a foundation PR.
