# #531 repeating EXISTS filter-frame assessment

VERDICT: REJECT the forked-row extraction as a correction for the measured WASM floors. This is a completed source assessment, not a package validation. Source identity: #470 checkout HEAD `838667cab`, with the uncommitted `binop.rs` LATERAL work left untouched. No build, source edit, budget change, or floor change was made. The retained optimized package showed 7,104 shadow-stack bytes per additional NOT EXISTS level from depth 2 and failed the original synchronous/job and NOT EXISTS floors (134/133 versus 181/180); that artifact does not validate this checkout's uncommitted source.

`crates/sparql-eval/src/expr.rs::eval_filter` first evaluates the data child, then calls `eval_filter_sequence`. The repeated EXISTS descent is later: the sequential row loop's `linked.filter(expr, &row, &schema, ctx)` evaluates `NOT EXISTS`, reaches `exists_recorded`/`exists_prepared`, and re-enters graph-pattern evaluation for the next nested filter. Its `Lift`, schema, checkpoint, linked VM, current row, and output builder remain live because the caller must finish the row's predicate, evidence, and barrier decision after that descent. Extracting the data-child call boundary does not move this recursion.

The proposed split would be semantically feasible for the native fork strategy only if it moved the entire current forked arm together: worker snapshot and deferred checkpoint clones, `par_loop_try_map_init_fallible`, worker witness harvest, source-order `commit_rows`, witness absorption, ordered resume, and the resident-row result. It must leave the sequential arm's `checkpoint.pass` before `linked.filter`, original row/evidence ownership, common expression barrier, and `lift.finish` in their current order. Moving only the worker loop and leaving commit/resume outside would risk changed first refusal, source order, and witness ownership. An out-of-line fork helper would also add a live call frame while that fork's worker evaluates an EXISTS on native targets.

Most decisively, `EvalCtx::may_fork_row_loop` in `crates/sparql-eval/src/eval.rs` returns `false` immediately for `cfg!(target_arch = "wasm32")`. Thus `forked` is always false in the measured optimized WASM package, before expression safety or governor checks; neither forked harvest nor worker temporaries execute on the failing path. In an optimized WASM build the constant-false arm is eligible for elimination. There is no source basis to attribute the 7,104-byte sequential slope to those forked temporaries or to expect their extraction to recover the three WASM floors. Removing `#[inline(always)]` alone likewise supplies no proven saving and could add a frame at every recursive level.

The bounded next computation is an optimized-WASM frame/stack-pointer attribution at the *actual* `linked.filter` → EXISTS → nested evaluation call, including `eval_filter_sequence`'s sequential live state and the prepared EXISTS/correlated-evaluation frames. A source correction must target state provably live across that call, then be measured against the unchanged original floors and exact answer, evidence, multiplicity, first-error and typed-refusal controls. No such correction is established by this review; the proposed forked-only extraction is rejected for #531.
