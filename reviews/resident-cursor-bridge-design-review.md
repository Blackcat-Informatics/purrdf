# Shared resident cursor bridge: bounded design review

VERDICT: a narrowly scoped macro at the existing `purrdf_sparql_eval::property_fn` home is a defensible one-body production consolidation for these two admitted-first implementors; no source edit or census pass is claimed. Read-only review of #536's dirty typed test adapter, `PropertyFunction`/`WorkspaceCursor`, both actual `open` bodies and `tasks/retrieval-adapter-census.log` (terminal 1: only `body:d3296d7513fe6e45`). The adapter's strict check, original 21/21 and independent ownership review are reported passing; this review did not rerun them.

Both `HnswRelation::open` and `CountingTextRelation::open` perform the **same semantic bridge**: call their own `open_admitted(args, ceiling, WorkspaceCapability::resident())`, then `WorkspaceCursor::into_resident`. Their admitted implementations differ and must remain separate: HNSW opens its index cursor; the test adapter increments its count and may wrap a prefix-refusal/evidence cursor under the supplied workspace. The duplicated `open` body neither computes HNSW ranking nor test evidence; it only converts the admitted cursor into the legacy resident `Box<dyn PfCursor>` required by the trait. The census failure reflects one repeated bridge job, not a reason to alter either answer.

`PropertyFunction::open` is required and has no default. Its default `open_admitted` calls `self.open` after a workspace certificate. Giving `open` a blanket default that calls `open_admitted` would recurse for ordinary opaque implementors that rely on the existing default, so it is **not** a safe simpler home. A free shared `resident_open_from_admitted` function at the trait home could centralize runtime code, but the two required `open` wrappers would still be identical thin shims and may leave the same census problem; it also adds a call boundary to the cursor's existing path. No existing `WorkspaceCursor` method accepts a relation plus arguments to perform this bridge.

A single, documented `macro_rules!` implementation declared in the existing property-function production module can generate the exact required `fn open` for admitted-first implementations. Both impls invoke it as an associated item; its body is written once and uses `$crate`-qualified `WorkspaceCapability`, `WorkspaceCursor`, `PfArgs`, `PfCursor` and `EvalError`, so it works from the HNSW crate and retrieval integration target without another dependency or runtime function. The macro must explicitly require that the invoking impl overrides `open_admitted`; otherwise the trait default would recurse. It must preserve the existing `args`, `ceiling`, resident capability, `.and_then(WorkspaceCursor::into_resident)` and exact `EvalError` propagation. The local test adapter's `open_admitted` and `PrefixRefusalCursor` ownership remain unchanged. This is analogous to the repository's first-party `constructors!`/`variant_from!` pattern: one declaration for a repeated, invariant implementation body, with the concrete differences supplied by the enclosing impl. It is warranted by the verified two-member census group, rather than a syntax rewrite or output-shape evasion.

The macro's export would be a small public production API addition, so it should be named for this precise admitted-to-resident bridge and documented as opt-in, not applied to other `PropertyFunction` implementors indiscriminately. Strict affected checks, original 21/21, independent ownership assertions and the **unchanged** helper census must run on the resulting final source. The current terminal-1 census remains failed until then; the mandatory full gate and #536 delivery remain open.
