# `ProjectStar` public contract disposition — 2026-10-13

**Scoped verdict: the compact representation is within Task 4's approved implementation choice, but its public source break needs an explicit release and migration disposition.** It is not a newly discovered projection correctness defect, and it does not require another implementation campaign before addressing the known #531 package floors. I inspected the captured #365 issue and plan, current algebra API and consumer map, and retained current-source qualification. No source, build, package or forge operation was changed.

The issue asks to represent nested `SELECT *` without repeatedly materializing visible lists, or refuse before doing that work. The accepted plan explicitly allows a compact star projection and requires ordered scope, roundtrip, evaluator and public native/optimized-WASM behavior. `GraphPattern::ProjectStar { variables: ProjectionVars }` implements that option while retaining explicit `Project { variables: Vec<Variable> }`. `projected_names()` and `ProjectionNames` provide the shared ordered view. Parser scope handoff, serializer, evaluator, deferred EXISTS, SERVICE, validation and ownership consumers have been migrated; the two remaining in-repository Project-only integration assertions were fixed in pushed `a73408ddf`, followed by the complete local `make check` terminal 0. Existing native growth/contextual MINUS/trailing VALUES/serializer controls and optimized public query/refusal/healthy-neighbor controls establish the Task 4 behavior at their recorded source and package identities. The original high-u64 WASM fixture passed on `a73408ddf`.

The public Rust enum is **not** `#[non_exhaustive]`. Its new variant breaks downstream exhaustive `match GraphPattern` source, even though `Project.variables` retains its type and existing explicit constructor behavior. The captured issue's opening says its observed follow-ups were nonbreaking and fixable in a 3.x release; it does not explicitly waive downstream source compatibility for the chosen fix. The plan approves compactness, not an explicit semver exception. The repository's `CHANGELOG.md` and book introduction promise a major-version bump for a breaking change. The current `T4-implementation.md` and `T4-consumer-map.md` candidly record the exhaustive-match adaptation, but `CHANGELOG.md`'s Unreleased section and `docs/MIGRATION-3.0.md` contain no `ProjectStar`/`ProjectionNames` guidance. An external consumer cannot infer the required match adaptation from an installed package's Rust API alone.

**Owner action:** carry an explicit breaking-API note and concrete downstream migration example in the appropriate release/migration documentation and PR description, with the integration/release version consistent with the repository's major-bump policy. A consumer should match both variants or use `GraphPattern::projected_names()` for common ordered projection names, preserving explicit `Project` construction when an owned list is intended. Do not claim source compatibility or silently ship the addition as a 3.x patch. If the intended delivery must remain source-compatible in 3.x, this exact public variant needs a different design; no such redesign is required by the Task 4 performance evidence itself and none was attempted here. This is a documentation/release-classification gate, not an extra user-permission ceremony.
