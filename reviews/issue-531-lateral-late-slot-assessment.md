# #531 LATERAL late-slot assessment (2026-10-13)

**Verdict: the exact WAT shows late use of the highest `$818` frame offsets, but does not identify them as final-merge-only state or justify a combined dispatcher rewrite.** This is a read-only assessment of clean N source `330c55f8c`, `tasks/T3-531-wat-defined-818.txt` from the exact instrumented release pre-link artifact, and retained final-merge qualification. No source or build was changed. The release `$818` Rust name remains inferred from the rejected named bench topology, not proven by a production symbol map.

WAT `$818` reserves 1,584 shadow-stack bytes. Its two direct `$2021` call sites around lines 2446 and 2479 lie in the repeated right-child path identified by the Node trace. The searched stores at offsets 1544, 1560 and 1568 occur only around lines 5228–5325, after those calls in the textual body and around a call to `$3553`. This supports the narrow statement that these *particular stores* are post-call in the displayed control flow; it does not show what source object they represent or that all high frame bytes are dead during the child. The function also performs post-right **per-row** schema/pair commits, truncated-child cleanup, and, after the loop, final schema union and output-row merge. A text-order scan of structured WAT and an unnamed `$3553` target do not distinguish those homes or establish the repeated control-flow edge that uses each offset. A full def-use/control-flow mapping or same-hash source-location anchor would be needed for that assignment.

There is already a relevant bounded measurement. The prior `finish_application_output` extraction moved the final schema union/row merge out of line after right recursion, with native semantics checked. Its optimized linked package reduced the original LATERAL high-water slope **4,080 → 3,840 bytes per level**, but the unchanged original floor still failed at **249 < 281** (`validation.md` and `tasks/T3-default-dir-lateral-{stack-bytes,original-floor}.log`). That proves final post-child work can contribute some reserved stack, not that the late 1544/1560/1568 stores are its variables or that repeating the same split will save more. The later compact-continuation candidate worsened LATERAL to 4,112 bytes/level and 233 < 281 despite moving retained state; it was reverted. Neither result licenses a claim that high offsets explain the remaining roughly 3.8 KB/level.

A truly thin `eval_application` dispatcher would have to select the property-function early path and the generic right-recursive path while preserving the existing sequence: left evaluation and `Lift::absorb`, truncation check, property-function interception, endpoint admission, deferred-site check, per-row right evaluation, then final merge. Moving the generic loop into another no-inline function while the dispatcher retains the left bag/Lift merely adds a live call frame. Moving left evaluation into separate property and generic helpers risks duplicating the one left-evaluation/absorption path; boxing those owners already incurred a new default allocation and failed the original floors. Outlining only the property cold branch could avoid a default call, but there is no artifact evidence that its locals cause `$818`'s late high offsets. A combined boundary is therefore a testable architecture idea, **not a source correction supported by these offsets**.

The next useful read-only computation is to resolve `$818`'s high-offset def-use and `$3553`'s role on the exact artifact, and compare a retained pre/post final-merge artifact if one is available. If those identify cold variables live solely because of fixed-frame allocation, one one-home extraction can be tested against unchanged row/evidence, first-error, truncation, admission and 281-level controls. Do not add a second LATERAL loop, another generic wrapper, a new ordinary allocation, or relax the floor based on WAT text order alone.
