# PR 544 wide Datalog tail assembly assessment — 2026-10-13

VERDICT: FAILED hosted assembly acceptance on head `10316f2c1`; this is a read-only, bounded diagnosis, not a corrected source or whole-issue verdict.

`store.rs::Tail<I>::contains` retains the single generic `TermIdentity` body and correct OR-fold over the two structure-of-arrays columns. S1 widened native `TermId` to a `NonZeroU64`-backed ID; generic `I` also permits caller host IDs, so narrowing/casting/transmuting to `u32` would violate real join identity. The four retained hosted logs show the `datalog.relation-contains` site failing: x86_64 baseline has zero vector ops against floor six; x86-v3 lacks required `vpcmpeqd`/`vpmovmskb`; wasm SIMD lacks `i32x4.eq`; aarch64 lacks `cmeq .4s`. Other two configured failures reported by root require their own exact logs; these four do not establish their details. This site is currently not qualified.

The manifest and `docs/design/purrdf-simd.md` still describe packed **u32** key columns and original 32-bit mnemonics. That doctrine is stale for native `NonZeroU64`: AVX2/AVX-512, NEON and wasm SIMD may compare 64-bit lanes (`vpcmpeqq`, `cmeq .2d`, `i64x2.eq`) and reduce them differently. A stale mnemonic alone is not a performance pass, and x86_64's measured zero vector ops is an actual loss, not explained away by the mnemonic change. Lowering floors or changing expected mnemonics before the emitted code is measured would conceal a failed contract.

Smallest first source experiment at the same home: keep the generic ID type, three columns, non-short-circuit `&`/`|` semantics and insertion-order behavior; replace the zipped iterator with a counted, no-early-exit index loop over the equal-length key columns (for example `for i in 0..self.subjects.len() { hit |= (self.subjects[i] == subject) & (self.objects[i] == object); }`). The columns' equal-length invariant is already established by `push`/`take_rows`; check that invariant in the existing tail tests. This gives LLVM one canonical induction variable and paired contiguous loads without introducing a second body, host-ID assumption or intrinsic. It is a hypothesis to compile and inspect, not a claim it will vectorize—particularly SSE2, which lacks a direct packed 64-bit integer equality. Preserve the existing duplicate oracle and native/host-ID boundary tests. The source comment saying contiguous `u32` columns also needs correction to actual ID width if this is retained.

After the source reformulation, inspect the exact seven configured `Relation::contains` symbols and emitted vector counts with the unchanged manifest. For a lane whose actual 64-bit vector sequence is present but only a 32-bit mnemonic fails, update that lane's manifest to the *observed* 64-bit instruction/reduction and document the source/width reason; retain a meaningful vector floor based on the measured sequence, not an arbitrary relaxed threshold. For a lane still lacking vector execution (notably baseline x86_64 unless the experiment changes it), diagnose its lowering at the computation and then consider one warranted backend implementation at the original home. No intrinsic or architecture dispatch is justified by the current four logs alone. Rerun the original per-configuration assembly gate after any correction; local semantic tests and the generic host-ID path remain separate obligations.
