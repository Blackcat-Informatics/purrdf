# `purrdf-sparql-governors` — SPARQL 执行 governor profile

[English（当前 profile）](SPARQL-GOVERNOR-PROFILE.md) | 简体中文（profile v18）

**Profile 标识符：** `purrdf-sparql-governors` &nbsp;·&nbsp; **Profile 版本：** 18
&nbsp;·&nbsp; **编辑：** Patrick Audley，Blackcat Informatics® Inc.

本文中的各个值都可以从库中读取，而不只是出现在文档里：`purrdf_sparql_eval::GOVERNOR_PROFILE_ID`、`GOVERNOR_PROFILE_VERSION`、`GOVERNOR_PROFILE_DIGEST`、`GOVERNOR_CORPUS_DIGEST`、`CHARGE_SCHEDULE`、`STOP_POLL_FUEL`。使用方因此可以断言，自己链接的构建实现的正是所固定的 profile，而不必仅凭文档判断。

## 摘要

本 profile 规定**调用方提供的执行上限**如何计费、何时触发、多个上限同时触发时采用哪一个，以及调用方可以如何使用执行在触发之前已经到达的行。它是 `NativeSparqlEngine::query_governed`、`update_governed` 及其接受视图的对应入口所遵循的契约，也是 Python、JavaScript/wasm、C 和 `purrdf` CLI 中 governor 接口的契约。

预算中的数字只对**某一套**计费规则有意义。固定这套规则的身份，才能使双方对同一个数字有相同的理解；本 profile 因此具有版本号和内容摘要。

所有示例 IRI 都使用 `example.org`。PurRDF 不分配词汇 IRI；下面的 profile 标识符刻意采用单独的标记，因而不能被解引用、用作断言中的 IRI，或被误认为本体。

## 1. 确定性：保证哪些性质

首先说明这一点，因为使用方最容易把这项保证理解得过宽。

| 受 governor 管控的量 | 是否确定？ |
|---|---|
| `fuel` | **是** |
| `answer-rows`（答案上限） | **是** |
| `intermediate-cells`（基数／单元格上限） | **是** |
| `scratch-bytes` | 是——由相同的固定输入决定 |
| `remote-requests` | 是——由相同的固定输入决定 |
| `udf-depth` | 是——构建时固定的上限，调用方不能设置 |
| **挂钟时间截止期限** | **否。对此不作确定性保证。** |

这里的“确定性”是指：相同查询在相同数据和相同上限下，消耗完全相同的数量，并在完全相同的位置触发上限，不受工作线程数、线程调度、散列种子、机器或构建 profile 的影响。并行求值保留这一性质，是因为计费先在分块内部累计：每个输入行一条记录，没有原子操作，也没有共享状态；随后再按**源输入项顺序**归并。因此，报告的触发点仅由 `(query, data, ceilings)` 决定。如果按整块粒度归并，触发点就会依赖 `rayon::current_num_threads()`；采用此归并方式正是为了避免这种错误。

**挂钟时间截止期限被明确排除在外。** 运行时间在何处耗尽取决于机器，而非查询本身，因此其触发点、行数和成本都不可复现，也不公布这些值。§11 的规范性语料库把时钟读取与停止轮询规则分开：三个注入截止期限的用例采用确定性的轮询次数，完整固定零上限、边界和超界记录；挂钟时间截止期限的冒烟用例只固定确实发生了触发，且报告的原因是截止期限。它没有预期行数或成本，因为依赖时间的触发点没有可以如实公布的固定值。

**取消不是时钟**，因此取消用例的记录会被完整固定。

## 2. governor 改变执行结果状态，绝不改变答案

这是整个 profile 的不变量。

> 上限绝不改变查询的完整答案。它改变的是：在完整答案尚未求出之前，可以返回哪个经过认证的区间（如果存在）。

因此，上限既不是可选语义，也不是换了名字的 Cargo feature。它决定调用方收到的是完整答案，还是三种带类型的区间结果之一：`Certain` 只包含已经证明的答案；`AtMost` 包含所有答案，但也可能包含尚未排除的候选项；`Unknown` 不暴露任何行。不同上限可以暴露不同区间，但都不能改变完整答案，也不能把未经认证的行标成答案。

两项结构性规则防止这一契约退化为“有时返回错误答案”：

* **截断结果绝不以完整结果的形状返回。** 受 governor 管控的调用返回 `GovernedOutcome`，其中 `BudgetExhausted` 分支是携带证书的独立类型。`SparqlResult` 和 `CompleteSparqlResult` 仍然表示“这就是答案”。
* **真正的求值错误优先于任何 governor**（§6）。如果查询本来就无法求出答案，却报告预算耗尽，就等于把一个根本没有答案的问题的部分答案交给调用方。

**不受 governor 管控**的查询，以及 `QueryGovernors::UNBOUNDED`，会在任何 governor 停止探测、计数器、证书账本或输出重新包装之前进入直接求值路径。仅供报告的 `governed_eval` 基准把该路径与 `UNBOUNDED` 载体作比较；不保证两者的耗时相等。`QueryGovernors::METERED` 则采用相反的取舍：启用所有计数器，并把上限设为不可达到的值。它是**测定预算大小**的预期方式：在该模式下执行，读取完整结果中的证据，再据此选择实际上限。

## 3. 受管控的维度

下表按 `purrdf_core::ResourceDimension` 的声明顺序排列。标签是固定契约：冻结语料库以这些标签区分用例，因此改名属于破坏性变更，而非文字润色。

| 标签 | 限制的量 | 累计方式 | 调用方可设置 |
|---|---|---|---|
| `fuel` | 按 §4 计费的抽象执行步骤 | 求和 | 是 |
| `answer-rows` | 查询提交到其**答案序列**中的内容 | 求和 | 是 |
| `intermediate-cells` | 最大的单个中间多重集，按 `rows × columns` 计算 | **最大值** | 是 |
| `scratch-bytes` | 计算项存储区、身份预留，以及显式计费的保留聚合缓冲区／状态 | 求和 | 是 |
| `remote-requests` | 向联邦端点发出的请求 | 求和 | 是 |
| `udf-depth` | 用户定义函数调用的嵌套深度 | **最大值** | **否**——固定为 32 |
| `pages` | 按需分页操作可以准入的不同页面 | 求和 | 通过 `PagedQueryLimits` |
| `bytes` | 提供方报告的已准入页面字节费用 | 求和 | 通过 `PagedQueryLimits` |

两个维度取最大值而非总和，其理由相同，只是体现方式不同。`intermediate-cells` 限制**某一个**算子实例的多重集大小；如果求和，就无法区分一个很长但便宜的查询与一次灾难性的笛卡尔积，而它正是为防止后者而设。`udf-depth` 是**深度**：查询在深度一调用函数一千次，达到的深度仍是一，而非一千。

`udf-depth` 刻意不允许调用方设置。它是栈递归防护；允许调用方放宽的递归界限就不能承担这一防护作用。无论执行是否受 governor 管控，它始终生效；这里列出它，只是为了**报告**其消耗。

### 3.1 `answer-rows` 是操作上限，绝不是 `LIMIT`

`LIMIT` 属于查询语义，**先于**上限检查生效。上限按相应查询形式自己的答案序列计量，因为那才是调用方收到的内容：

| 形式 | 一个单位表示 |
|---|---|
| `SELECT` | 一个解行 |
| `CONSTRUCT`、`DESCRIBE` | 一条**输出陈述**——普通三元组、RDF 1.2 具体化节点绑定或注解 |
| `ASK` | 不计量；布尔值没有可限制的序列 |

图结果形式不按解行计数。一个 `CONSTRUCT` 行可以实例化整个模板，一个 `DESCRIBE` 行可以提取一整份简洁有界描述。如果调用方把这样的查询限制为一千，却收到十万条陈述，这个 governor 就没有起到限制作用。

### 3.2 上限包含边界，零也是有效值

消耗**等于**上限时允许继续；只有将要超过上限才触发。零是有效上限，会在第一个计费工作单位处触发。这与 `PagedQueryLimits` 对 I/O 层的定义一致，也解释了语料库的 `boundary` 档（上限等于测得成本）必须**完成**，而 `over-bound` 档（上限等于测得成本减一）必须触发的原因。

计费在 `u64::MAX` 处饱和，而不溢出：资源计量器中的算术 panic 会把预算耗尽变成崩溃。

每个临时存储区按自身的确定性增长计费：单独计费的聚合缓冲区／状态以及其他存储区都不能充当它的水位线。重复检查点不会重复计费同一个字节。清空／替换以及独立求值的副本各自开始计量；不同的执行记录独立计量其保留值。存储区代理按每个拥有值的词法／IRI 负载加每项 32 字节求和；身份预留同样按保留标签的字节数加 32 计费。

普通计算输出在算子提交边界设置检查点，此时才知道存储区的精确增长量。报告的消耗可以比上限多出该算子的一次增长量。如果要在产生值之前准入 `CONCAT`、`REPLACE`、聚合和扩展函数的输出，就必须猜测尚不存在的值的字节数。

具体的源输入预留，以及每次新空节点分配，都会立即设置检查点。有状态的用户函数子执行保留并计费自己的预留副本。耗尽仍然是带类型的 governor 结果：不完整的表达式行和模板／列表／SERVICE 输出不会交付；UPDATE 请求会在发布之前中止其暂存修改。这些检查点在首次触发之后停止进一步分配，但不会撤销在触发之前已经到达的、经过认证的 WHERE 前缀。

## 4. 计费规则（规范性）

`fuel` 统计**可观察的求值事件**。每个计费点都收取一个单位，这是刻意的选择：所有成本都为 `1` 的规则，才能让调用方理解 fuel、让语料库固定它，而不是得到只对当前构建有意义的加权分数。

| 计费点（`CHARGE_SCHEDULE` 标签） | 成本 | 每次计费对应 |
|---|---:|---|
| `algebra-node-entry` | 1 | 求值时进入一个代数节点 |
| `committed-output-row` | 1 | 向算子输出提交一行 |
| `bgp-candidate-quad` | 1 | 匹配基本图模式时检查一个候选四元组 |
| `path-frontier-expansion` | 1 | 展开一个属性路径前沿节点 |
| `row-expression-evaluation` | 1 | 对一行求值一个表达式（按行而非子表达式计费，因此成本不随规划器变化）；此外，凡是在任意精度数值塔上执行的 `xsd:integer`／`xsd:decimal` 操作，每个二进制 `u64` limb 操作再计一个单位，包括算术、比较、一元函数、强制转换、结果呈现，对此类值进行的 `SUM`／`AVG`／`MIN`／`MAX`／`ORDER BY`／统计折叠，以及每种策略下的十进制除法。操作执行前，按它自身的成本界限计费；该界限仅由操作数大小计算 |
| `user-function-invocation` | 1 | 调用一次用户定义函数 |
| `remote-request-issued` | 1 | 向远程端点发出一个请求 |
| `remote-row-ingested` | 1 | 从远程端点响应中摄入一行 |
| `update-mutated-quad` | 1 | SPARQL `UPDATE` 向存储插入或删除一个四元组 |
| `property-function-invocation` | 1 | 调用一次宿主提供的属性函数关系（针对一个驱动行执行一次 `open`） |
| `property-function-row` | 1 | 属性函数关系输出、且引擎接受的一行 |
| `aggregate-invocation` | 1 | 折叠一个 `(group, aggregate expression)` 对，即折叠的初始化／结束开销 |
| `aggregate-accumulation` | 1 | 把一个值折叠进某组的运行中聚合状态 |
| `exists-probe-answered` | 1 | 通过记忆化探测求值，回答一个 `EXISTS`／`NOT EXISTS` 过滤条件 |
| `exists-definition-answered` | 1 | 对 `EXISTS`／`NOT EXISTS` 内部进行一次按行定义求值：每种把该行限制到内部相关变量后得到的不同取值计一次，绝不按每个外层行计一次 |
| `exists-inner-solutions-consumed` | 1 | 定义路径的内部在首次见证停止之前物化的一行 |
| `property-function-work` | 1 | 属性函数关系执行、并通过 `PfCursor::take_work` 报告的一个内部工作单位；单位由关系自身定义，例如检查一个候选项或解码一条倒排记录，因为引擎无法查看宿主代码内部来定义单位 |
| `native-function-work` | 1 | 原生扩展内核执行的一个已文档化内部工作块；其工作观察器在执行前准入并计费该块，并在块之间轮询调用方的停止条件 |

`update-mutated-quad` 是唯一位于查询求值器之外、且不由代数节点产生的计费点。`CLEAR ALL`、`MOVE`、`COPY`、`ADD`、`LOAD` 和 `DATA` 形式的工作量与**存储**成正比，而不与请求文本成正比；这些工作不会进入求值器。如果没有这一点，即使调用方设置了所有上限，`CLEAR ALL` 仍可处理一亿个四元组直到完成，同时报告零消耗。它按操作、在应用四元组**之前**计费，因此一次修改会超出上限时，该操作不作任何修改，而不是只完成一部分。

两个 `property-function-*` 点针对另一种由外部决定多重集大小的生产方补上了同类计费。属性函数调用从谓词位置进入宿主代码，摄入该关系选择输出的行。如果没有这两个点，整个调用只会按通用节点计费：进入时一个 `algebra-node-entry`，每个已提交输出行一个 `committed-output-row`。这些通用点已经统计提交行和进入的节点，但不会单独标识关系调用及被接受的源行。专门计费点使这两个事件显式可见；关系特有的内部工作则在下文另行计价。

* `property-function-invocation` 在调用准入拒绝之后计费，例如元数不匹配或没有声明模式支持访问模式时不会计费；它紧接在进入关系之前。这与 `user-function-invocation` 的位置相同，理由也相同：被拒绝的调用没有执行求值，为从未发生的工作计费，就会使规则描述查询文本而不是实际执行。
* `property-function-row` 与 `remote-row-ingested` 经过同一个受 governor 管控的摄入核心，按输出顺序计费：先检查中间单元格上限，再在行被驻留之前计费。按行顺序计费，使摄入的多重集成为关系输出的位置前缀，截断证书才能描述它。调用**过滤掉**的行——与已绑定参数位置不一致，或与重复变量的较早出现不一致——从未准入，因此不计费；它是普通的不匹配，已由提出请求的那次调用计量。

准入控制按所选的物理执行计价。预测峰值是已记录算子峰值中的**最大值**。普通 `JOIN` 中符合条件的正向右操作数接收左侧多重集的行数预测和确定绑定掩码；其输出已包含驱动行的重数，不会再乘一次该多重集。`OPTIONAL` 一次预测一个驱动行出现，再以驱动数量乘每次出现的匹配数来计算累计输出，填充时匹配数至少为一，并采用两个操作数模式的合并宽度。变量不相交的操作数仍采用只计一次因子的计划。

属性函数节点贡献 `rows_per_invocation(mode) × driving_rows` 行；`columns` 等于关系展开后的元数。`driving_rows` 是调用直接左分支的预测行数，沿受支持的包装和链式结构追溯；没有预测时为 `1`。`rows_per_invocation` 按调用**实际**采用的访问模式读取；勘测运行之前，可行性排序已经固定该模式。高估最多使调用方失去一次本可得到的答案，不会给出错误答案；低估也不会改变答案，因为实时单元格上限仍然生效。

可以逐代数节点读取 fuel 去向：`explain_query` 在 `METERED` 下运行，返回 `QueryExplanation`。其账本按节点和计费点分解同一个 fuel 总量，并列出成本规划器对每个基本图模式的估计。

两个 `aggregate-*` 点对聚合补上了同类计费。聚合是第三种由外部——此处是数据，而非计划——决定每组工作量的生产方。内置聚合与注册的自定义聚合都把一组行折叠成一个答案；如果没有专门的计费点，这个折叠就只按通用节点计费，进入时一个 `algebra-node-entry`，每组输出一个 `committed-output-row`。这样，`GROUP_CONCAT` 把一百万行折叠成一组与把十行折叠成一组的计费就相同。

* `aggregate-invocation` 对每个 `(group, aggregate expression)` 对计费一次，位置是求值器中唯一决定使用内置状态机还是注册自定义累加器的分派点。因此两种聚合按同样规则计费；同一 `GROUP BY` 上的 `SELECT` 若指定多个聚合表达式，则每组每个表达式各计一次，与各组行数无关。
* `aggregate-accumulation` 对折叠路径将传给 `step` 的每个值计一次：内置聚合要求参数表达式求出已绑定项；自定义聚合要求参数元组的每个位置都已绑定。计费在可能丢弃它的 `DISTINCT` 去重检查**之前**。生成并检查该值就是这一点所计量的工作，丢弃重复项时这项工作早已发生。因此，`COUNT(DISTINCT ?x)` 折叠同一值的一百万个副本时，此点计一百万次，即使底层累加器的 `step` 只执行一次。`COUNT(*)` 完全没有参数表达式，因此无条件按行计费，而不是永不计费。

若某行的参数表达式确实未绑定，除了已经执行的调用计费之外，这两个点不再把它计为一个值：没有求出的值可供 `aggregate-accumulation` 计量。

## 5. 停止信号与唯一的时钟读取

截止期限与取消采用同一个原语：宿主提供的 `StopSignal`，其接口是 `poll() -> Option<StopCause>`。两者仅报告的原因不同。

**实现必须锁存。** `poll` 一旦返回 `Some(cause)`，之后必须始终返回同一原因。可以解除触发的信号不是 governor：查询可能在一个计费点观察到截止期限，下一点又观察到未触发信号，于是越过截止期限继续执行，而调用方却被告知查询在早已超出的预算内完成。

随库提供两个实现：

* `CancellationFlag`：宿主可从任意线程翻转的共享单调位。其构造保证锁存；应为每次查询创建新标志，而非重置旧标志。
* `WallDeadline`：本 profile **唯一的时钟读取器**。库提供它，是为了避免把构造截止期限变成调用方的义务：如果每个调用方都自行编写信号，就会对“过期”产生不同定义，而本 profile 在其他地方同样拒绝这种行为差异。

`WallDeadline` 按目标采用不同实现：原生使用 `std::time::Instant`，`wasm32-unknown-unknown` 使用宿主的 `Date.now()`，从而继续支持 wasm。wasm 部分通过对真实模块执行 Node 往返来验证，而非仅凭交叉编译成功。

它在 `now >= deadline` **或** `now < start` 时锁存。第二项是**回拨规则**：wasm 的时钟是挂钟时间，可被 NTP 调整。时钟后退会使朴素的 `now >= deadline` 检查无法触发，从而让查询悄悄超过调用方以为正在生效的预算。观察到回拨时按过期处理，绝不恢复预算，因为引擎无法区分小幅时钟修正与大幅回拨。两个目标使用同一个谓词实施这一规则。

信号在进入和离开代数节点时、未启用 fuel 时的每个逻辑计费点、启用 fuel 时每 **`STOP_POLL_FUEL` = 4093** 个单位、跨越上限时，以及联邦请求前后被观察。退出检查点不可省略：它避免最后一个算子内部触发的信号仅仅因为不存在下一个节点而被报告为完整完成。轮询间隔是构建常量，绝不是可调参数；若让调用方调整间隔，注入截止期限被观察到的确切计费点就会成为调用方配置的一部分。该常量是素数，既不是二的幂，也不是十进制整百整千值，因而减少与常见十进制整数上限的周期对齐，但不保证与调用方所选的每个上限都互质。`STOP_POLL_FUEL` 属于固定身份的一部分（§10），因为它界定周期轮询之间的计费工作间隔。

再次提醒 §1 的核心区别：本节的挂钟时间测量不具有确定性。轮询规则本身具有确定性，并由注入截止期限的矩阵固定。

## 6. 优先级（规范性）

多个 governor 在**同一个计费点**同时满足时，由 `TrippedGovernor::precedence_rank` 决定采用哪一个，较小者优先。顺序与内核类型定义在一起，使各层对同时触发作相同处理；分配优先级的 match 没有通配分支，因此新增 governor 必须同时确定优先级。

1. 真正的 `EvalError`：**优先于任何 governor**；在合并求值结果处比较，而非在优先级函数内部比较。
2. `Stopped { cause: Cancelled }`：显式取消是一项决定。
3. `Stopped { cause: Deadline }`：截止期限信号触发；挂钟实现基于经过的时间，调用方也可以注入确定性信号。
4. 所有 `Refused { .. }`，按维度顺序排列：`IntermediateCells`、`Fuel`、`AnswerRows`、`ScratchBytes`、`RemoteRequests`、`UdfDepth`、`Pages`、`Bytes`。**准入拒绝**在首次计费之前决定，因此它是任何数值 governor 所能到达的最早判定，并解释为何没有开始执行。
5. 所有 `Budget { .. }`，采用同一维度顺序。`IntermediateCells` 最先，是因为它防止不可恢复的分配失败；`Pages` 和 `Bytes` 属于按需分页层，通常作为该层自己的带类型错误暴露，但仍在这里排序，使共享顺序完整覆盖所有情况。

停止信号每隔 `STOP_POLL_FUEL` 个单位轮询一次，因此 fuel 可以在两次轮询**之间**超过上限。规则是：在每个计费点，对**此时已经成立**的条件按优先级处理，绝不把将来可能成立的条件纳入比较。

### 6.1 `Refused` 与 `Budget` 是不同判定

`TrippedGovernor::Refused` 报告在**准入**时拒绝的上限：规划器对某项操作的估计已经超过上限，所以未执行任何工作，也没有消耗。刻意设为独立变体，是因为把它并入 `Budget` 会把**估计值**放进证据向量的 `consumed` 位置，而其他维度填入的都是实测值；这样一份记录就会声称查询花掉了仅仅预计会花掉的资源。

拒绝绝不声称结果完整。因此，高估最多使调用方失去本可得到的答案，绝不会给出错误答案。

## 7. 答案完整性区间

截断的执行返回 `BudgetExhausted { tripped, evidence, partial }`。`partial` 字段的类型是 `PartialAnswers`，表示**三种区间**，而非简单的是／否。这两个界限允许的用法不同；合并它们，要么会禁止正确用法，要么会允许错误用法。

| 分支 | 已证明的性质 | 允许的用法 |
|---|---|---|
| `Certain(rows)` | 经过认证的**下界**：这里的每一行都是答案 | 把这些行接纳为答案；查询可能还有更多答案 |
| `AtMost(rows)` | 经过认证的**上界**：所有答案都在这里，但某些行可能不是答案 | **只能作否定判断**：不在此结果中的行，确定不是答案 |
| `Unknown(barrier)` | 两种界限都未能保留到根节点 | 不允许任何行越过该边界。`NonMonotoneBarrier` 指明扣留这些行的算子，调用方可据此判断应增加预算还是修改查询 |

证书通过对代数进行静态分析计算，依据**前缀**单调性，而非子集单调性。这一区别不可省略：`Slice(0, 1)` 不具备子集单调性；如果采用子集证书，就可能允许某个唯一答案为 `a` 的查询输出 `b`。

### 7.1 位置前缀位

`PartialSparqlResult::is_positional_prefix()` 携带行本身无法表达的另一个事实：这些行是否按顺序构成真实输出的**最前面几行**。它描述与完整输出的关系，本身不是耗时保证。对确定性 governor，在相同查询和快照上提高上限重新执行，会先返回这些行，因此调用方可通过提高上限分页。挂钟时间截止期限不具备确定性；即使延长持续时间，另一次执行也可能更早停止，因此必须视为全新执行。

不具备位置前缀性质时，这些行仍是可靠的子多重集（或超多重集），但其**位置**没有保证。`ORDER BY` 会失去这一性质；截断左侧优先哈希连接的**右**输入，或 `UNION` 的**左**分支也一样，因为这些情况从输出中间删除行，而不是只截去末尾。

### 7.2 部分结果的模式

完整结果报告查询生成的列。部分结果报告**实际求值**的算子分支的列。四个算子在这里有所不同：当 `JOIN`、`OPTIONAL`、`LATERAL` 或 `UNION` 的**左**分支截断时，只报告左分支的列。右分支刻意不求值：预算耗尽后启动新子树会允许无界工作，而 governor 不能这样做。本引擎在求值期间选择列**顺序**，因此不执行刚刚被拒绝的工作，就无法导出右分支的列。行本身不受影响，只是报告的列列表更窄；比较完整路径与部分路径列列表的调用方必须考虑这一点。

### 7.3 `UPDATE` 在结构上没有部分结果分支

`GovernedUpdateOutcome` 刻意不同于 `GovernedOutcome`。部分**修改**无法认证：若 `INSERT`／`DELETE` 只落地一半，却报告“预算耗尽”，那不是不完整结果，而是损坏的存储；之后每个查询都会确信地从中读取，因而这种损坏是隐蔽的。

因此，触发分支只携带 governor 和证据，**在结构上没有其他内容**。它没有可读取部分修改的字段，因为没有部分修改。请求触发上限后，调用方的数据集句柄保持原状。

可变分支先冻结成私有句柄，再由同一个请求状态在唯一的句柄发布赋值之前轮询停止信号。批量撤销命名图声明时，也会在每个基础声明或新增声明之前轮询，所以即使 DROP 只涉及空图，也可以在条目之间停止。这些检查点不会把图元数据计为四元组修改；按行计费的 fuel 规则不变。

### 7.4 蕴涵机制（entailment regime）分两个阶段接受管控

第二阶段——在物化闭包上执行 SPARQL 求值——受到完整管控。此处触发时返回普通的 `BudgetExhausted`，并携带经过认证的部分答案。第一阶段——物化闭包——**只遵守停止信号**。这是语义边界，而非遗漏：推理执行的数值上限需要一套计费规则；如果允许调用方设置这种上限，同一机制、同一数据的两个调用方就可能得到不同闭包。停止信号则没有这种性质：闭包要么逐位完全等同于未附停止信号时的完成结果，要么执行以 `ClosureStopped` 结束且不返回任何闭包。完整理由见 `purrdf_datalog::stop`。

## 8. 联邦传输接口

只有能够放弃正在进行的调用的传输实现，才能遵守 `HttpRequest::stop`；宿主并不被强制要求编写这样的实现。忽略它也是受支持的实现方式，两种情况的契约如下：

* **忽略** `stop` 的传输仍在**每请求粒度**受到限制，而非完全无界：求值器在分派之前轮询信号并为请求计费，在调用返回的那一刻检查结果。
* 不读取信号的传输会失去**位置前缀保证**。遵守信号的传输会**放弃**本次交换，因此手中的行仍是真实输出最前面的行，并保留确定性恢复所需的关系。不读取信号的传输会**完成**交换，然后其响应被丢弃；因此缺失的行位于答案中间，而非仅在末尾，此时撤销位置前缀保证。
* 两种情况下多重集界限都保留：证书都是 `Certain`。失去的是可恢复性，不是正确性。

两种情况都由语料库的 `service-*-transport-*` 用例固定，记录请求传输执行的精确交换次数。这个次数区分了“请求被阻止”与“请求已经发出但答案被丢弃”；仅靠 governor 证据无法区分它们。

### 8.1 属性函数关系接口

`PfCursor::next` 同样没有一个被要求必须读取的信号。如果某个关系在一次 `next` 内永远阻塞，停止检查粒度就退化为一次调用。这里的契约比传输更强，因为关系输出是行**流**，而非一次原子交换：

* 求值器在打开游标之前及相邻拉取之间轮询停止信号；每个输出行进入多重集之前，都经过逐行准入点。该点本身是有界工作检查点，因此无论关系是否读取过信号，都能在那里观察到已触发信号。
* 因此，不读取信号的关系仍然受到**逐行**限制，而不只是逐次调用限制：额外的一行会被拉取，但随后在准入时被拒绝，不会摄入。
* 这一后果由语料库中的 `property-function-*-relation-cancel-mid-invocation` 用例对固定：在完全相同的一次拉取处触发调用方标志，一个游标放弃调用，另一个完全忽略信号；两者答案**逐字节一致**，包括证书。在调用内部读取信号是一项优化，而不是使查询有界的前提。

这一对用例都携带 `positional-prefix=false`。这不是遵守信号与不读取信号之间的区别泄漏到了结果中，而是因为语料库横向驱动调用：`?s ex:p ?m . ?s ex:pf:emit ?x` 通过 `LATERAL` 把驱动模式与调用相连。因此，调用本身的输出顺序不等于连接输出顺序。发生在横向驱动调用内部的截断，可以为答案提供下界，却无法说明截断发生在答案的什么位置；无论游标是否配合，都因这一结构原因撤销位置前缀保证。在独立形式中，调用直接位于投影节点之下，其自身顺序与输出顺序一致，因而保留该保证；这一部分见 `property-function-first-row-fuel-ceiling` 用例，以及 `property-fn-eval` 自己的截断测试。

`rows_per_invocation` 是另一项义务，而且是**如实声明的契约**，并非提示：如果声明的界限已经超出单元格上限，准入控制会拒绝该计划，因此低报实际数量会使准入决定出错。确实无界的生成器应声明 `u64::MAX`。

## 9. 证据

`GovernorEvidence` 在**完整**路径和耗尽路径上都会返回，因为“已完成，消耗 N fuel，峰值 M 单元格”正是调用方初次测定预算的依据。它携带每个维度的消耗、当前上限（原样回显，使证据能够自我说明），以及导致执行停止的 governor；未停止时为 `None`。

governor 状态**仅属于一次操作**。每次执行都应创建一个：消耗会累计，跨查询共享状态会把一个查询的预算消耗带入下一个查询，形成间歇性且极难发现的错误。

## 10. Profile 身份（规范性）

| 常量 | 值／读取方式 |
|---|---|
| `GOVERNOR_PROFILE_ID` | `purrdf-sparql-governors` |
| `GOVERNOR_PROFILE_VERSION` | `18` |
| `GOVERNOR_PROFILE_DIGEST` | 由内容导出，见下文 |
| `STOP_POLL_FUEL` | `4093` |

摘要**由内容导出，而非手工声明**。“成本变化时记得更新”只靠自觉实施，等于没有强制实施：只要忘记一次，使用方固定的身份就会悄悄指向一套已经不存在的规则，所有按它设定的预算都会出错。对表格计算散列，意味着规则变化时**不可能**保留旧身份。

摘要是逐行编码原像的 SHA-256，以小写十六进制表示：先是 profile 标识符，再是版本，然后按表格顺序为 `CHARGE_SCHEDULE` 的每一项写入一行 `label\tcost`，每行均以 `\n` 结尾。标签不能包含制表符和换行，因此一项不会有多种编码，不同规则也不会得到同一编码。使用方仅凭本文即可重新计算：

```sh
{ printf 'purrdf-sparql-governors\n18\n'
  printf '%s\t1\n' algebra-node-entry committed-output-row bgp-candidate-quad \
    path-frontier-expansion row-expression-evaluation user-function-invocation \
    remote-request-issued remote-row-ingested update-mutated-quad \
    property-function-invocation property-function-row \
    aggregate-invocation aggregate-accumulation \
    exists-probe-answered exists-definition-answered \
    exists-inner-solutions-consumed property-function-work native-function-work
} | sha256sum
# 37dc8ab3f6505ede9167817441a9162852fd2453bfdaa29b967d213f065d9674
```

SHA-256 通过 `sha2` crate 计算，它是没有熵源的纯软件实现，因此推导过程可用于 `wasm32-unknown-unknown`，并在所有目标上复现。

**固定身份的含义。** 标识符和版本说明双方约定的是**哪一套**规则；摘要说明这套规则的**确切内容**。三者一起让 fuel 数字可以跨使用方比较：持有同一三元组的双方，谈论的是按同样方式计价的同类事件。它们不说明执行过哪些验证用例；那是 §11 的职责。

## 11. 规范性向量语料库

语料库位于 `vectors/sparql-governors/`，且已**冻结**：每个负载字节都由每次构建检查的 SHA-256 清单覆盖（`scripts/check-corpus-frozen.py`），因此悄悄修改预期值会导致失败，而非通过。它由 `crates/sparql-conformance/tests/governor_corpus.rs` 执行，并列入 [`CONFORMANCE.md`](./CONFORMANCE.md) 的计分表。用例清单和文件格式见该语料库自己的 `README.md`。

每个可复现用例固定**三份**记录，刻意保持分离：

1. **结果判别标签**，采用内核自己的 `TrippedGovernor::label` 词汇；
2. **经过认证的行及证书类别**（`certain`／`at-most`／`unknown`，加上位置前缀位）；
3. **执行消耗**，独立于行记录。

属性函数或聚合用例还固定**第四份**记录：从逐节点账本读取的、**按计费点**分解的实测 fuel。fuel 是一个总数；v5 为属性函数接口加入两个计费点，v6 又为聚合折叠加入两个点，因此只看档位，无法区分一对计费点中的哪一个发生了变化。

第三份记录最容易遗漏，也最不可能事后重建：只固定行的语料库，无法发现恰好仍在相同位置截断的计费规则变化。答案不变，消耗记录却变了；所有按旧规则设定的预算都会悄悄失效，语料库却仍然全绿。

挂钟时间截止期限冒烟用例是刻意的例外：它只有结果判别标签，因为行数和消耗取决于经过的时间。整个语料库共 54 个用例，其中 46 个构成零上限、边界或超界档位；其余 8 个涵盖传输、关系、计费接口、`EXISTS` 证据和挂钟时间。

边界是**测出的，绝非手工指定**。对于每个调用方可设置的维度，语料库包含 `zero` 上限（必须触发）、等于实测成本的上限（必须**完成**，因为边界包含在上限内），以及低一个单位的上限（必须触发）。运行器每次都在 `METERED` 下重新测量并重新推导这一关系，而不是信任文件中的数字。

三个档位组用于区分两个**由引擎观察**的属性函数计费点，而不是覆盖某个维度：即 `property-function-invocation` 和 `property-function-row`，这两个点由求值器自己计数。（v8 的 `property-function-work` 是第三个点，这里不按档位覆盖；它由关系**报告**，本语料库的关系都是不报告内部工作的脚本夹具，因此这些档位都记录 `property-function-work 0`。实际报告该点的验证位于有真实内部工作的关系处，即嵌入 kNN 接口自己的计费测试。）一个组多次调用完全不输出行的关系，因此行计费为零；一个组单次调用输出很多行；另一个驱动 1200 行，超过求值器的并行分叉阈值。最后一组使 §1 的并行不变性成为冻结向量，而不只是文档声明：`METERED` 启用中间单元格计数器，档位用例则只设置 fuel。若记账行界限对应的外层解向量布局不可表示，则允许相同的并行驱动；可达到的单元格界限保留有界顺序生产。两种情况下记账和预测准入都保持启用。等于测量值的边界与低一个单位的超界档位，仍必须复现相同计费和按源顺序的触发点。

另外两个档位组以同样方式区分两个聚合计费点：`aggregate-invocation-fuel-*` 在没有输入匹配的单个隐式组上折叠十二个聚合表达式，因此累加计费为零；`aggregate-accumulation-fuel-*` 在包含十二行的单个隐式组上折叠一个聚合表达式，因此恰好有一次调用计费。两个夹具都在远低于边界上限的位置完成单组折叠，所以比边界低一个单位的超界上限，触发于该组已经计算完成的输出行的通用逐节点 `committed-output-row` 计费，而非折叠内部。边界与超界都报告该行：前者为 `complete`，后者为经过认证、具有位置前缀性质的 `budget-exhausted`。

### 11.1 语料库摘要及其固定方式

```text
GOVERNOR_CORPUS_DIGEST = 6f856ca8ab7274b85908ac329bff7d8b806ac9e18f91f479ddb002bd07090a2f
```

这是语料库冻结清单的 SHA-256，而清单又覆盖每个负载字节。以清单定义摘要，而不另造遍历规则，使使用方只需一条命令即可复现，无须运行本 crate 的代码；只有作者自己算得出的摘要，不是别人能够独立核验的摘要：

```sh
sha256sum scripts/conformance-frozen/vectors-sparql-governors.sha256
```

库推导出同一个值，运行器比较两者，因此修改语料库时必须在同一个提交中重新固定常量。

**该摘要认证什么。** 它固定的是**证据**，而非行为：两个构建的摘要相同，说明双方使用的用例和预期数字相同，从而能明确讨论行为差异。行为本身由 `GOVERNOR_PROFILE_DIGEST` 固定，语料库则用于证明某个构建实现了它。

## 12. 版本管理

任何可能**移动调用方预算触发位置**的变化，都必须递增 `GOVERNOR_PROFILE_VERSION`：

* `CHARGE_SCHEDULE` 的变化：新增、删除、重命名计费点，或改变其价格；
* §6 优先级顺序的变化；
* §3.2 包含边界规则的变化；
* 即使规则本身逐字节不变，某个查询执行的计费事件数量发生变化；
* 即使数值成本不变，停止检查点发生变化，包括仅涉及元数据的工作和最终 UPDATE 发布。

不会移动计费的变化，例如重构或更清楚的诊断，不递增版本。这样的克制，才能让版本号值得固定。

| 版本 | 变化内容 |
|---|---|
| 1 | 初始规则 |
| 2 | 规则逐字节不变；嵌入表达式的 `EXISTS` 不再按每个 rayon 分块重新求值，因此其 fuel 不再依赖机器线程数 |
| 3 | 规则逐字节不变；答案上限和 `LIMIT` 沿经过认证的前缀单调路径下推，使行上限下的叶节点到达上限就停止扫描，而非物化全部输出。还新增 `Refused`，并把答案上限应用于 `CONSTRUCT`／`DESCRIBE` 输出陈述 |
| 4 | 首个规则**并非**逐字节相同的版本：追加 `update-mutated-quad`，因为 SPARQL `UPDATE` 开始受 governor 管控，而修改是预算必须能够限制的工作。没有任何**查询**对此点计费 |
| 5 | 追加 `property-function-invocation` 和 `property-function-row`，因为求值器增加了第二种由外部决定多重集大小的生产方，即从谓词位置调用的宿主关系。准入控制也开始根据关系声明的行界限为调用计价。未注册属性函数的查询不计这两个点 |
| 6 | 追加 `aggregate-invocation` 和 `aggregate-accumulation`，因为求值器的第三种此类生产方——内置或注册自定义聚合——把一组行折叠成一个答案，而此前折叠的初始化／结束及逐值工作仅按通用节点计费。两个点都由唯一的聚合分派位置计费，因此相同组形状下，内置与自定义聚合消耗相同 fuel。没有聚合的查询不计这两个点 |
| 7 | 追加 `exists-probe-answered`、`exists-definition-answered` 和 `exists-inner-solutions-consumed`，使存在性求值的策略选择成为可观察事件：一次记忆化探测、一次按行定义求值（每种把行限制到内部相关变量后得到的不同取值计一次，绝非按每个外层行计一次），以及定义路径内部在首次见证停止之前物化的一行。三者使探测／定义路径的区别及其见证成本可以直接从证据读取，而不是推测，因而可按查询实际采用的策略设定上限。没有 `EXISTS`／`NOT EXISTS` 过滤条件的查询不计这三个点 |
| 8 | 追加 `property-function-work`。v5 按**引擎**可见的两个量——驱动的调用次数与接受的行数——计价；但生成器关系的主要工作不在这里：检查一百万个向量、返回五行的近邻搜索只计六个单位，相当于把一百万次距离计算按六行表扫描计价。计数由唯一能观察自身搜索内部的关系，通过 `PfCursor::take_work` 提供；它会实际**消耗**预算，而不只是记录。因此，高报会耗尽该报告方调用者自己的预算；低报（默认是零）可能降低记录精度，但不会损害正确性，因为其他上限保持不变。按 v5 接口编写的关系不计此点 |
| 9 | 规则逐字节不变；`FILTER`、`BIND`、`UNFOLD` 和每种聚合的逐行循环经过同一检查点：在下一行之前观察已经锁存的触发；`UNFOLD` 在摄入之前准入行；工作只向停止轮询报告一次；跨线程分叉的循环只准入剩余 fuel 能覆盖的行，并按源顺序提交。因此，它在与顺序循环相同的行上触发，消耗相同 fuel，保留相同前缀。这些循环中的计费顺序，以及分叉循环中轮询的位置发生变化 |
| 10 | fuel 规则逐字节不变；每个临时存储区独立于聚合缓冲区／状态和子存储区计量自身保留量，避免无关的临时内存计费掩盖后续计算值。具体身份注册、新空节点分配和有状态子执行的预留副本立即检查临时存储增长。不完整的表达式／模板／列表／SERVICE 输出被扣留；触发时中止暂存 UPDATE 发布。临时内存消耗及其上限触发位置可能变化 |
| 11 | fuel 规则逐字节不变；普通连接中符合条件的正向操作数接收传入绑定，把独立关系工作替换为索引候选访问与携带行。OPTIONAL 对每个驱动行出现求值其正向右操作数，改变节点进入次数和行计费顺序；符合条件的相关 EXISTS/NOT EXISTS 使用原生限制和首次见证定义路径，改变候选项及存在性证据计费。携带列改变中间单元格宽度；准入预测采用带传入绑定的计划及关系局部连接域。完整答案保持其作用域和多重集重数；fuel 总数和预算截断点可能变化 |
| 12 | fuel 规则与查询计费逐字节不变；受 governor 管控的 UPDATE 在每次批量撤销命名图声明之前，以及冻结私有分支之后、发布之前轮询。仅元数据工作与最终发布边界可能更早观察到停止；声明仍不同于计费的四元组修改 |
| **13** | 规则不变；`row-expression-evaluation` 的计量内容与临时内存上限的触发位置变化，因为 `xsd:integer` 和 `xsd:decimal` 在所有大小上都变为精确：超出机器字的值在任意精度数值塔上运算。两个百万位整数的一次乘法可以有数十亿次 limb 操作；一位系数也可以呈现为百万位结果（反复对 `0.1` 求平方会不断加倍标度）。若仍只按一个 `row-expression-evaluation` 计费，平方链就可以在所有上限下持续运行直到内存耗尽。现在，所有数值塔操作——算术、比较、一元函数、强制转换、结果呈现、对此类值执行的 `SUM`／`AVG`／`MIN`／`MAX`／`ORDER BY` 和统计聚合，以及非默认策略下的任何除法——都在执行前，按仅由操作数大小计算的自身成本界限，为每个基数为 `1e9` 的 limb 操作收取一次 `row-expression-evaluation`，并对工作字节作临时内存准入（若不能与此前已分配内容共存则拒绝，但不加入累计总量）。机器字操作数不额外计费，因此数字都能放进机器字的查询仍得到 v12 下相同的执行。所有宿主按求值顺序把计费送达 governor：在没有其他调用方上限阻止的情况下，受 fuel／临时内存上限管控的 `FILTER`、`BIND`、`GROUP BY` 或 `OPTIONAL` 过滤条件可以分叉；每个工作线程在求值内部记录其行、组或左行的每次计费，包括 fuel、显式临时内存、瞬时工作集和存储区增长，各自对分叉时的可用余量作准入；有序提交再在求值本身的上下文中按源顺序重做这些计费，沿途把工作线程分配的项纳入本身的存储区。因此，每种线程数下的触发、消耗和答案，都与按顺序运行的循环相同，正如 wasm32 构建那样；表达式内部触发时同样扣留算子输出。调用方设置 fuel 或临时内存上限时，工作线程按输入顺序领取小块，共享一个包含已分配字节的累计消耗；总量超过余量后，每个工作线程都停止。随后提交在顺序循环相同的位置触发，或从第一个工作线程停止的项开始按顺序完成。因此，循环超过上限后持有的内容大约是一份可用余量，加上每个工作线程尚未报告的共享间隔与在途行。仅停止信号与无限计量使用普通分块，但采用同样的有序计量。即使公共行上限辅助函数丢弃了外层解向量布局不可表示的界限，单元格计量和预测准入仍启用；可达到的单元格上限保留有界顺序生产，仅用于记账的单元格则允许符合条件的原生及 CLI `--fuel` OPTIONAL 过滤条件分叉，并使用可失败的输出预留与有序拼接。历史测量中，4400 行、每行把 3125 位整数提高到 32 次幂（每行约 1.75 MB 临时内存，加载数据需 67 MB），在 100000000 字节上限下，1、8、32 个线程的峰值内存分别为 130、231、284 MB；在 400000000 字节上限下则为 438、505、536 MB。v12 的分叉循环丢弃工作线程分配但没有保留的项，例如查询常量和中间值，因此比顺序循环少计临时内存：`SELECT (UCASE("abc") AS ?u) {}` 现在计 148 字节（v12 为 74），`concat` 语料用例计 465（原为 353），`exists-inner-counters` 计 153（原为 76），自定义聚合的临时内存超界则认证顺序折叠的空前缀 |
| **14** | 规则不变。精确算术使用工作区共享的二进制 `u64` 整数引擎。数值成本计入八字节 limb、乘除法工作存储，以及十进制解析／呈现的进制转换。准入读取常数时间的二进制大小界限；不确定的十进制位数界限不能触发精确指数捷径。机器字分派及其内联 `i128` 操作保持不变。应按重新生成的语料库重新测量任意精度 fuel 和临时内存上限。 |
| **15** | 规则不变。携带证据的 `EXISTS`／`NOT EXISTS` 保留原始主体和每个备选见证，不使用普通定义路径中合成的首次见证 `Slice`；节点／输出计费遵循实际主体。 |
| **16** | 追加 `native-function-work`。原生扩展内核通过同一调用方的 governor 对物理存储作准入、为已文档化的内部工作块计费，并在块之间轮询。此前十七个标签保持原顺序与单位成本。不调用这些原生函数的查询保持原有规则。应针对所选内核和 profile 重新测量上限。 |
| **17** | 规则不变。默认精确分支除法对可终止商保留完整标度，否则舍入到小数点后十八位，采用半数取偶。其数值塔工作和 AVG 的最终除法，即使对以前走有界数值路径的操作数，也可能移动 fuel 与临时内存截断点。应按新默认行为重新测量数值上限。 |
| **18** | 规则不变。仅精确的数值与精确时间秒数通过经准入的求值器算术、比较、时区调整与呈现路径。这些操作现在为任意精度工作和保留临时内存计费，取代原有界或零成本路径。应重新测量数值与时间查询的 fuel 和临时内存上限，包括答案未变的查询。 |

版本 **15** 保持计费规则不变。携带证据的 `EXISTS`／`NOT EXISTS` 求值原始主体，保留每个备选见证，以及归一化时可能丢失声明的代数节点。它不进入普通定义路径中合成的首次见证 `Slice`；节点进入与输出计费描述实际执行的主体。在两个固定的空属性函数用例中，答案、提供方调用、临时内存和输出计费不变，而 fuel 从 11 降为 10，因为不再进入一个合成节点。仅仅安装了但未使用的关系注册表，不会选择这条执行路径。应重新测量携带证据查询的 fuel 上限和停止截断点。

### 12.1 版本变化时，使用方必须重新验证什么

版本递增不能直接当作无需迁移的升级。下面清单的每项，都涉及一个固定数字可能悄悄失去原有含义的情况：

1. **重新读取 `GOVERNOR_PROFILE_VERSION`**，确认它现在为 `18`，即本节描述、下列步骤针对的版本；然后**重新读取 `GOVERNOR_PROFILE_DIGEST`**，确认它匹配预期采用的计费规则。如果摘要变化而版本未变，这个构建的声明就是不实的，必须拒绝，不能自行调和。
2. 针对自己的代表性查询，在 `QueryGovernors::METERED` 下**重新测量每个 fuel 上限**。旧版本设定的上限针对的工作，当前构建可能不再执行（v3、v11）、现在才执行（v4、v5、v6、v7、v8、v13），或改用不同顺序执行（v9、v11）。**也要重新测量中间单元格上限**：v11 携带传入列，并预测带传入绑定的执行及关系局部连接域。**也要重新测量临时内存上限**：v10 独立计算保留量，并立即检查具体身份分配；v13 对每次任意精度操作的工作字节作准入。不要按比例缩放旧数字。
3. **重新检查设在边界处或接近边界的上限。** 上限包含边界，因此过去恰好等于实测成本的上限可以完成；版本递增后可能差一个单位。
4. **重新读取 `GOVERNOR_CORPUS_DIGEST`**，并针对链接的构建重新执行语料库。没有语料证据的 profile 版本只是声明，不是执行记录。
5. 若 §6 变化，**重新检查同时触发的处理**：查询同时超过两个上限时，调用方观察到哪个 governor，也是本契约的一部分。
6. **重新检查调用方定义的停止检查点。** v12 新增声明工作和冻结后的 UPDATE 检查点；即使每行 fuel 成本不变，确定性信号也可能在不同边界停止。
7. **挂钟时间截止期限没有需要重新验证的固定结果**，因为原本就未对它作此类保证（§1）。不要把截止期限触发点变化当作回归。

`answer-rows`、`intermediate-cells`、`scratch-bytes` 和 `remote-requests` 上限**通常**不受版本递增影响，因为它们计量结果而非事件；但“通常”不是保证，第 2 步的重新测量会同时覆盖它们，无须额外执行。

## 13. 使用方固定的内容

| 字段 | 来源 |
|---|---|
| profile 标识符 | `purrdf_sparql_eval::GOVERNOR_PROFILE_ID` → `purrdf-sparql-governors` |
| profile 版本 | `purrdf_sparql_eval::GOVERNOR_PROFILE_VERSION` → `18` |
| profile 摘要 | `purrdf_sparql_eval::GOVERNOR_PROFILE_DIGEST`（§10） |
| 停止轮询间隔 | `purrdf_sparql_eval::STOP_POLL_FUEL` → `4093` |
| 语料库摘要 | `purrdf_sparql_eval::GOVERNOR_CORPUS_DIGEST`（§11.1） |
| 发行版本 | 读取上述值时所用的带标签发行版本 |

profile 标识符、版本、计费规则摘要和停止轮询间隔一起作为 `ProfileIdentity` 随每个 `QueryExplanation` 传递，因此，对查询成本理解不同的两个构建，不能生成看起来可直接比较的解释。语料库摘要从 `GOVERNOR_CORPUS_DIGEST` 单独读取：它标识外部证据集合，而不是产生某次解释的执行。发行版本标识同时携带两者的已发布构件。

针对链接的构建执行 §11 语料库，才能把固定值变成执行记录。它刻意**不能**把挂钟时间截止期限变成这种记录。最后重申：确定性保证适用于 fuel、答案上限、基数／单元格上限和注入的轮询次数信号；**不适用于经过的时间**。
