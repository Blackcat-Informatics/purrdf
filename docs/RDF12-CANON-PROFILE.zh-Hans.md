# `purrdf-rdfc12` — RDF 1.2 规范化 profile

[English](RDF12-CANON-PROFILE.md) | 简体中文

**Profile 标识符：** `purrdf-rdfc12` &nbsp;·&nbsp; **Profile 版本：** 3 &nbsp;·&nbsp;
**编辑：** Patrick Audley，Blackcat Informatics® Inc.

这两个值不仅写在文档里，也可从库中读取：`purrdf_core::CANON_PROFILE_ID` 和 `purrdf_core::CANON_PROFILE_VERSION`。使用方因此可以断言，实际链接的构建实现的正是自己固定的 profile。

## 摘要

本 profile 规定 PurRDF 为 RDF 1.2 数据集生成的规范字节形式。它以 W3C RDF 数据集规范化算法（RDFC-1.0）为基础，扩展支持 RDFC-1.0 未涵盖的三种 RDF 1.2 结构：具体化节点、注解和三元组项。它还规定了**保留词汇**，并**拒绝**携带这些词汇的输入，只有本 profile 自身输出所采用的两种精确形状除外。这使得规范字节既能安全地用于分配身份，也能从该身份对应的内容重新导出（§3.1）。

## 1. 状态：这不是 RDFC-1.0

对本 profile 输出计算的摘要，**绝不能标为“RDFC-1.0”**。

本 profile 与 RDFC-1.0 有两方面区别，两者都不可忽略：

* **接受的输入更少。** RDFC-1.0 对任何良构的数据集进行规范化。本 profile 会拒绝携带 §4 保留词汇的数据集（§5）。
* **生成的字节不同。** 携带具体化节点或注解的数据集，在这里生成的字节与 RDFC-1.0 实现不同，因为 RDFC-1.0 没有这些结构，也就无从输出它们（§3）。

在 **RDF 1.1 子集**上，也就是没有具体化节点、注解、三元组项或保留 IRI 时，本 profile 与 RDFC-1.0 逐字节一致。这一性质由每次提交都运行的、仓库内固定版本的 W3C `rdf-canon` 测试套件把关，并非仅凭文档声明。

## 2. 基础算法

完整采用 RDFC-1.0，包括“计算四元组的一阶散列”（§4.6）、初始规范标签分配（§4.4），以及带有“计算关联空节点的散列”（§4.7）和排列回溯的“计算四元组的 n 阶散列”（§4.8）。空节点获得 `c14n0`、`c14n1`、……这样的规范标签。输出是陈述行的集合，每行以 `\n` 结束，**按字节升序排列并去重**。

默认散列算法是 SHA-256；也可选择 SHA-384（`purrdf_core::CanonHash::Sha384`），与 RDFC-1.0 §3 对应。**散列算法是身份的一部分**：SHA-384 下生成的字节不能与 SHA-256 下生成的字节直接比较。使用方固定本 profile 时，也必须同时固定算法。

RDFC-1.0 **只规范化空节点标签**。字面量的词法形式、数据类型 IRI、语言标签和基础方向都原样输出，绝不归一化：`"0.70"` ≠ `"0.7"`，`@en--ltr` ≠ `@en--rtl`，任何词法形式都不执行 Unicode 归一化。在本 profile 下，仅词法形式不同的两个数据集也是不同的数据集。

## 3. RDF 1.2 叠加层

在散列和序列化之前，每条陈述都转换为四元组形状。原生四元组保持原状。两种叠加结构按下表展开；其中 `⟨…⟩` 表示以 N-Triples 形式书写的 IRI。

| 结构 | 规范行 |
|---|---|
| 默认图中的具体化节点绑定 `(r, t)` | `r ⟨urn:purrdf:rdfc:reifies⟩ t .` |
| 命名图 `g` 中的具体化节点绑定 `(r, t)` | `r ⟨urn:purrdf:rdfc:reifies⟩ t g .` |
| 默认图中的注解 `(r, p, o)` | `r p o ⟨urn:purrdf:rdfc:annotation⟩ .` |
| 命名图 `g` 中的注解 `(r, p, o)` | `r p o ⟨urn:purrdf:rdfc:annotation⟩ g .` |

`t` 是三元组项本身，以 RDF 1.2 形式书写（`<<( s p o )>>`）。三元组项可以嵌套；出现在任何位置的三元组项都会完整写出，不会被替代项取代。

由于叠加行与原生四元组互不重叠，规范形式中仍然可以观察到**具体化节点的数量和注解是否存在**。两个数据集如果仅具体化节点数量不同，或仅是否存在某条注解不同，也会生成不同的规范字节。这就是叠加层要提供的无损身份性质，也是 §5 拒绝规则要保护的性质。

### 3.1 幂等性：规范文档再次规范化后保持不变

规范输出是一份文档；文档和其他输入一样，可以再次作为输入。解析本 profile 的输出，再执行规范化，结果与解析前的字节**完全相同**：

```
canon(parse(canon(D))) == canon(D)
```

这一等式适用于规范形式能够重新解析的每个 `D`，也就是不携带命名图注解的每个 `D`。命名图注解是唯一无法由四元组承载的输出形状，详见下文。图作用域入口没有这种形状，因此其幂等性无须附加条件。

等式成立，是因为陈述层在往返过程中得以保留。重新解析输出时，§3 的叠加行会成为带有哨兵 IRI 的普通四元组，这正是展开步骤写出的内容。**形状与展开步骤的输出完全相同**的四元组会折叠回陈述层，而不是被拒绝：

| 重新解析的四元组 | 读回的结构 |
|---|---|
| `r ⟨urn:purrdf:rdfc:reifies⟩ t .` / `… g .`，其中 `r` 为 IRI 或空节点，`t` 为三元组项 | 具体化节点绑定 `(r, t)`（位于 `g` 中） |
| `r p o ⟨urn:purrdf:rdfc:annotation⟩ .`，其中 `r` 为 IRI 或空节点，`p` 为 IRI | 默认图注解 `(r, p, o)` |

其他位置都不改变。以哨兵为谓词但客体不是三元组项、哨兵出现在主体、客体或数据类型位置、注解哨兵出现在单独的图槽位以外，以及保留命名空间中的任何其他 IRI，都严格按 §5 拒绝。

**这为何不是 §5 的漏洞。** 拒绝规则要求内容不同的两个数据集绝不能共享规范字节。形状与展开输出完全相同的四元组，并非只是“像”一条具体化节点或注解行；它**就是**该行的书面形式。两者内容相同，赋予它们同一摘要是无损叠加层按规定工作，并不是碰撞。折叠在两个方向上都要求精确形状，因此对内容是单射：每个被折叠的四元组恰好表示一条陈述层行，每行恰好对应一种四元组形状，同时以两种形式携带同一行的数据集只携带它一次。折叠未消耗的位置仍会接受检查，因此不能把保留 IRI 藏在三元组项或注解谓词中来绕过可接纳性检查。保留命名空间的所有其他用法仍然被拒绝。

#### 有一种形状无法重新解析，这是输出形式本身的选择

**命名图注解**行在终止的 `.` 之前输出**五个**词元：主体、谓词、客体、注解哨兵和图项。它刻意不是有效的 N-Quads：原生四元组绝不会携带两个图词元，所以这种形状不可能与原生四元组碰撞，命名图注解也因此保持无损。没有四元组能承载这一行，因此也没有相应的折叠；上述身份等式适用于规范形式不含命名图注解的每个数据集。

**图作用域**入口（`purrdf_core::try_canonicalize_graph_view`）会擦除图槽位，所以输出始终是四元组形状，具有**无条件的幂等性**。需要无条件往返性质的使用方，应从图作用域规范化结果分配身份。

仅比较或计算摘要的使用方不受这一差别影响：输出始终是**规范字节串**，比较或散列都不需要先解析它。幂等性是使用方可以依赖的性质——分配身份时所用的字节能够重新导出同一身份——而不是使用方必须另行证明的义务。在 RDF 1.1 子集上，输出确实是有效的规范 N-Quads，因此可以由 W3C 套件把关。

### 3.2 叠加层中的空节点

空节点标签针对**包含叠加行的整个数据集**分配，而不是仅针对原生四元组分配。仅作为具体化节点、仅出现在三元组项内部，或仅作为注解图出现的空节点，也参与规范标签分配，其关联关系也计入 n 阶搜索。

这使叠加层在同构下保持成立：仅空节点重命名不同的两个数据集生成相同的规范结果，**即使被重命名的空节点只出现在引用三元组项内部**也是如此；空节点连接结构确实不同的数据集则生成不同结果。

### 3.3 平铺断言表示

每个可接纳的 RDF 1.2 陈述层，除了 §3 的输出形式之外，还有第二种书写形式：**平铺断言表示**。其标识由 `purrdf_core::CANON_PRESENTATION_FLAT_ASSERTION_ID` / `purrdf_core::CANON_PRESENTATION_FLAT_ASSERTION_VERSION` 导出，可通过 `purrdf_core::try_canonicalize_flat_view` 及其名称含 `_flat_` 的对应入口调用，包括 `try_canonicalize_flat_graph_view`、`check_admissible_flat_view` 和 `try_flat_digest_view`。§3 的输出形式也有独立名称，由 `purrdf_core::CANON_PRESENTATION_OVERLAY_ID` / `purrdf_core::CANON_PRESENTATION_OVERLAY_VERSION` 导出；名称**不含** `flat` 的入口（`try_canonicalize`、`try_canonicalize_view`、`try_canonicalize_graph_view` 等）固定使用这种叠加表示。

两种表示回答的是同一问题：“这个**可接纳的** RDF 1.2 陈述层生成哪些规范字节？”它们以不同书写形式表达**相同的可接纳内容**。表示选择与可接纳性相互独立：§4 的保留词汇和 §5 的拒绝规则不随调用方选择的表示而改变。不同之处仅在于：已接纳的具体化节点或注解行最终**如何输出**。

| 结构 | 平铺规范行 |
|---|---|
| 原生四元组 | 不变 |
| 默认图中的具体化节点绑定 `(r, t)` | `r rdf:reifies t .` |
| 命名图 `g` 中的具体化节点绑定 `(r, t)` | `r rdf:reifies t g .` |
| 默认图中的注解 `(r, p, o)` | `r p o .` |
| 命名图 `g` 中的注解 `(r, p, o)` | `r p o g .` |
| 以基础四元组书写的具体化节点绑定（§3.1 的折叠形状）`r ⟨urn:purrdf:rdfc:reifies⟩ t [g] .` | `r rdf:reifies t [g] .`——与原生具体化节点绑定 `(r, t)`（位于 `g` 中）展开为相同的行 |
| 以基础四元组书写的注解（§3.1 的折叠形状，哨兵位于该四元组自身的图槽位）`r p o ⟨urn:purrdf:rdfc:annotation⟩ .` | `r p o .`——与原生注解 `(r, p, o)` 展开为相同的行 |

这里的 `rdf:reifies` 是 RDF 1.2 词汇自身的具体化谓词（`http://www.w3.org/1999/02/22-rdf-syntax-ns#reifies`），不是 PurRDF 哨兵。平铺表示不会输出 `urn:purrdf:rdfc:` IRI，**任何保留命名空间 IRI 都不会参与平铺规范文档**。具体化节点绑定写入其声明所在的图；注解行写入自身的图槽位，与被注解的具体化节点所在的图无关（§3.2）。如果某行精确的 `(s, p, o, g)` 已作为原生基础四元组存在，则该行**只输出一次**：平铺表示按行去重。因此，同时将具体化节点绑定声明为具体化结构、又以其所表示的字面 `rdf:reifies` 四元组断言该绑定的数据集，与仅以其中一种方式断言它的数据集生成相同规范结果；同一行的两种书写形式绝不重复计数。

**表中的最后两行，是在当前表示下应用同一个 §3.1 折叠。** 它们涵盖携带精确折叠形状基础四元组的 §3 叠加规范文档或其他输入，尤其是经由**解析时不识别叠加层哨兵写法的加载器重新读入的叠加规范文档**。例如，普通 N-Quads/Turtle 解析器没有理由了解 `urn:purrdf:rdfc:`，因此会将这种四元组作为带有哨兵的普通基础四元组直接交出。识别和折叠它的是**规范化器自身的接纳检查**，不是加载器；两种表示都如此。§3.1 已说明，这种四元组恰好表示它所书写的具体化节点或注解行，并非恰好形似的不同结构。平铺表示将其按与原生存储行相同的方式展开，所以同一行的两种书写形式绝不会获得不同的平铺身份。上述按行去重也涵盖一行可能出现的全部三种形式：原生附表条目、以哨兵书写的基础四元组、使用真实谓词的基础四元组。它们无论怎样组合，都只输出一次。因此，“任何保留命名空间 IRI 都不会参与平铺规范文档”对**所有**可接纳输入都成立，包括自身携带哨兵写法的输入，而不只对从不触发折叠的输入成立。

**平铺表示是 RDF 1.2 陈述层的第二种规范化判定书写形式，绝不是 RDF 1.1 回退模式。** 选择它不会退回普通三元组语义：§3 规范化的每条陈述层行，都以其所断言的普通四元组出现在平铺文档中；§4/§5 的可接纳性、§6 的上限和 §3.2 的空节点标签分配规则仍然适用。不过，两种表示刻意给出不同的可区分性承诺。平铺表示标识的是**断言投影**：按行去重意味着，同时以具体化节点声明／注解声明和其自身的基础四元组断言一行，或通过折叠形状书写该行，所产生的字节与仅断言一次相同。所以，已声明的具体化节点绑定与普通 `rdf:reifies` 基础四元组，在平铺字节中不可区分；叠加表示则以哨兵行和普通谓词保持二者的区别。§3 无条件的无损身份性质是**叠加表示**的保证。必须始终观察陈述层结构（具体化节点数量、某行由哪种书写形式断言）的使用方应固定叠加表示；希望得到独立 RDFC-1.0 实现也能复现的 RDF 1.2 断言集合的使用方应固定平铺表示。

在两种表示下，`Canonicalized::labels` 都有同一限制：标签仅在**允许自同构置换的意义上**具有同构不变性。图存在非平凡自同构时，n 阶搜索在其他方面等价的候选之间如何打破平局，取决于枚举顺序。因此，同构但不完全相同的输入，可能为处于自同构关系的空节点分配不同、但结构等价的标签。而 `Canonicalized::nquads` 本身在两种表示下都完全保持同构不变性：两个同构视图生成逐字节相同的规范文档。

## 4. 保留词汇

IRI 命名空间

```
urn:purrdf:rdfc:
```

由**本 profile 保留**，并以 `purrdf_core::RESERVED_NAMESPACE` 导出。当前版本只展开为其中的两个名称：`urn:purrdf:rdfc:reifies` 和 `urn:purrdf:rdfc:annotation`；但保留范围是**整个命名空间**，不只是这两个名称。

保留规则约束该命名空间的每种用法，处理方式只有两类，不存在第三类：

| 保留命名空间的用法 | 处理方式 |
|---|---|
| `r ⟨urn:purrdf:rdfc:reifies⟩ t .` / `… g .`，其中 `r` 为 IRI 或空节点，`t` 为三元组项 | **折叠**：作为其表示的具体化节点绑定行接纳（§3.1） |
| `r p o ⟨urn:purrdf:rdfc:annotation⟩ .`，其中 `r` 为 IRI 或空节点，`p` 为 IRI | **折叠**：作为其表示的注解行接纳（§3.1） |
| 任何其他位置、任何深度的所有其他出现 | **拒绝**（§5） |

前两行就是 §3 展开**所生成**的两种精确形状。它们不是保留规则的例外，而是从使本 profile 自身输出可以接纳的方向读取同一条保留规则（§3.1、§5.1）。

刻意按整个命名空间声明保留范围，是因为按名称枚举会要求叠加层每增加一种行就重新审查。如果规则的可靠性依赖一项无人安排的审查，它就不能成为可靠规则。命名空间保留只需一句话，就能对照整个实现检查，而且不会排斥合法内容：PurRDF 不发布词汇，不分配本体术语，这个前缀下没有合法的应用词汇。

## 5. 拒绝规则（规范性）

> 如果数据集中的**任意项，在任意位置，是以 `urn:purrdf:rdfc:` 开头的 IRI**，该数据集就不可接纳，必须拒绝。**仅有的例外**是该 IRI 出现在 §3.1 的两种四元组形状之一中：在检查开始前，先将它们读回其所表示的陈述层行。不可接纳的数据集不得规范化，也不得从中分配任何摘要。

例外精确且穷尽：只有 §3.1 表中列出的、§3 展开所生成的两种形状，没有其他例外。以哨兵为谓词但客体不是三元组项、哨兵出现在主体、客体或数据类型位置、注解哨兵出现在单独图槽位以外，以及命名空间中的其他所有名称，都被拒绝。折叠作用于整个四元组，绝不孤立地作用于一个项。折叠未消耗的位置仍和其他位置一样接受检查：嵌套在折叠行的三元组项内部，或作为折叠注解谓词的保留 IRI，仍会导致拒绝。

“任意位置”包括主体、谓词、客体和图，任意深度的**三元组项内部**，以及**字面量的数据类型 IRI**。即使叠加层从不把哨兵展开到数据类型槽位，也仍检查该槽位。如果只因某个位置眼下无害就将其豁免，使用方就无法审查这一规则。

### 5.1 为什么要拒绝，以及拒绝为何必要

叠加层的无损性依赖于哨兵行与原生四元组互不重叠。IRI 语法本身不能保证这种不重叠：`urn:purrdf:rdfc:reifies` 是完全合法的 IRI，数据集也可能将它作为普通谓词断言。

要保护的性质十分明确：**内容不同的两个数据集绝不能共享规范字节。** 规范字节相同就会得到相同摘要；对只追加、内容寻址的权威存储而言，不同内容共享摘要会成为伪造身份的手段。控制输入字节的一方可以分配一条声明或一个视图，使其身份与结构不同的内容相同。作为真值层的底层设施，必须通过构造方式杜绝这种情况，而不能仅靠约定。

这一性质同时决定了 §4 表中的两种处理方式，二者并不矛盾：

* **相同内容应有同一摘要。** 形状与展开输出完全相同的四元组，不只是像一条具体化节点或注解行；它**就是**该行的书面形式。携带这种四元组和携带原生结构的两个数据集只在写法上不同，内容并未不同，所以将它们规范化为同一值正是无损叠加层按规定工作。由于折叠在两个方向上都要求精确形状，它对内容是单射，只能将一行与它自己的书面形式合并，不会与其他内容合并。§3.1 的幂等性正是建立在此基础上。
* **不同内容必须拒绝。** 该命名空间的其他出现都携带叠加层没有对应行的内容。接纳这些内容，会把未经解释的保留名称放入规范字节空间；未来的叠加行就可能与早期版本已经接纳并计算摘要的数据碰撞，甚至在这些字节进入存储多年后才发生。因此，§4 保留整个命名空间，§5 拒绝它的每种未折叠用法；profile 尚未分配的名称就不可能预先存放在使用方的存储里，等待未来发生冲突。

这里规定拒绝，而不是单射转义。两者都能堵住漏洞，但使用方需要审查的内容不同：拒绝把这一性质变成覆盖**全部输入的规则**，阅读一个判定函数即可检查；转义则要求证明**一个函数的性质**，包括转义是否单射、能否与嵌套组合，以及增加下一种叠加行后是否仍成立。较简单的证明义务更容易持续成立。

### 5.2 类型化结果

拒绝通过类型化值返回，绝不是要求调用方解析一段消息：

| Rust | 含义 |
|---|---|
| `CanonError::ReservedVocabulary(ReservedVocabulary)` | 违反 §5；携带 `iri` 和 `position` |
| `CanonError::BudgetExceeded(BudgetExceeded)` | 达到 §6 上限；携带 `blank_count` |

两者是不同变体，因为持有者需要采取的行动不同。预算耗尽的数据集良构，只是在当前上限内无法规范化；保留词汇数据集一旦被接纳，就会破坏身份不碰撞的保证。审查拒绝结果的使用方必须无须阅读英文消息就能区分两者。

`purrdf_core::check_admissible` 只应用 §5 的判定，因此存储可以在**接纳时**筛查，而不是等到分配身份的时刻才检查。

### 5.3 报告的违规是确定的

数据集多次违反 §5 时，报告的是按 `Subject < Predicate < Object < Graph` 顺序排列后最小的 `(position, iri)` 对；位置相同时，按 IRI 字节顺序打破平局。

拒绝本身原本就覆盖全部输入；现在**诊断**也具有完整的确定规则。如果报告首次遇到的违规，结果就会依赖陈述顺序，而陈述顺序又依赖驻留顺序；保存相同数据集的两个后端未必具有相同的驻留顺序。两个合规实现既必须拒绝相同数据集，也必须指出同一处违规。

### 5.4 优先顺序

§3.1 的折叠先于 §5 的检查，检查又先于任何散列。先折叠使两条覆盖全部输入的规则得以组合：检查开始时，被折叠的四元组已经不在四元组层中；折叠未消耗的一切，包括折叠行中剩余的每个槽位，都仍被检查。同时不可接纳且具有病态对称性的数据集，会按 §5 而不是 §6 拒绝：以其危险性的根本原因拒绝，且不消耗 §6 的预算来发现这个原因。

## 6. 搜索策略和执行证据（规范性）

每个执行搜索的入口都要求调用方提供 `CanonicalizationControl`，并明确选择
`SearchPolicy::Finite(u64)` 或 `SearchPolicy::Unlimited`。没有隐式有限上限，也没有
默认策略。历史常量 `RDFC_V2_CORPUS_POLICY` 仅供显式选择有限值使用，包括核对未更改的版本 2
固定语料时的 `RDFC_V2_CORPUS_POLICY`。

RDFC 计费规则版本 1 对每次进入 n-degree 帧和每次排列尝试各计一次，包括随后剪枝的排列。
接纳事件之前检查调用方的停止信号。有限上限拒绝下一个事件时不增加计费；无限策略去掉逻辑
上限，但停止信号和精确计数器的表示能力仍然有效。计数溢出返回类型化拒绝，不回绕或饱和。

每次规范化运行使用新的独立上限。复合操作保留每次运行的有序回执，没有累计搜索上限。
缓存命中不执行规范化，因此不新增运行；结构比较的提前退出记录零搜索工作和实际输出阶段。
调用方拥有控制器及其证据，也可以选择丢弃证据。操作边界只截取属于本次操作的回执范围。

`SearchReceipt` 记录实际算法和 profile 版本、标签哈希、表示、精确选择范围、输出操作及摘要
算法、有效策略、计费规则版本、已接纳事件计数、最终阶段、是否完成以及观察到的控制拒绝。
已计费事件可能随后被中断，不能声称已经完成。布尔停止接口不能推断取消与截止时间的区别。
源检查点故障仍优先于内部搜索或停止拒绝，同时保留已经观察到的工作。

`CanonError::BudgetExceeded` 携带实际有限上限、已计费工作和输入空白节点数。它只说明本次
运行到达调用方所选上限，不把图判定为恶意或无法规范化。拒绝或停止的运行不发布部分身份。
成功规范字节和内容摘要不包含策略或工作计数；执行配置属于独立证据。无限搜索不声称实现了
整个操作的物理内存准入：成功结果、准备、搜索、输出和回执存储的准入仍是独立工作。

### 6.1 所有入口均返回类型化拒绝

| 入口 | 拒绝时的行为 |
|---|---|
| `try_canonicalize` / `try_canonicalize_with` | 返回 `Err(CanonError)` |
| `try_canonicalize_view` / `try_canonicalize_graph_view` | 返回原始 `Err(CanonError)`，包括源读取失败 |
| `try_graph_digest_view` | 返回原始 `Err(CanonError)` |

任何从规范字节分配身份的使用方，都必须传播这些类型化拒绝。被拒绝的输入不会产生身份。原先供受信任调用方使用、会 panic 的入口已删除；调用方直接使用可失败入口。

## 7. 版本管理

任何可能改变使用方所分配身份的变更，都会递增 `CANON_PROFILE_VERSION`，包括：

* 改变给定数据集生成的规范字节；
* 改变 §4 的保留词汇；
* 改变 §5 的拒绝规则；
* 改变 §6 的上限。

**不会**改变输出的变更，例如重构、加快搜索或使诊断消息更清晰，不递增版本。这样版本号才值得固定；如果每次发布都改变版本，它就不能向使用方传达任何信息。

### 7.1 历史

| 版本 | 变更 |
|---|---|
| 1 | 初始 profile |
| 3 | §6 要求显式有限或无限搜索策略及实际执行证据，成功输出字节不变 |
| 2 | 收窄 §5：§3 展开所生成的两种四元组形状会折叠回陈述层，而不是被拒绝，使规范化对自身输出具有幂等性（§3.1） |

版本 2 **没有改变任何输出字节**：版本 1 接纳的每个输入，生成的规范字节都与版本 1 完全相同。改变的是拒绝规则，而拒绝也是使用方固定的契约的一部分。版本 1 拒绝的两类输入现在可以规范化，因此仅这一变化就已按 §7 第三项要求递增版本。

## 8. 规范性测试向量语料

语料位于 `vectors/rdf12-canon/`，并且已经**冻结**：每个载荷字节都由每次构建检查的 SHA-256 清单覆盖（`scripts/check-corpus-frozen.py`），所以静默修改期望结果会导致失败，而不是让检查通过。

它涵盖契约的两面：必须规范化为精确字节的黄金样本，以及必须返回精确错误变体判别值的投毒输入，包括 §5.3 指定的位置。两个样本从可接纳一侧检验 §3.1 的边界：每个样本将一种可折叠形状书写为普通四元组，并固定其规范化后的陈述层行。这样，折叠是被实际检验的性质，而非仅有声明，不能静默扩大或收窄。样本目录和文件格式见 `vectors/rdf12-canon/README.md`。

该语料有自己的内容寻址身份，由 `purrdf_core::CANON_CORPUS_DIGEST` 导出，并由测试框架断言。使用方可以固定 **(profile id, profile version, corpus digest)**，并对实际链接的产物验证这三个值。

## 9. 使用方固定哪些值

完整固定由四个坐标 `(profile, version, presentation, hash)`，再加上语料摘要和发布版本组成；后两者使使用方能够将四个坐标与实际链接的产物核对：

| 字段 | 来源 |
|---|---|
| profile 标识符 | `purrdf_core::CANON_PROFILE_ID` → `purrdf-rdfc12` |
| profile 版本 | `purrdf_core::CANON_PROFILE_VERSION` → `2` |
| 表示 | `purrdf_core::CANON_PRESENTATION_OVERLAY_ID`（→ `overlay`，版本 `purrdf_core::CANON_PRESENTATION_OVERLAY_VERSION` → `1`）或 `purrdf_core::CANON_PRESENTATION_FLAT_ASSERTION_ID`（→ `flat-assertion`，版本 `purrdf_core::CANON_PRESENTATION_FLAT_ASSERTION_VERSION` → `1`）（§3.3） |
| 散列算法 | `CanonHash::Sha256` 或 `CanonHash::Sha384`（§2） |
| 语料摘要 | `purrdf_core::CANON_CORPUS_DIGEST`（§8） |
| 发布版本 | 读取上述值时所依据的带标签发布版本 |

对实际链接的构建运行 §8 语料，会把这一组固定值变成验证凭据：它表明该构建生成 profile 规定的字节，并拒绝 profile 禁止的输入。

表示坐标不仅能从调用入口推知，也能从生成的结果中读回：每个 `purrdf_core::Canonicalized` 都携带 `presentation` 字段，精确指出两种表示中的哪一种生成了其 `nquads`。持有 `Canonicalized` 值的使用方因此可以直接对照该字段验证所固定的表示坐标，无须记住或从调用点重新推导。

执行配置还需固定每次运行的搜索策略和计费规则版本，并从控制器回执读取实际工作。
相同有限值具有相同策略身份，无论该数值来自哪个便利常量。输出 BLAKE3 摘要与 RDFC 标签
哈希分别记录，两者承担不同工作。固定版本 2 语料仍使用显式有限历史值，载荷及摘要不改写。
