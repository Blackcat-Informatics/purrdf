# PurRDF 嵌入向量 kNN：确定性、防护与搜索成本

`purrdf-core` 中的 PURREMB 层存储可由 RDF 1.2 寻址的向量、已声明的 `DistanceMetric`，以及把第三方索引载荷绑定到其构建所依据的确切矩阵的防篡改防护。该层刻意不排序：排序是查询操作，而 PURREMB 是工件格式。`purrdf-sparql-eval` 的 `knn` 模块通过属性函数扩展接口提供这一查询操作。

本文记录四项并非显而易见的决策及其理由。它是一份设计记录，不是教程；接口参考请见模块自身的 rustdoc。

## 1. 使用 binary64 而非定点数；这并非较弱的选择

PurRDF 的另一种排序检索接口以精确整数运算计算全部分数，在 crate 根部禁止浮点数。原因有其特定范围，不能直接套用到这里：BM25 需要自然对数，而 IEEE-754 **不要求** `ln` 正确舍入。不同 libm 可以产生不同的最低有效位，也确实如此；同一个分数在 x86-64 与 `wasm32-unknown-unknown` 上可能成为两个相邻的 double，足以交换近乎并列的两篇文档，使同一引擎返回不同的行序。

kNN 内核完全不需要超越函数。欧氏距离平方只涉及减法、乘法与加法；余弦距离另外需要除法与平方根。**IEEE-754 对这五项运算都要求正确舍入**：对于给定操作数，每个符合规范的目标架构只能有一个结果。在这里改用定点数无法获得更强保证；它只会引入 PURREMB 格式本身没有的量化步骤，造成额外成本并偏离工件算术。

格式规范也要求这一选择。`docs/PURREMB.md` 对工件折叠运算作出规范性规定：全部中间运算使用 IEEE-754 binary64、最近且遇半取偶的舍入、按书写顺序执行，不融合乘加。L2 范数属于这些折叠（§13.2），所以 kNN 内核不会另算一份范数：`Resolved::<Exact>::norm`（通过 `knn` 重新导出）调用 `purrdf_core` 的规范性 `norm_fold`，这是工作区中该顺序的唯一实现；工件写出器的规范化也使用它。距离求和则不同：PURREMB §7.4 允许内核优化求值，只要保留度量与行号并列规则。因此其运算顺序属于此 crate 的契约，而非格式契约，并同样受到固定：每个点积与欧氏距离平方求和都使用 `purrdf_core::distance::Exact`。

浮点内核因此只有两种残余的分歧路径；两者都通过结构约束关闭，而非寄望于碰巧一致：

| 风险 | 分歧原因 | 关闭方式 |
| --- | --- | --- |
| **重新结合** | 浮点加法不满足结合律，总和取决于折叠顺序 | 顺序属于算术定义（`Exact`，标识 `binary64-lane16-tree-v1`）：十六条 binary64 通道；通道 `l` 按 `c` 升序累加完整十六元素块中下标为 `16·c + l` 的项；然后依次执行 `(l, l+8)`、`(l, l+4)`、`(l, l+2)`、`(0, 1)` 成对树形合并；最后按下标升序逐一加入余项。累加器绝不拆给不同 rayon 工作线程。每个目标架构和每条分派路径都执行同一顺序。 |
| **融合乘加** | `a * b + c` 若作为一次 FMA 执行只舍入一次，书写形式则舍入两次 | 每个乘积先绑定到有名称的局部变量，再加入总和；Rust 不会隐式融合，精确路径均不启用 `fma`，PURREMB 也禁止融合。 |

十六条独立通道的固定顺序既允许向量化，也不允许编译器重排：通道是十六条分离的加法链，LLVM 可将其打包到目标架构支持的向量宽度（x86-64 上的 SSE2、AVX2、AVX-512F；aarch64 上的 NEON；wasm `+simd128` 下的 `f64x2`）。在 `x86_64` 上，每次搜索只分派一次，在同一函数体的可移植编译版本、AVX2 版本和 AVX-512F 版本之间选择。`purrdf_core` 的测试把宿主可执行的每条路径与通道、树和尾部的标量参考模型逐位比较。短于一个完整块的向量与旧的升序顺序循环得到相同结果，因为十六条零通道的树仍为零。

顺序不仅写在文档里，还有断言。测试选择确实会因顺序不同而产生不同结果的向量：通道 0、1、8 上的 `1e16`、`1`、`-1e16`，其余为全 1；通道树得到 `1`，两种顺序循环都得到 `0`。测试固定内核应产生的那一种结果。只检查「同一输入两次输出相同」无法发现运算顺序不固定的内核。

此算术还假设 IEEE-754 的默认浮点环境。如果线程启用了 flush-to-zero、denormals-are-zero 或不同的舍入方向，同样的代码会产生不同位。解析算术路径时，会在每个目标架构上以十三项结果已知的 binary64 运算检查浮点环境；在可读取控制寄存器的目标上先读取寄存器（x86-64 的 MXCSR、aarch64 的 FPCR、由 x87 计算 binary64 时的 x87 控制字）。不符合环境的线程在空间构建时和每次搜索时都以 `EvalError::FloatEnvironment` 拒绝，因为一次调用可能在另一线程运行。检查返回的句柄不能离开创建它的线程：环境是线程局部状态，因此 `Resolved<A>` 既非 `Send` 也非 `Sync`。引擎跨线程共享的关系只存放与线程无关的 `Selected<A>` 路径，每次扫描与成员查找都在执行线程上解析该路径。

逐对距离入口遵守同一规则：`Kernel::distance` 和 `Kernel::distance_bounded` 接收由 `Exact::resolve` 返回的 `Resolved<Exact>` 句柄（两者均由 `knn` 重新导出）；重新结合版本接收 `Resolved<Reassociated>`。因此，启用了异常浮点环境的线程不可能未经显式拒绝就计算逐对距离。调用方在每个调用点解析一次，将 `Copy` 句柄传给所评分的各对。逐对计算中用于相除的范数也遵守该限制：范数只作为精确句柄的方法 `Resolved::<Exact>::norm` 存在，因为折叠只有一个书写顺序，没有重新结合形式；重新结合的使用者可经 `Resolved::exact` 取得它。在冲刷次正规数的线程上，次正规范数会折叠成 `+0`，因此任何范数计算都必须先经过检查。`EmbeddingSpace::from_artifact` 把先解析的句柄传给 PURREMB 的确定性 L2 行读取器（`EffectiveMatrixView::f32_row`／`f64_row`）以及随后计算的范数。

算术选择不改变度量。`DistanceMetric` 命名*测量内容*，向量族契约摘要只由它计算；算术身份记录在旁边的 HNSW 映像头和 profile 中，也记录在下述两种关系的排序声明中。

另一种算术以自己的名称与精确路径并存：`Kernel::distance_reassociated` 和 `Kernel::distance_bounded_reassociated` 用 `purrdf_core::distance::Reassociated`（标识 `binary64-reassociated-v1`）计算相同度量。每个 64 元素块内部用 `algebraic_*` 运算折叠总和，编译器因此可以重新结合并将乘加融合；块总和按升序合并，所以有界版本的检查点是完整结果的真实前缀。最低几位可能随目标架构、构建和分派路径变化：x86-64 运行时选择 SSE2、AVX2+FMA 或 AVX-512F；aarch64 用 NEON；wasm 按构建选用 `simd128` 或标量。解析后句柄的证据明确描述这一点。每条路径的函数体只在行外编译一次，因此同一路径的每个调用方对同一对输入得到相同的位。精确入口绝不执行这条路径，它也不会代替精确路径。聚焦测试 `knn_wasm_reassociated` 仅在 `+simd128` 构建上执行 simd128 内核，并将结果限制在相对于精确结果的求和误差界内；其独立路径选择断言在两种 wasm32 构建上都运行。

### 关系以算术类型为参数

`EmbeddingKnnRelation<A: Arithmetic = Exact>` 将法则作为类型参数。`EmbeddingKnnRelation::new(space)` 构造保持既有行为的精确关系；构造函数本身不返回错误，搜索仍会验证环境：每次搜索解析浮点环境与分派路径，每条精确路径都返回相同位。`EmbeddingKnnRelation::new_reassociated(space)` 返回 `Result<EmbeddingKnnRelation<Reassociated>, EvalError>`：它只解析一次重新结合分派路径，对冲刷次正规数的环境以 `EvalError::FloatEnvironment` 拒绝，并把路径保存为 `Selected<Reassociated>`（`EmbeddingKnnRelation::selected`）。此后每次搜索及成员查找，都在调用线程上解析该路径、检查该线程环境，并运行 `A` 的批量内核。两种关系执行同样的扫描，评分每一行，因此重新结合关系不会漏掉精确关系会命名的行；它可能改变两条近乎并列的行的顺序。

差异被明确声明，而非隐藏。`ranked_declaration` 在 `RankedDeclaration::arithmetic` 中将法则命名为 `RankArithmetic::FloatDistance`（`binary64-lane16-tree-v1` 或 `binary64-reassociated-v1`），`canonical_description` 将其纳入内容指纹；注册表指纹和从中得出的每个计划 ID 都绑定算术。因此同一空间上的精确检索结果生成器与重新结合检索结果生成器是两个计划。重新结合关系还经由 `composed_order_fidelity`（HNSW 关系也使用的唯一组合）把宿主的顺序保真性与 `OrderFidelity::Perturbed` 组合，原样携带解析路径的算术证据。融合答案在 `FusionTrailer::fidelities` 中携带该证据，报告相应层没有有限分数上界。完整性轴仍按宿主声明。

测试将两条路径各自绑定到观测。`exact_scan_matches_kernel_bits` 和 `reassociated_scan_matches_reassociated_kernel_bits` 把关系输出的每个距离与同一路径上的 `Kernel::distance`、`Kernel::distance_reassociated` 逐位比较。夹具中精心构造的一对向量在所有未融合顺序下恰好抵消，只在那些路径留下零；因此融合路径上的重新结合关系会与精确关系产生可见差异。`reassociated_relation_declares_perturbed_order` 及其对照 `exact_relation_names_exact_arithmetic` 固定声明；`purrdf-retrieval` 中的 `fusion_trailer_names_reassociated_kernel` 在同一空间融合两个检索结果生成器，以精确检索结果生成器为对照行。

### 原生算术固定值与聚焦 WASM 内核

算术契约跨目标架构适用。下述数值固定值在原生环境实际执行；`make wasm` 只检查发布 crate 能构建到 wasm32。编译成功本身不能证明第二种目标架构上的数值一致。

`crates/purrdf/tests/knn_wasm_determinism.rs` 在原生 Rust 中固定精确数值预期。真实 SPARQL 查询读取分量无法由 双精度 精确表示的 PURREMB 工件，按顺序断言五个字面量 `xsd:double` 的词法形式。六维夹具触及顺序尾部；七十维夹具在余弦距离与欧氏距离平方下，覆盖全部十六通道、64 元素边界检查点及六元素尾部。`make wasm-test` 则选择实际 WASM 路径准入及 `knn_wasm_reassociated` 中的直接 simd128 内核比较；一般算术与查询语义的测试仍在原生环境运行。

### 保证的边界

余弦自距离**不保证严格为零**。`dot(v, v)` 与 `|v| · |v|` 对同一个实数采用不同的 binary64 舍入。两者之商可能略微偏离 `1`，因此 `1 - quotient` 保留一个可能为负的小残差；残差的尺度来自商在一附近的舍入，而不是 `0` 处的 ULP。这是 PURREMB 所定义运算的性质，不是内核缺陷。测试断言接口真正需要的性质——该向量严格排在其他方向之前——而不要求并不存在的零。

距离作为 `xsd:double` 输出，其规范词法形式可往返还原精确位。若改用经舍入的 `xsd:decimal`，两个相邻 double 可能呈现为同一个值，正好掩盖本节讨论的分歧。

## 2. 按内容处理并列，而且不增加排序成本

名次顺序是 `(distance ASC, row ASC)`。行号互不相同，因此没有两个候选比较相等：这是**严格全序**。有界 top-`k` 堆与完整排序因而在构造上而非偶然得到相同结果；`sort_unstable` 也成为规范性选择，而非仅仅更快。

并列规则具有语义，因为 PURREMB 目标集合在构建时按 `TargetId` **排序并去重**，而 `TargetId` 是目标规范身份的域分隔摘要。所以行号升序就是规范内容顺序升序。两个宿主即使按相反插入顺序基于相同目标构建工件，也会得到相同行号与答案。测试以正向和反向构建的两个工件直接断言，直到序列化 JSON 字节。

*距离*并列确实会发生：两个相同向量距任何对象都一样远，且都会返回。*名次*并列则不可能。

## 3. 防护限定工作量，不许可近似答案

PURREMB v1 存储派生索引载荷，却不解释它们。`IndexGuardView` 将不透明的第三方 ANN 载荷绑定到其构建所依据的确切 `(source, family, space, matrix, projection, prefix)` 元组，并声明自身的损失契约；它不是 PurRDF 能直接执行的算法。因此此接口不会假装执行该算法。

**搜索是精确的。** 每个候选行都会评分，返回的 `k` 个结果是实际最近的 `k` 个。没有候选剪枝。这使「在已声明度量下顺序正确」成为模块可测试的性质，而非调参结果；也使引擎的行数上限下推在此处合理：输出顺序*就是*名次顺序，所以对于每个 `n ≤ k`，前 `n` 行就是最近的 `n` 项。

精确性测试不仅使用其余测试套件常用的三点夹具，还在可能失去精确性的规模上检查：一个 192 点空间在五个不同的 `k` 值下，与测试中明确写出的暴力搜索判定依据（oracle）比较。同时断言两个方面——数量必须精确（把 `k-1` 个邻居报告为完整答案是此接口最可能隐藏的失败），每行输出距离也必须与判定依据的相应前缀一致。

`KnnGuard` 是由调用方提供、没有默认值的工作准入界限：

* `max_candidates`：单次调用最多允许扫描的空间大小。更大的空间在**构造时**被拒绝，不在查询时截断。截断远比拒绝危险：对空间的任意前缀计算 top-`k`，会得到看似正确的错误答案。
* `max_neighbours`：单次调用可请求的最大 `k`。更大的请求会以包含两个数值的错误拒绝，而不是被钳制。

两个上限均包含边界值，测试也双向覆盖：等于上限的值被接纳，超过一个单位的值被拒绝。只测试拒绝侧，无法与「全部拒绝」的错误实现区分。

`max_neighbours` 还有结构上的理由：`k` 是每次调用的参数，`PropertyFunction::rows_per_invocation` 无法看到它；若没有配置上限，唯一诚实的声明就是整个空间。规划器依据所声明的上界与中间单元上限为属性函数节点定价，就会拒绝实际上只输出三行的调用。在本仓库中，估算器过度拒绝属于真实缺陷类别；配置上限让声明足够紧，使其不再造成这种问题。测试断言适中的单元上限**允许**该关系。

防护除限制工作量之外还有一项用途：工件中凡是命名此目标集合和向量空间的派生索引防护，都会针对实际扫描的矩阵检查。如果防护命名此空间，却指向不同矩阵或投影，它便已过期或被替换；这是关于该空间不再成立的声明，须在构造时失败，不能无声同意。

## 4. 搜索成本，以及使其可计量的扩展接口变更

此前，求值器只能按两种量给宿主关系定价：被请求的次数（`property-function-invocation`）和返回的行数（`property-function-row`）。对于*检索结果生成器*关系，两者都不代表主要成本。搜索一百万个向量、返回最近五个的查询只计一次调用与五行：一百万次距离计算只花六单位 fuel，与扫描六行的表价格相同。于是调用方预算限制的是答案大小，而非执行成本；但governor恰恰应该限制后者。

计费计划 **v8** 加入 `property-function-work`，由 `PfCursor` 新增的默认方法供给：

```rust
fn take_work(&mut self) -> u64 { 0 }
```

该方法报告上次调用以来执行的内部工作量，并*取走*它，使连续读取把工作分段，避免重复计费。引擎在每次拉取后读取，包括终止拉取。因此无论游标在第一次 `next` 才懒执行搜索，还是在 `open` 时提前执行，总工作量相同，每个报告单位花费一个单位 fuel。

三个性质防止它成为规避预算或虚构成本的通道：

1. 数量被真正**花费**，而非仅记录；关系若夸大数量，会耗尽其调用方预算，激励方向正确。
2. 少报（以及默认的零）会使查询看起来比实际便宜，但其他上限仍原样生效：调用点、行点、中间单元峰值、答案上限及墙钟期限。它可能降低收据的精度，不能破坏其他上限的健全性。引擎无法观察宿主代码内部工作，无法做得更好。
3. 默认值为零，因此使用 v5 扩展接口编写的关系不会新增费用，按 v7 预算设置的查询在 v8 下仍能得到相同执行。重新生成的governor语料直接显示这一点：**每个固定花费数值保持不变**，仅在逐计费点分解中增加一行 `property-function-work 0`。

本接口的单位是**检查一个候选**，即计算空间中一行的距离。验收测试让两个不同大小空间的返回行数都为一：行点无法区分它们，工作点分别报告 3 和 8。

搜索在首次 `next` 时才懒执行，而不在 `open` 时执行，确保「不需要任何行」与「没有做任何工作」表达同一事实。若调用的上限已经用尽，就不会拉取，也不会搜索或计费。

## 5. 拒绝与空答案

二者有明确区分，每种情况两侧都有测试。

**拒绝**（查询终止；若贡献零行，就无法与诚实的空答案区分）：

| 条件 | 原因 |
| --- | --- |
| 种子或 `k` 未绑定 | 此关系为*某个*种子检索邻居，不能枚举种子，也不能发明返回数量 |
| `k` 不是整数字面量，或为负数 | 这种请求没有定义 |
| `k` 超过 `max_neighbours` | 返回较少项会把不完整答案报告为完整 |
| 空间超过 `max_candidates` | 构造时拒绝；见 §3 |
| 向量族声明扩展度量 | 参数是不透明字节，引擎无法计算；据此排序等于依照进程中无人知道的规则排序 |
| 使用余弦距离时某个已存向量的范数为零 | PURREMB 规定零范数操作数的结果未定义，必须硬错误，不能编造分数 |
| 目标集合的一行没有调用方提供的项 | 未命名行会参加搜索却无法报告，top-`k` 将无声变成某个子集的 top-`k` |
| 距离超出有限 binary64 范围 | 无穷值仍能排序，且排在最后；这会给从溢出数值计算出的答案赋予虚假的可信名次 |

**空答案**（数据无法回答的合乎格式的查询）：

| 条件 | 原因 |
| --- | --- |
| 种子不在空间中 | 与不匹配的三元组模式一样。若拒绝，任何把部分无嵌入向量的项作为种子遍历的查询都会整体中止；这正是此关系的普通使用方式 |
| `k = 0` | 请求零个邻居，返回零行，做零工作；钳制或拒绝规则很容易误处理这一边界 |

零范数拒绝有显式对照：同一工件在另外两个不按范数相除的度量下可以正常打开，说明拒绝确实来自*度量*，而非向量本身。`k` 的数据类型检查也有对照：`xsd:int`、`xsd:long`、`xsd:unsignedByte` 和 `xsd:nonNegativeInteger` 都被接纳；若只允许字面上的 `xsd:integer`，会拒绝合法查询，却不影响其他测试通过。
