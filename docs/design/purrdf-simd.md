# PurRDF SIMD: the stable ceiling, arithmetic contracts and the hot-path audit

This document is the audit of every hot path in the PurRDF workspace against one
question: what does the compiler actually emit for it, on each target a PurRDF
build runs on? It records the rules a vectorized kernel must satisfy to ship, and
the arithmetic contracts that decide whether a float kernel may be reordered. The
evidence is always the emitted assembly, never the source.

Explicit vector kernels serve scanning, hashing, compression and numeric paths.
LLVM also vectorizes ordinary scalar Rust. Section 4 measures the emitted work;
latency and throughput require separate workload measurements.

The measured columns of §4.1 are generated by `scripts/check-simd-asm.py
--write-doc`, and `make simd-asm` fails when the committed document and a fresh
measurement disagree. Every count in this document is therefore the count of the
tree the document ships in.

---

## 1. The stable ceiling

PurRDF builds on a nightly toolchain but uses no nightly feature, and its MSRV is a
stable release (§5). Everything below is therefore restricted to what
stable Rust offers. That is project law, not a preference.

### 1.1 Capability table

| Capability | Stable status | What PurRDF does with it |
|---|---|---|
| `#![feature(...)]` of any kind | not stable | never used; `git grep '#!\[feature'` over `crates/` and `bindings/` is empty |
| `std::simd` (portable SIMD) | not stable | not used |
| `core::arch` intrinsics | stable, per target | allowed only where the asm proves a reformulation cannot reach the same code (§2.3, rule c) |
| `#[target_feature(enable = "...")]` on a function | stable | allowed under the same rule. Such a function does not coerce to a plain `fn` pointer, so dispatch goes through ordinary wrapper functions, never through a table of `#[target_feature]` pointers |
| `is_x86_feature_detected!` / `is_aarch64_feature_detected!` | stable (std) | run-time dispatch, resolved once per scan, relation or index, never once per pair |
| wasm `simd128` (`-C target-feature=+simd128`) | stable, compile-time only | the `+simd128` wasm artifact; there is no run-time detection on wasm |
| wasm `relaxed-simd` | stable | **disqualified** for ranked and identity kernels: its results are allowed to differ between engines, so a ranking or a digest computed in one browser would not be the one computed in another. Every ranked or identity site is measured with `forbid_relaxed` |
| `f64::algebraic_add` / `algebraic_mul` / `algebraic_sub` (`float_algebraic`) | stable from Rust 1.98 | the only stable grant of reassociation and contraction for a single operation; the reassociated arithmetic of §3 is built on it, and it is why the MSRV moves (§5) |
| `-C target-cpu` / `-C target-feature` | a build flag | a consumer's choice. A library cannot make it for its consumers, so there is no workspace-wide `target-cpu` in cargo configuration; the audit measures the baseline and two raised levels per ISA instead |

### 1.2 Reproduction

The measurement is one gate. It emits assembly for seven configurations and counts
the vector work in every audited symbol:

| Configuration | Target | Codegen flag |
|---|---|---|
| `x86_64` | `x86_64-unknown-linux-gnu` | `-C target-cpu=x86-64` (SSE2) |
| `x86_64-v3` | `x86_64-unknown-linux-gnu` | `-C target-cpu=x86-64-v3` (AVX2, FMA) |
| `x86_64-v4` | `x86_64-unknown-linux-gnu` | `-C target-cpu=x86-64-v4` (AVX-512) |
| `aarch64` | `aarch64-unknown-linux-gnu` | none (NEON) |
| `aarch64-neoverse-v1` | `aarch64-unknown-linux-gnu` | `-C target-cpu=neoverse-v1` (SVE) |
| `wasm32` | `wasm32-unknown-unknown` | none (no SIMD proposal) |
| `wasm32-simd128` | `wasm32-unknown-unknown` | `-C target-feature=+simd128` |

```sh
make simd-asm                                      # measure, check the manifest and this document
python3 scripts/check-simd-asm.py --write-doc      # regenerate the measured columns of §4.1
python3 scripts/check-simd-asm.py --self-test      # every refusal and its valid neighbour, no build
python3 scripts/check-simd-asm.py --probe 'REGEX' [--config NAME] [--crate NAME] [--dump]
```

The gate retains separate Cargo build contexts for each compiler, target configuration
and build graph. Every run asks Cargo to check freshness, verifies the assembly's
recorded compiler arguments and content digest, and reevaluates the current manifest.
Parsed functions can be reused; a previous pass verdict cannot. Missing or changed
assembly evidence fails explicitly and can be reconstructed with `--fresh`.

Two configurations run concurrently by default, sharing the effective Cargo job
budget. `--jobs` changes the number of configuration workers, not the total compiler
budget. The Stage Cargo shim recognizes the gate's explicit assembly context, retains
its lease through analysis, and keeps these artifacts out of normal release outputs.
Other Cargo invocations retain their usual directory, cache and publication policies.

```sh
make simd-asm SIMD_ASM_ARGS="--config x86_64 --jobs 1"  # checked partial shard
make simd-asm SIMD_ASM_ARGS="--fresh"                  # new Cargo/reader contexts
make simd-asm SIMD_ASM_ARGS="--report target/asm-report.json"
```

`--fresh` leaves the external compiler cache enabled. The per-configuration timing
summary separates Cargo execution, lease waiting and assembly analysis, and reports
compiler invocations, Cargo-fresh artifacts and parsed/reused units. Cargo's detailed
timings and stdout/stderr logs remain in the private context, including on failure.

CI runs seven independent configuration jobs. The required `simd-asm` aggregate accepts
exactly one successful report for every configuration, with matching source, manifest
and compiler identities, then checks complete document parity. A partial shard cannot
write the audit document or stand in for the complete matrix.

Each configuration is a release build with LTO off and one codegen unit, with
`--emit=asm` added through `CARGO_TARGET_<TRIPLE>_RUSTFLAGS`:

```sh
cargo build --release --locked --lib --target <triple> -p <audited packages> \
  --config 'profile.release.lto=false' --config 'profile.release.codegen-units=1'
```

That emits a `.s` for every crate in the graph, dependencies included, so a
dependency's own kernels (sha2's, `regex-automata`'s) are measured in that
dependency's symbols. The asm is per crate and before LTO. LTO can inline,
specialize and eliminate code, so these counts establish available kernels;
they do not prove the final application's instruction mix or throughput. `purrdf-wasm` is
also a `cdylib`, and linking one needs a linker for the target, which the asm does
not; it is built alone as an rlib (`cargo rustc --crate-type rlib`) against the same
dependency units.

The manifest, `scripts/simd-asm-manifest.toml`, names for each site the symbol it is
measured in on each configuration, a floor of vector operations, the mnemonics that
prove the shape, and an FMA bound. A private or inlined function is measured in the
out-of-line symbol that inlines it, and the manifest names that symbol. A missing
target standard library or tool is a failure, locally and in CI; nothing skips.

## 2. The three regimes and the formulation rule

### 2.1 The regimes

Every float fold in this workspace is in one of three regimes.

1. **Sequential exact.** `s += x * y` in index order. IEEE `+` is not associative,
   and LLVM is not permitted to reassociate it, so the accumulation compiles to one
   scalar add chain on every target. LLVM may still vectorize the parts that carry
   no order: the kNN dot fold was regime 1 before it moved to regime 3, and on
   `aarch64` with f32 operands its widening (`fcvtl`, `fcvtl2`) and products
   (`fmul v.2d`) were packed while the sum stayed a chain of scalar `fadd d`
   instructions. Same bits on every target; no vector accumulation anywhere. The
   PURREMB norm (`core.purremb-norm`, `knn.norm`) stays in this regime because its
   order is normative.
2. **Reassociated.** The operation grants LLVM reassociation and contraction
   (`algebraic_*`). The accumulation vectorizes and may fuse into FMA. The bits
   depend on the target, the dispatch path and the build.
3. **Fixed-lane exact.** The fold is *defined* as `LANES` independent accumulators
   followed by a fixed pairwise tree and a sequential tail. That order is the
   contract, so it is the same order on every target, it needs no grant from the
   compiler, and it vectorizes. Same bits on every target.

### 2.2 The formulation is load-bearing

Regime 3 is only regime 3 if LLVM can see the lanes. A fold written
`acc[l] += a[i * LANES + l] * b[i * LANES + l]` compiles to zero vector operations:
the index arithmetic hides the independence of the lanes. The same fold written over
`a.chunks_exact(LANES).zip(b.chunks_exact(LANES))` with an `array::from_fn`
accumulator update compiles to a packed loop. So a claim that a kernel vectorizes is
a claim about emitted asm, and every site in §4 is measured.

### 2.3 The preference order

1. **(a) Reformulate the source** so LLVM vectorizes it: `chunks_exact`,
   `array::from_fn` accumulators, bounds checks hoisted out of the loop, no dispatch
   in the inner loop. It stays portable and free of `unsafe`.
2. **(b) Offer a separate fast-variant function** under its own contract (§3).
3. **(c) Gate internally** with `core::arch` or `#[target_feature]`, only where the
   asm proves (a) cannot reach the code, and only with bit-equality under the
   function's contract.

### 2.4 What asm can and cannot prove

- `max_fma = 0` is necessary for an exact kernel and is enforced on every exact
  site. It is **not sufficient**: a fold with no FMA can still add in the wrong
  order. Summation order is proven only by the scalar reference-model tests, which
  emulate the lane, tree and tail order in plain nested loops and compare bits.
- Rust never sets LLVM's `contract` fast-math flag on a plain `*` or `+`. So
  `#[target_feature(enable = "fma")]` on an exact kernel cannot fuse it; FMA appears
  only where an `algebraic_*` operation or an explicit `mul_add` asks for it.
- A count is the whole symbol a site is measured in. When a site is inlined into a
  larger function, that function's other vector work (hashbrown's SSE2 or NEON
  group probes, straight-line struct moves, a UTF-8 width computation) lands in the
  same count. The *proof mnemonics* are what tie a count to the audited loop, which
  is why every `covered` row requires them and no `leave` or `rewrite` row claims
  vector work from a bare count.
- Asm proves a kernel was *compiled*, never that it *ran*. Every kernel family
  with more than one path (BLAKE3, SHA-1, CRC-32, base16, DEFLATE, the CSV field
  scanner, the distance arithmetic) names its paths through
  `purrdf_hash::Backend`, and its tests run every available path against the
  portable one and the frozen vectors. `PURRDF_REQUIRE_SIMD_PATHS` turns
  "available" into a checked claim, read by the one check in
  `purrdf_hash::dispatch`: set to `1`, every path the host is expected to run
  (its architecture's baseline paths, and each path whose features Linux
  `/proc/cpuinfo` advertises) must be available, and the families that promise it
  also require it selected or executed; set to a list of `family:path` entries
  (`distance:avx512f,blake3:avx512,deflate:neon`), exactly those are required, so
  a job on a known or emulated processor proves what that processor ran. A
  misspelt family or path, or any other value, fails the run.

### 2.5 Rust and LLVM lessons from hashing and compression

Optimize the complete operation the caller performs: short identity creation,
incremental updates, bulk hashing, or gzip decoding. A faster compression round
can lose overall through buffer initialization, copies, dispatch or tree work.

| Technique | Concrete use | Evidence to require |
|---|---|---|
| Make dimensions and indices constant | Fixed arrays, `as_chunks`, const-generic stream capacities; SHA-3's 25 literal rho/pi lane expressions | Bounds checks and indexed schedule loads disappear; rotations use immediate counts |
| Expose independent work | BLAKE3 chunks in separate SIMD lanes; four scalar quarter-round chains for short x86 inputs | Compare scalar and vector paths at the same message sizes; wider registers alone do not establish a win |
| Bound expansion | Seven BLAKE3 rounds expanded; SHA-3 expanded two rounds per loop | Inspect spills and code size; compare against partial and full expansion |
| Keep dispatch outside repeated work | Select a stream backend once; enter a kernel for a batch | Count inner-loop calls and repeated feature checks, including after inlining |
| Use contiguous loads and transpose | BLAKE3 word lanes from contiguous message blocks; parent lanes from pairs of child CVs | No strided gather or scalar reconstruction hidden in the load path |
| Batch the reduction too | AVX-512 reduces up to 256 chunk CVs together | Parent lanes remain occupied across neighbouring chunk batches; measure the stack footprint |
| Preserve finalization state directly | A complete BLAKE3 subtree retains its final `Output` until more bytes arrive | Correct ROOT domain separation across empty updates, appends, snapshots, clones and reset |
| Write to the final destination | Gzip's slice and vector sinks share decoding; CRC is updated from accepted window bytes | Fewer copies and allocated bytes, with identical limits, trailers and error behavior |
| Pack typed metadata at the caller seam | Literal datatype, language presence and direction; blank-node scope and variant | Borrowed, stored, global and frozen lookup paths use one protocol; field boundaries and high id bits remain distinct |

**Scalar can win inside a block.** BLAKE3's four independent scalar quarter
rounds give an out-of-order x86 processor multiple dependency chains to schedule.
Putting those four rounds in a vector creates one instruction chain. Measurements
on the Ryzen AI Max+ 395 favored scalar ARX through one 1 KiB chunk, even with
AVX-512 available. Default x86 one-shot hashes and short stream finalizations use
that path; explicit backend forcing retains each SIMD single-block kernel for
tests and comparison. Independent *chunks* still benefit from SIMD. Match batch width to the live
input too: the AVX-512VL four-chunk path avoids a padded 16 KiB batch for
messages through 4 KiB, while full batches keep sixteen lanes. This is a
workload decision, not a claim that scalar always wins on other processors.

**Specialization must survive code generation.** SHA-3's rho/pi indices and
rotation counts are mathematical constants. A compact indexed loop left variable
rotations in baseline x86 code. Expanding the lane expressions exposes immediate
rotations. Two round expansions improved scheduling; expanding all 24 rounds
performed worse. The permutation still executes exactly 24 rounds. Use narrow
macros or const generics when they reliably expose the required shape; indiscriminate
`inline(always)` and unrolling can enlarge code and increase register pressure.

**Inspect register allocation, not just instruction count.** Native x86 tuning
changed scalar BLAKE3 rotations from two-operand `ROR` to three-operand BMI2
`RORX`; the resulting schedule spilled more state and nearly doubled the measured
1 KiB latency. A narrowly scoped inline assembly helper keeps the rotation's
input and output in one register. It declares flag clobbers and `pure, nomem,
nostack`; it requires no optional ISA. Paired baseline and native builds validate
the choice, native arithmetic tests validate the helper, and frozen full-hash
answers validate its integration. Miri takes the ordinary Rust rotation path,
so its result does not validate that assembly.

**Keep late values off the shuffle path.** A BLAKE3 quarter round produces
`b` last. The four-chunk AVX-512 kernel keeps `b` stationary at diagonal
boundaries and permutes `a`, `c` and `d`, allowing those shuffles to overlap
the final `b` operations. Its message schedule is expressed in that register
basis. Invariant counter/length vectors are formed outside the block loop.
A separate complete-subtree entry prevents partial-input padding from imposing
its stack frame on full batches. Check both the critical dependency chain and
the caller's prologue; a correct SIMD body can still inherit expensive setup.

**Inline where assembly demonstrates a cost.** The AES table hasher's byte
update was outlined at a monomorphic terminal-IRI call site, forcing the state
through stack memory. A scoped `inline(always)` on that update keeps the
accumulator in registers. This is a measured call-site intervention, not a
rule to inline every hot function. The ordinary string path adds another boundary:
`Hash::hash` reaches the `Hasher::write` wrapper through the standard library's
string implementation. Inspect that complete caller too. An inline attribute on
the inner update alone left calls and accumulator spills in string-keyed maps.
Keep the long-slice compression body out of line so the short string wrapper
stays small enough to inline; preserve the rounds and field separators.
Packed short RDF fields likewise use
fixed-size loads and shifts after variable-length copies proved slower.

**Tree arithmetic determines the streaming API.** A BLAKE3 subtree starts at an
aligned chunk counter and contains a power-of-two number of chunks. Binary carries
determine how its CV joins the pending stack. A complete subtree at the end of an
update can retain its final compression inputs instead of copying its message
bytes into the stream buffer. Finalization sets ROOT; a later nonempty update
converts that pending output to a CV before appending. This preserves the hash
law while allowing large updates to use the same batches as one-shot hashing.
Tiny writes still collect in a 16 KiB buffer; short framed identities use the
1 KiB `RecordHasher`. The caller owns any parallel scheduler through `Join`.

**An allocation budget is not an allocation floor.** Track allocator calls,
requested bytes, retained bytes and peak working bytes separately. Hash creation,
updates, finalization and reset are tested for zero heap allocations. Gzip retains
its history window and reusable Huffman tables; decoding a subsequent warmed
member into reserved output is also tested for zero allocations. Its convenience
decoder allocates its result and working storage. Removing a 256 KiB staging
buffer avoids both an allocation and an output copy; avoiding a three-times-input
capacity estimate also reduces retained memory on incompressible input. Do not
move large buffers to the stack merely to reduce the allocation counter: stack
initialization, copies and cache footprint remain performance costs.

**Keep mathematical contracts exact.** Integer wrapping, BLAKE3 counters and tree
flags, SHA-3 round constants, CRC polynomial reduction and Huffman prefix lengths
are part of the function. Optimize their evaluation without changing them. Hash
quality tests are independent gates for table-hasher experiments: a cheaper mixer
that fails avalanche or distribution checks is rejected. Miri checks supported
execution paths for memory and arithmetic defects; it does not measure throughput
or prove collision resistance.

**Exercise structured keys on every selected function.** Avalanche and random
collision tests do not replace the actual RDF field protocol. XOR-folding a
128-bit product maps zero to zero and an all-ones word to all ones for every
nonzero multiplier. An unseeded second lane can therefore cancel the next
all-ones field. The portable table hasher seeds that lane independently, retaining
parallel multiplies and constant-foldable metadata. Successive folds remove the
same special case but introduce a dependency chain: the paired baseline-x86-64
[measurements](../benchmarks/hash-optimization-2026-09-28/portable-mixing/README.md)
show their cost for packed triples. Explicit portable regressions run even on
an AES host. Public fixed seeds still do not resist deliberately constructed
collisions.

### 2.6 Measuring the complete optimization

The release manifest requests optimization level 3, fat LTO and one codegen unit.
The assertion-enabled development/test profile has a separate purpose and retains
overflow checks and debug assertions. Inspect the effective compiler invocation;
a Cargo configuration or environment override can change what a manifest appears
to request. Applications control `target-cpu` and any profile-guided optimization.
A portable library must not assume the benchmark host's ISA or training workload.

`scripts/bench-hash-comparison.py` creates an isolated oracle workspace, pins the
comparison packages to versions and checksums from a supplied historical lock,
and calls only public APIs. The production dependency graph remains unchanged.
Each case calibrates its repetitions, records twelve samples in alternating A/B
and B/A order, and keeps the individual observations. It retains the compiler,
flags, source hashes, generated lock, executable and requested CPU affinity.
Its `--lto` option is enforced with a Cargo command-line override: a host profile
configuration must not silently turn the requested fat LTO into thin LTO.

```sh
python3 scripts/bench-hash-comparison.py --lock-ref <historical-commit> \
  --output /tmp/hash-baseline --cpu x86-64 --cpus 8
python3 scripts/bench-hash-comparison.py --lock-ref <historical-commit> \
  --output /tmp/hash-native --cpu native --cpus 8
python3 scripts/bench-hash-comparison.py --lock-ref <historical-commit> \
  --output /tmp/hash-sse2 --cpu x86-64 --cpus 8 \
  --baseline-isa sse2 --mode blake3-backend-sse2
```

`scripts/bench-hash-workloads.py` compares immutable repository snapshots over
nine complete operations: IRI and mixed RDF 1.2 interning/build/freeze, N-Quads
and Turtle parsing, a SPARQL join, and GTS authoring/reading with 4 KiB and
1 MiB blobs. It requires equal output counts and byte identities before timing.
A separate executable measures allocation calls, requested bytes, peak and
retained memory. `--perf` enables counters only around the operation loop;
fixture creation, warmups and output verification remain outside it. Counter
control transitions and the loop's clock reads remain bounded overhead.

```sh
python3 scripts/bench-hash-workloads.py \
  --source before=/path/to/immutable-before \
  --source candidate=/path/to/immutable-candidate \
  --output /tmp/hash-workloads --cpu native --cpus 8 --jobs 16 --perf
```

Build parallelism follows Cargo configuration unless `--jobs` is supplied.
The script preserves compiler/profile/source identities, binary hashes, locks,
raw paired samples and counter receipts. It refuses a source mutation during
compilation. `--reuse label=/previous/run` reuses a matching control build only
after checking the source, compiler, profile, harness and executable identity.
Timing uses the system allocator. Do not reuse a counting-allocator latency as
normal throughput, or call noisy shared-host wall times an exclusive-host result.

Run timed comparisons sequentially on a quiet host; record background load and
thread-pool size. Use a normal allocator for latency measurements and the counting
allocator for a separate allocation experiment. Report paired ratios and their
distribution per algorithm, input size and update width. Include fresh and reused
states, realistic interner keys, and both bulk and irregular streaming workloads.
Keep rejected experiments with their measurements so they are not mistaken for
untried opportunities.

Original library implementations may inform the experiments: inspect their
batch widths, instruction scheduling, state layout and dispatch choices, then
implement the chosen technique using PurRDF's own arithmetic and interfaces.
Do not copy or port their code. Record the exact source version, files consulted
and ideas tested in the affected crate's provenance notes. Once a source has
been consulted, do not describe subsequent work as clean-room. Frozen public-API
answers remain an independent correctness check; source inspection does not
replace them.

ISA forcing on a modern CPU proves path selection and functional coverage. Cross
compilation proves buildability and emitted instructions. Neither measures an old
x86 CPU, an Arm core, or another architecture's cache, multiplier or vector costs.
Hardware-specific throughput claims require execution on that hardware. Assembly
counts, Miri, frozen-answer replay, allocation assertions, release builds and
end-to-end benchmarks supply different parts of the evidence; none substitutes
for the others.

## 3. Contract law

### 3.1 An arithmetic contract is a type

`purrdf_core::distance::Arithmetic` is a sealed trait with two implementations:

- **`Exact`**, the regime-3 law: sixteen binary64 accumulators over the whole
  sixteen-element chunks (`as_chunks::<16>`, the array form of `chunks_exact(16)`,
  rebuilt each step with `array::from_fn`), the pairwise tree `(l, l+8)`, `(l, l+4)`,
  `(l, l+2)`, `(0, 1)`, then the remainder folded sequentially in ascending index. Its identifier is
  `binary64-lane16-tree-v1`, a plain identifier and not an IRI.
- **`Reassociated`**, regime 2, identifier `binary64-reassociated-v1`.

Every consumer (the kernels, the exact kNN relation and HNSW) is generic over
`A: Arithmetic` with `Exact` as the default. Monomorphization gives two separate
functions per site, so there is no mode. Mixing arithmetics is a type error, and the
evidence strings, identifiers and guard tables are derived from `A`'s constants
rather than kept by hand. A further arithmetic (binned, quantized) is one more
`impl`.

### 3.2 Two functions, two contracts

The named entry points stay: `Kernel::distance` is `Exact`, and
`Kernel::distance_reassociated` is `Reassociated`. Each takes the resolved handle of its
own arithmetic (`Resolved<Exact>`, `Resolved<Reassociated>`), so passing one law's handle
to the other's entry point is a type error, and neither runs without the environment check
(§3.7). The exact kernel keeps its name and its promise. There is never a mode argument, an environment variable or a
switch that turns one into the other.

### 3.3 The fast contract names its divergence

A reassociated result carries evidence text that says what it gives up: sums are
reassociated and may be contracted to FMA along a named dispatch path, results may
differ in the last bits from the exact arithmetic and between dispatch paths or
builds, the sign of a zero result is unspecified, and near-ties may order
differently. The text is pinned by a test.

### 3.4 No substitution, in either direction

An exact call never runs reassociated code and a reassociated call never silently
falls back to exact code. Dispatch happens only inside one contract: `Exact` may
choose between a portable, an AVX2 and an AVX-512F compilation of the *same* generic
body (identical bits by construction and by test), and `Reassociated` may choose
between its own SSE2, AVX2+FMA and AVX-512 paths. The exact AVX-512F compilation is
kept on a measurement, not an argument: under generic tuning its sixteen lanes are two
`zmm` registers rather than AVX2's four `ymm`, so a sixteen-element block of the
squared-Euclidean fold is two `vsubpd`, two `vmulpd` and two `vaddpd` where AVX2 issues
four of each -- the same shape, with no FMA -- and every out-of-line kernel is shorter
(the `distance.exact.*` rows of §4.1 carry the counts). Both arithmetics select their
`avx512f` path by one rule: the processor reports AVX-512F, AVX2 and FMA. Every target has a reassociated path, so a
reassociated call is never refused for its target: x86_64 dispatches among those
three, aarch64 runs NEON and wasm its `simd128` or scalar build, and every other
target runs the `portable` path, the same body compiled once for the target's
baseline features. Dispatch is resolved once per scan, batch or index, never once per
pair.

### 3.5 Where the choice is recorded

The choice of arithmetic is recorded wherever it outlives the call:

- the HNSW image header carries an arithmetic field (formerly a reserved `u32` that
  had to be 0), holding the code of the path resolved at build time (`1` for `Exact`
  on every path; for `Reassociated` `2` sse2, `3` avx2+fma, `4` avx512f, `5` neon,
  `6` wasm-simd128, `7` wasm-scalar and `8` portable); decode refuses a code that is
  not one of the index type's own. Decode, search and rebuild verification resolve the
  recorded path itself (`Arithmetic::resolve_recorded`), not the widest this process
  runs, so an image recorded on a narrower path the processor also runs -- SSE2 or
  AVX2+FMA on an AVX-512F processor -- runs on that path; only a path this process
  cannot run (another target's compilation, or a processor without a feature it
  needs) is a named refusal;
- the path does not pin the code that ran. Every path is also compiled under the
  consumer build's own `-C target-cpu`/`-C target-feature`, and the `distance.reassociated.dot`
  row in §4.1 measures the consequence: the `avx512f` path is `zmm` FMA under generic
  tuning and `ymm` in an x86-64-v4 build, the `sse2` path is itself FMA code in an
  x86-64-v3/v4 build (and in any build with `target-cpu=native` on an FMA processor),
  and the `neon` path is SVE `fmla` + `faddv` in a neoverse-v1 build. Two builds recording
  one path can compute different bits. So a reassociated image header also records,
  right after its code, the build's `BuildShape` (`Arithmetic::build_shape`): a versioned
  `u64` naming the target architecture and the `cfg(target_feature)` set that decides
  the reassociated body's vector and FMA code (on `x86_64` `sse3` through `avx512vl`
  and `fma`; on `aarch64` `neon`, `sve`, `sve2` and their neighbours; on wasm
  `simd128` and `relaxed-simd`; the layout table is in `distance/shape.rs`). Decode,
  search and rebuild verification refuse another build's shape with the named
  `HnswError::ArithmeticBuildMismatch`, whose message lists both feature sets. `Exact`
  has no shape and its image carries none: its bytes are the same in every build.
  The feature bits are not the whole build: `rustc` exposes no `cfg` for
  `-C target-cpu`, CPU tuning (x86-64-v4's 256-bit preference, a Neoverse
  scheduling model) is not a target feature, and neither the compiler release nor the
  optimisation level is a `cfg`. So the shape also carries a `BuildIdentity`, recorded
  as a second `u64` after the bits: the FNV-1a digest of one line of text that
  `purrdf-core`'s build script writes from what `cargo` hands it -- `rustc -vV`'s
  release, commit hash and LLVM version (run on `RUSTC`, never through a wrapper), the
  target CPU (`-C target-cpu` as named, `native` resolved to the host CPU `rustc`
  reports, else the target's default from `rustc --print target-cpus`), every
  `-C target-feature` as `rustc` applies them (tuning features such as
  `prefer-256-bit` included), any `-C llvm-args`, `codegen-units`, `lto` or
  `overflow-checks` in the rustflags, and the optimisation level -- followed by the
  crate's own `cfg(debug_assertions)`. A build of another identity is the same named
  `ArithmeticBuildMismatch`, whose message shows both identities and says which half of
  the shape differs. Under an equal path and shape the rebuild compiles the body to the
  code that computed the image, so a rebuild that differs is `false`, the same tamper
  evidence as an exact image's. What no build script sees is named on `BuildIdentity`:
  a `[profile]` table's own `lto`, `codegen-units` and `overflow-checks`, flags a
  `cargo rustc --` invocation appends, and a compiler whose `rustc -vV` does not tell it
  apart from another; builds that differ only there share an identity;
- the HNSW profile declaration folds the arithmetic identifier, so the profile
  digest binds the law, and a reassociated declaration ends with a
  `build-shape=<bits>` line and a `build-identity=<digest>` line, so its digest binds
  the build too;
- HNSW is `HnswIndex<A: Arithmetic = Exact>`, with `HnswSpace<A>` and
  `HnswRelation<A>` over it: every constructor is generic over the sealed
  `IndexArithmetic` family, and `build::<Reassociated>` / `decode` under
  `Reassociated` are the reassociated index. A
  reassociated index publishes its own implementation, `hnsw-reassociated-v2`, whose
  evidence revision is `LOSS_EVIDENCE` followed by the reassociated evidence for the
  path the build ran and the sentence that its canonical image is reproducible only by
  a build of the shape that made it, running the same dispatch path, since the image
  records that build's target, features and identity and a build of another shape
  refuses it (`profile::loss_evidence_for::<Reassociated>`). The
  guard's legal (identifier, revision, image codes) rows are derived from `Exact` and
  `Reassociated`, and a cross pairing is a profile failure. `HnswSpace::evidence()`
  returns that text, `HnswRelation::fidelity` carries it into `Completeness::Lossy`
  and composes the order axis with `OrderFidelity::Perturbed` carrying the
  arithmetic's own evidence, and the ranked declaration names the law;
- the kNN relation is `EmbeddingKnnRelation<A: Arithmetic = Exact>`: `new` builds the
  exact relation and `new_reassociated` the reassociated one, resolving its dispatch
  path once at construction (a flushing float environment is refused there, and on
  every search, with the named `EvalError::FloatEnvironment`), and the scan runs
  `A`'s batch kernel on that path. Its ranked declaration names the law in
  `RankedDeclaration::arithmetic` as `RankArithmetic::FloatDistance`, which
  `canonical_description` folds, so an exact
  and a reassociated producer over one space have different registry content
  fingerprints and so different plan ids. A `RankArithmetic::FloatFree` declaration
  (the lexical producer, which ranks fixed-point integers) describes itself in the
  bytes it always did. A reassociated relation also composes the host's order
  fidelity with `OrderFidelity::Perturbed`, carrying the evidence text for its
  resolved path verbatim, through `composed_order_fidelity`, the one composition
  the HNSW relation also uses. The completeness axis stays the host's, because a
  reassociated scan still scores every row;
- the fusion trailer (`FusionTrailer::fidelities`, `RankFidelity`) carries that
  fidelity into any fused ranking, and an answer with a reassociated stratum reports
  it as having no finite score bound.

Two records deliberately do **not** change. `DistanceMetric` names the metric's
semantics, which are unchanged; PURREMB §7.4 permits a kernel to optimize the
evaluation as long as it preserves the metric and row-number tie-breaking, so the
family-contract digest is the same for both arithmetics and a test asserts it.
`IndexLossContract` stays `transforms_vectors: false`: an arithmetic does not
transform the stored vectors, and `purrdf-core` requires `loss_encoding: None` in
that case, so the choice lives in the image field and the profile instead.

### 3.6 Identity paths are exact

Content identity, canonical serialization, GTS and RDFC-1.0 are exact by contract.
A kernel on those paths is regime 3 or bit-exact integer code, never reassociated.
This is enforced statically: `algebraic_add` and its siblings, and the
`Reassociated` arithmetic, may appear only under `crates/rdf-core/src/distance/`,
`crates/sparql-eval/src/knn/`, `crates/hnsw/src/` and those crates' tests and
benches. A hit anywhere else fails `make simd-asm`.

The PURREMB norm is the one float fold on an identity path. PURREMB §13.2 makes its
written order normative (no FMA, sequential), so `norm_fold` is never reordered and
has no reassociated sibling.

### 3.7 The float-environment precondition

Both arithmetics assume IEEE round-to-nearest, ties-to-even, with subnormals
preserved. A thread that has set flush-to-zero or denormals-are-zero, or another
rounding direction (MXCSR on x86_64, FPCR on aarch64, `frm` on RISC-V, FPSCR on
32-bit Arm and POWER), would compute different bits from the same code. So would a
unit that rounds twice: where `f64` arithmetic runs on the x87 (`i586`, or `i686`
built without SSE2), each result is rounded to the register's 64-bit significand and
again when it is stored, and a value kept in a register has a 15-bit exponent, so it
neither overflows nor becomes subnormal where binary64 would.

The x87 is made correct, not refused -- and not only here. Every binary floating-point
operation in the workspace whose bits reach a result runs through one layer,
`purrdf_xsd::ieee`, the lowest crate every consumer depends on: both distance
arithmetics, the PURREMB norm and the probe (as `Binary64` methods inside a `Precision`
scope, `distance::binary64`, a thin wrapper over `ieee::Binary64Scope`), and beyond the
distance module the `xsd:double` and `xsd:float` operators (`numeric_add`, `_sub`, `_mul`,
`_div`, so SPARQL `+ − × ÷`, `SUM`, `AVG`, `VARIANCE`), `fn:round`, the decimal and
big-integer conversions' exact paths, `STDDEV`'s square root, the join planner's cost
model (whose estimate orders an unordered query's rows and decides a governed refusal),
the normalized-projection reads, and the CSVW percentage scaling. `+`, `−`, `×`, `÷` and
`√` at both widths are correctly rounded; the transcendentals are not required to be by
IEEE-754, and no result is computed with one. On every other target each operation is
the language's operator, `#[inline(always)]`, and each scope is empty (the reassociated
body keeps its `algebraic_*` operations there; they are defined in `distance::binary64`,
not in the exact-only `ieee` layer, and on the x87 they are its correctly rounded `+`,
`−`, `×` in written order). On the x87 a `Binary64Scope` saves the
control word and sets its precision-control field to 53 bits (a `Binary32Scope` to 24),
restoring the caller's word on exit, unwinding included; each operation is one `asm!`
block that loads its operands, performs one instruction and stores a result of the
operation's width, so no value outlives its operation at the register's precision or
range. That makes `+`, `−` and `√` correctly rounded: a normal result already has the
format's width, an overflow is stored as the infinity IEEE gives, and a sum or
difference in the subnormal range is exact. It does not make `×` and `÷` correct in the
subnormal range, where the result is rounded again by the store (Monniaux, *The pitfalls
of verifying floating-point computations*, 2008). The technique `HotSpot` used for Java's
`strictfp` closes that: one operand is scaled by the distance between the x87's smallest
normal exponent (−16382) and the format's -- 2⁻¹⁵³⁶⁰ for binary64 (−1022), 2⁻¹⁶²⁵⁶ for
binary32 (−126) -- so the x87 denormalizes the result onto the format's subnormal grid
(scaled) and rounds once; scaling back and storing are exact. On the x87 the reassociated
body runs these same operations in written order: the licence permits reassociation and
requires none, and every value the fold holds is then binary64, as its evidence claims.
An integer software reference that rounds without any floating-point unit
(`ieee::reference`) is the oracle: the operations at both widths, the probe constants,
the exact kernels, the norm, and the SPARQL operators and aggregates on double-rounding
witnesses equal it bit for bit on every target, and the CI runs the `purrdf-xsd` unit
tests, the SPARQL arithmetic tests and the distance, kNN and HNSW suites on `i586`. A
thread that loaded a directed rounding control into its x87 control word is refused by
name at every distance entry point, on the thread that computes, rayon workers included.

The law is behavioural, and it holds on every target. Resolving an arithmetic runs a
probe of thirteen binary64 operations whose correctly rounded results under the
assumed environment are known constants, computed through the same `Binary64`
operations and inside the same `Precision` scope as every kernel, with every operand
passed through `core::hint::black_box` so none is folded at compile time:

| Operation (`ulp` = 2⁻⁵²) | IEEE-754 result | A mismatch shows |
|---|---|---|
| `f64::MIN_POSITIVE × 0.5` | subnormal 2⁻¹⁰²³ | subnormal results flushed |
| `2⁻¹⁰⁷⁴ × 2¹⁰²³` | normal 2⁻⁵¹ | subnormal operands read as zero |
| `1 + 0.75 ulp` | `1 + ulp` | rounding toward zero or down |
| `1 + 0.25 ulp` | `1` | rounding up |
| `−1 − 0.75 ulp` | `−(1 + ulp)` | rounding toward zero or up |
| `−1 − 0.25 ulp` | `−1` | rounding down |
| `1 + 0.5 ulp` | `1` | a tie rounded away from zero, or up |
| `(1 + ulp) + 0.5 ulp` | `1 + 2 ulp` | a tie rounded toward zero, or down |
| `1 + (2⁻⁵³ + 2⁻⁷⁸)` | `1 + ulp` | a sum rounded twice |
| `(1 + ulp) + (2⁻⁵³ − 2⁻⁷⁸)` | `1 + ulp` | a sum rounded twice |
| `(1 − 0.5 ulp) × (1 + 2 ulp)` | `1 + ulp` | a product rounded twice |
| `2⁻⁵¹²(1 + 4 ulp) × 2⁻⁵¹¹(1 − ulp)` | subnormal `2⁻¹⁰²³ + 2⁻¹⁰⁷⁴` | a subnormal product rounded twice |
| `2⁻⁵¹² ÷ 2⁵¹¹(1 − ulp)` | subnormal `2⁻¹⁰²³ + 2⁻¹⁰⁷⁴` | a subnormal quotient rounded twice |

The last five rows are double-rounding witnesses: each exact result lies within a
64-bit rounding of a binary64 midpoint without being one, so rounding it first to the
x87's 64 bits lands on the midpoint and the tie then goes to the wrong neighbour.
Precision control at 53 bits closes the three normal-range rows; only the scaling
closes the two subnormal ones. Every unit that rounds once passes all five, and the
software reference shows that none of the first eight rows can tell double rounding
apart. The first row whose bits differ is refused as `FloatEnvironmentError::FlushToZero`,
`RoundingMode` or `DoubleRounding`, with `FloatEnvironmentEvidence::Probe` naming the
operation and both bit patterns; a thread where the precision guard did not take hold
is refused as `DoubleRounding` rather than handed doubly rounded distances. The probe is binary64 only because binary64 is the only precision the
arithmetics execute: `f32` operands are widened per component before any operation.

Where this build reads the control register — MXCSR on x86_64, FPCR on aarch64, and the
x87 control word where the x87 is the binary64 unit — it reads it first, so a refusal
names the register and its value (`FloatEnvironmentEvidence::Register`), and then runs
the probe as well, which proves the environment rather than the bits the build knows
the meaning of. The x87 control word is refused for a directed rounding-control field
only: its precision-control field is the guard's to set, so a caller that left it at 24
or 64 bits is served correctly rounded binary64, not refused. WebAssembly's
numeric instructions are specified to round to nearest-even and preserve subnormals;
the probe runs there too, since it is thirteen operations and an engine departing from
the specification is then refused by name rather than trusted. No target is refused
for being unread: an environment is refused only when it has been observed to depart.

The check cannot be bypassed by choosing a different entry point, because every public
entry point that computes a distance takes the resolved handle the check produces
(`Resolved<A>`): the batch and pair kernels on `Resolved` in `purrdf-core`,
`Kernel::distance`, `Kernel::distance_bounded` (a `Resolved<Exact>`) and their
`_reassociated` siblings (a `Resolved<Reassociated>`) in `purrdf-sparql-eval`, and
`VectorMatrix::distance`, `distance_from_query` and `distance_bounded` (a `Resolved<A>`)
in `purrdf-hnsw`. There is no handle-free distance. A flushing thread is refused by name
when it asks for the handle, so it never obtains one and no distance, per-pair or batch,
is computed on it; `crates/hnsw/tests/float_environment.rs` executes that refusal and, as
its valid neighbour, every pair entry point in the default environment agreeing bit for
bit with the batch kernel on a pair whose distance is subnormal, so a flushing thread
would have returned zero for it.

Nor can it be bypassed by choosing a different thread. The environment is per-thread
control state: MXCSR and FPCR are saved and restored with the thread, so a handle
resolved on a clean thread proves nothing about another. `Resolved<A>` is therefore
neither `Send` nor `Sync` (a `PhantomData<*const ()>` marker beside the path), and the
compiler refuses to move one, or share a reference to one, across threads; two
`compile_fail` doctests on the type pin both refusals, beside a passing one that sends
the thread-free selection instead. What outlives a thread is `Selected<A>`, the
arithmetic and its dispatch path with no environment proof, which is `Send`, `Sync` and
computes nothing: `Selected::resolve` repeats the environment check on the calling
thread (the path was selected once, from the process's processor features) before it
hands out a handle. Every long-lived structure stores that: `HnswIndex` its recorded
path (`HnswIndex::arithmetic`), and the kNN relation and its cursor the path a
reassociated relation selected at construction (`EmbeddingKnnRelation::selected`).
Every compute entry resolves on the thread that computes: HNSW search, `search_batch`,
`row_distance`, `verify_rebuild` and the kNN scan and membership lookup once per call,
and `search_batch` and the build's parallel proposals once inside each rayon worker,
per worker's share rather than per query or pair.
`crates/hnsw/tests/float_environment.rs` builds every index and relation on the test
thread and executes the refusal from a worker thread that set flush-to-zero on itself
(`search_batch` and `row_distance` on both indexes, the scan and the membership lookup
on both kNN relations), with the same calls from a clean worker answering the test
thread's bits as the valid neighbour; `crates/hnsw/tests/float_environment_rayon.rs`
makes rayon's global pool flush-to-zero and shows a batch called from a clean thread
refused by its workers, while the same batch on a clean pool answers the single-thread
bits.

The L2 norm a cosine kernel divides by is arithmetic too, and follows the same law. Its
only public form is `Resolved::<Exact>::norm` in `purrdf-core` (re-exported through
`knn`), a method of the exact handle alone: PURREMB §13.2 gives the fold one written
order, so it has no reassociated form, and a `Reassociated` consumer obtains the exact
handle with `Resolved::exact`, which carries the environment its own handle proved. The
other public norm entry points take that handle as well: `VectorMatrix::norm_of_row` in
`purrdf-hnsw`, and PURREMB's deterministic-L2 projection rows,
`EffectiveMatrixView::f32_row` and `f64_row` in `purrdf-core` (and
`guard::read_effective_matrix`, which reads through them). The artifact writer and
`verify_embedding` resolve the exact handle once where a normalized projection is present
and refuse a flushing thread with `EmbeddingError::FloatEnvironment`; a raw projection
folds stored bytes and no arithmetic, so it is written and verified on any thread. The
same suite executes the norm refusal on a row whose norm is subnormal (`[3e-310,
4e-310]`, which a flushing thread folds to `+0`) and, as the valid neighbour, every norm
entry point returning the reference fold's nonzero bits once the register is restored;
`crates/rdf-core/tests/purremb_float_environment.rs` does the same for the writer, the
verifier and the normalized row, with a raw artifact written and verified under the
flushed register as the neighbour.

The probe runs on every resolve, which is once per scan, search, lookup, rebuild, pair
call site or rayon worker's share of a batch, never once per pair: the handle is `Copy`,
and a loop on one thread passes the one it holds.
A resolve is a handful of operations and no allocation. The `cross-arch` CI job checks the kernels on
i686, armv7, riscv64, powerpc64le, s390x and loongarch64 and executes the distance,
kNN and HNSW suites on i686, and `cross-arch-riscv64` executes them on riscv64 under
emulation; on both no register is read and the probe alone decides.

## 4. Inventory

### 4.1 Site table

One row per site. `crate` is the workspace member the row belongs to; `fn` and
`path` locate the source; `covers` names the minimum-coverage roster entries the row
answers for; `class` is **I** (integer or byte code), **FI** (float whose bits are
identity or normative) or **FR** (float used for ranking). The verdicts:

- **covered**: the site already compiles to vector work, or deliberately to a
  SWAR or popcount path; its manifest entry carries floors and proof mnemonics;
- **rewrite**: the site was reformulated (§2.3) so LLVM vectorizes it;
- **regime-3**: a float fold on the fixed-lane exact law, with dispatch inside
  `Exact`;
- **fast-variant**: a site with a separate reassociated entry point;
- **leave**: nothing vector-shaped is left to take, for the stated reason.

Each configuration cell is generated: per measured symbol, `v` vector operations
(the minimum over the symbol's copies), `f` fused multiply-adds and `r` `relaxed_`
wasm instructions (the maxima), and `req✓` where the required mnemonics are present.
A `leave` entry has a floor of 0 and requires no mnemonic, so its cells are a record
of what the site compiles to, subject to the whole-symbol caveat of §2.4. A
`rewrite` entry carries the floors and proof mnemonics of its reformulated shape; a
rewritten site with nothing vector-shaped left in it (a cursor, a table load) keeps a
floor of 0 and says so. A crate-level row names no function and has no cells.

## 5. MSRV decision

**The rule.** The MSRV moves from 1.96 to 1.98 if and only if two things hold: the
reassociated arithmetic (regime 2) takes a real win the exact law cannot, and §3 can
express that arithmetic as a separate contract without weakening the exact one.

**Both hold.** Regime 3 already vectorizes the exact fold, but it cannot reassociate
across its fixed tree and it can never fuse a multiply into an add: FMA and free
reassociation are exactly what the exact contract forbids (§2.4). The only stable way
to grant them for one operation is the `algebraic_*` family, stable from Rust 1.98.
That win is taken by the reassociated distance kernels, and nowhere else: the
reassociated `dot` and `squared_euclidean` behind `Kernel::distance_reassociated`,
the reassociated kNN relation, and the reassociated HNSW build and search. §3 expresses
them as the `Reassociated` implementation of `Arithmetic`, with their own names,
their own evidence and their own recorded identifiers, and the static scan keeps
them off every identity path. The MSRV therefore moves to 1.98.

**What moved with it.** `rust-version` in the workspace manifest, the CI `msrv` job
(its toolchain, both `RUSTUP_TOOLCHAIN` values and the assertion that the resolved
compiler really is 1.98), `clippy.toml`, the README badge and MSRV policy, the
contributor and agent guides, and every crate README that states the floor. The
floor is proven in both directions: a 1.98 compiler checks the workspace, and a 1.97
compiler, with cargo's `rust-version` guard set aside, rejects the crate on
`float_algebraic` itself (E0658), so the floor comes from the code, not the manifest.

**The consequence, accepted deliberately.** 1.98 was the current stable release when
the floor moved, so a consumer has no headroom: the oldest compiler PurRDF supports is
the newest one available. Every other capability this document relies on (the x86,
aarch64 and wasm intrinsics, safe `#[target_feature]` functions, `as_chunks`) was
already inside the previous floor; `algebraic_*` alone required the move.
