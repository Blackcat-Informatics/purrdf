# PurRDF SIMD: the stable ceiling, arithmetic contracts and the hot-path audit

This document is the audit of every hot path in the PurRDF workspace against one
question: what does the compiler actually emit for it, on each target a PurRDF
build runs on? It records the rules a vectorized kernel must satisfy to ship, and
the arithmetic contracts that decide whether a float kernel may be reordered. The
evidence is always the emitted assembly, never the source.

Two things in the tree used SIMD on purpose before this audit: `memchr` on the
codec and lexer paths, and the `+simd128` wasm artifact. Everything else is what
LLVM chose to do with ordinary scalar code, and §4 measures what that is.

The measured columns of §4.1 are generated by `scripts/check-simd-asm.py
--write-doc`, and `make simd-asm` fails when the committed document and a fresh
measurement disagree. Every count in this document is therefore the count of the
tree the document ships in.

---

## 1. The stable ceiling

PurRDF builds on a nightly toolchain but uses no nightly feature, and its MSRV is a
stable release (§5). Everything below is therefore restricted to what
stable Rust offers. That is project law, not a preference.

### 1.1 Capability table

| Capability | Stable status | What PurRDF does with it |
|---|---|---|
| `#![feature(...)]` of any kind | not stable | never used; `git grep '#!\[feature'` over `crates/` and `bindings/` is empty |
| `std::simd` (portable SIMD) | not stable | not used |
| `core::arch` intrinsics | stable, per target | allowed only where the asm proves a reformulation cannot reach the same code (§2.3, rule c) |
| `#[target_feature(enable = "...")]` on a function | stable | allowed under the same rule. Such a function does not coerce to a plain `fn` pointer, so dispatch goes through ordinary wrapper functions, never through a table of `#[target_feature]` pointers |
| `is_x86_feature_detected!` / `is_aarch64_feature_detected!` | stable (std) | run-time dispatch, resolved once per scan, relation or index, never once per pair |
| wasm `simd128` (`-C target-feature=+simd128`) | stable, compile-time only | the `+simd128` wasm artifact; there is no run-time detection on wasm |
| wasm `relaxed-simd` | stable | **disqualified** for ranked and identity kernels: its results are allowed to differ between engines, so a ranking or a digest computed in one browser would not be the one computed in another. Every ranked or identity site is measured with `forbid_relaxed` |
| `f64::algebraic_add` / `algebraic_mul` / `algebraic_sub` (`float_algebraic`) | stable from Rust 1.98 | the only stable grant of reassociation and contraction for a single operation; the reassociated arithmetic of §3 is built on it, and it is why the MSRV moves (§5) |
| `-C target-cpu` / `-C target-feature` | a build flag | a consumer's choice. A library cannot make it for its consumers, so there is no workspace-wide `target-cpu` in cargo configuration; the audit measures the baseline and two raised levels per ISA instead |

### 1.2 Reproduction

The measurement is one gate. It emits assembly for seven configurations and counts
the vector work in every audited symbol:

| Configuration | Target | Codegen flag |
|---|---|---|
| `x86_64` | `x86_64-unknown-linux-gnu` | `-C target-cpu=x86-64` (SSE2) |
| `x86_64-v3` | `x86_64-unknown-linux-gnu` | `-C target-cpu=x86-64-v3` (AVX2, FMA) |
| `x86_64-v4` | `x86_64-unknown-linux-gnu` | `-C target-cpu=x86-64-v4` (AVX-512) |
| `aarch64` | `aarch64-unknown-linux-gnu` | none (NEON) |
| `aarch64-neoverse-v1` | `aarch64-unknown-linux-gnu` | `-C target-cpu=neoverse-v1` (SVE) |
| `wasm32` | `wasm32-unknown-unknown` | none (no SIMD proposal) |
| `wasm32-simd128` | `wasm32-unknown-unknown` | `-C target-feature=+simd128` |

```sh
make simd-asm                                      # measure, check the manifest and this document
python3 scripts/check-simd-asm.py --write-doc      # regenerate the measured columns of §4.1
python3 scripts/check-simd-asm.py --self-test      # every refusal and its valid neighbour, no build
python3 scripts/check-simd-asm.py --probe 'REGEX' [--config NAME] [--crate NAME] [--dump]
```

Each configuration is a release build with LTO off and one codegen unit, with
`--emit=asm` added through `CARGO_TARGET_<TRIPLE>_RUSTFLAGS`:

```sh
cargo build --release --locked --lib --target <triple> -p <audited packages> \
  --config 'profile.release.lto=false' --config 'profile.release.codegen-units=1'
```

That emits a `.s` for every crate in the graph, dependencies included, so a
dependency's own kernels (memchr's, sha2's, `regex-automata`'s) are measured in that
dependency's symbols. The asm is per crate and before LTO. LTO can only inline
further; it never removes a vector body a crate already compiled. `purrdf-wasm` is
also a `cdylib`, and linking one needs a linker for the target, which the asm does
not; it is built alone as an rlib (`cargo rustc --crate-type rlib`) against the same
dependency units.

The manifest, `scripts/simd-asm-manifest.toml`, names for each site the symbol it is
measured in on each configuration, a floor of vector operations, the mnemonics that
prove the shape, and an FMA bound. A private or inlined function is measured in the
out-of-line symbol that inlines it, and the manifest names that symbol. A missing
target standard library or tool is a failure, locally and in CI; nothing skips.

## 2. The three regimes and the formulation rule

### 2.1 The regimes

Every float fold in this workspace is in one of three regimes.

1. **Sequential exact.** `s += x * y` in index order. IEEE `+` is not associative,
   and LLVM is not permitted to reassociate it, so the accumulation compiles to one
   scalar add chain on every target. LLVM may still vectorize the parts that carry
   no order: the kNN dot fold was regime 1 before it moved to regime 3, and on
   `aarch64` with f32 operands its widening (`fcvtl`, `fcvtl2`) and products
   (`fmul v.2d`) were packed while the sum stayed a chain of scalar `fadd d`
   instructions. Same bits on every target; no vector accumulation anywhere. The
   PURREMB norm (`core.purremb-norm`, `knn.norm`) stays in this regime because its
   order is normative.
2. **Reassociated.** The operation grants LLVM reassociation and contraction
   (`algebraic_*`). The accumulation vectorizes and may fuse into FMA. The bits
   depend on the target, the dispatch path and the build.
3. **Fixed-lane exact.** The fold is *defined* as `LANES` independent accumulators
   followed by a fixed pairwise tree and a sequential tail. That order is the
   contract, so it is the same order on every target, it needs no grant from the
   compiler, and it vectorizes. Same bits on every target.

### 2.2 The formulation is load-bearing

Regime 3 is only regime 3 if LLVM can see the lanes. A fold written
`acc[l] += a[i * LANES + l] * b[i * LANES + l]` compiles to zero vector operations:
the index arithmetic hides the independence of the lanes. The same fold written over
`a.chunks_exact(LANES).zip(b.chunks_exact(LANES))` with an `array::from_fn`
accumulator update compiles to a packed loop. So a claim that a kernel vectorizes is
a claim about emitted asm, and every site in §4 is measured.

### 2.3 The preference order

1. **(a) Reformulate the source** so LLVM vectorizes it: `chunks_exact`,
   `array::from_fn` accumulators, bounds checks hoisted out of the loop, no dispatch
   in the inner loop. It stays portable and free of `unsafe`.
2. **(b) Offer a separate fast-variant function** under its own contract (§3).
3. **(c) Gate internally** with `core::arch` or `#[target_feature]`, only where the
   asm proves (a) cannot reach the code, and only with bit-equality under the
   function's contract.

### 2.4 What asm can and cannot prove

- `max_fma = 0` is necessary for an exact kernel and is enforced on every exact
  site. It is **not sufficient**: a fold with no FMA can still add in the wrong
  order. Summation order is proven only by the scalar reference-model tests, which
  emulate the lane, tree and tail order in plain nested loops and compare bits.
- Rust never sets LLVM's `contract` fast-math flag on a plain `*` or `+`. So
  `#[target_feature(enable = "fma")]` on an exact kernel cannot fuse it; FMA appears
  only where an `algebraic_*` operation or an explicit `mul_add` asks for it.
- A count is the whole symbol a site is measured in. When a site is inlined into a
  larger function, that function's other vector work (hashbrown's SSE2 or NEON
  group probes, straight-line struct moves, a UTF-8 width computation) lands in the
  same count. The *proof mnemonics* are what tie a count to the audited loop, which
  is why every `covered` row requires them and no `leave` or `rewrite` row claims
  vector work from a bare count.

## 3. Contract law

### 3.1 An arithmetic contract is a type

`purrdf_core::distance::Arithmetic` is a sealed trait with two implementations:

- **`Exact`**, the regime-3 law: sixteen binary64 accumulators over the whole
  sixteen-element chunks (`as_chunks::<16>`, the array form of `chunks_exact(16)`,
  rebuilt each step with `array::from_fn`), the pairwise tree `(l, l+8)`, `(l, l+4)`,
  `(l, l+2)`, `(0, 1)`, then the remainder folded sequentially in ascending index. Its identifier is
  `binary64-lane16-tree-v1`, a plain identifier and not an IRI.
- **`Reassociated`**, regime 2, identifier `binary64-reassociated-v1`.

Every consumer (the kernels, the exact kNN relation and HNSW) is generic over
`A: Arithmetic` with `Exact` as the default. Monomorphization gives two separate
functions per site, so there is no mode. Mixing arithmetics is a type error, and the
evidence strings, identifiers and guard tables are derived from `A`'s constants
rather than kept by hand. A further arithmetic (binned, quantized) is one more
`impl`.

### 3.2 Two functions, two contracts

The named entry points stay: `Kernel::distance` is `Exact`, and
`Kernel::distance_reassociated` is `Reassociated`. The exact kernel keeps its name
and its promise. There is never a mode argument, an environment variable or a
switch that turns one into the other.

### 3.3 The fast contract names its divergence

A reassociated result carries evidence text that says what it gives up: sums are
reassociated and may be contracted to FMA along a named dispatch path, results may
differ in the last bits from the exact arithmetic and between dispatch paths or
builds, the sign of a zero result is unspecified, and near-ties may order
differently. The text is pinned by a test.

### 3.4 No substitution, in either direction

An exact call never runs reassociated code and a reassociated call never silently
falls back to exact code. Dispatch happens only inside one contract: `Exact` may
choose between a portable and an AVX2 compilation of the *same* generic body
(identical bits by construction and by test), and `Reassociated` may choose between
its own SSE2, AVX2+FMA and AVX-512 paths. Dispatch is resolved once per scan, batch
or index, never once per pair.

### 3.5 Where the choice is recorded

The choice of arithmetic is recorded wherever it outlives the call:

- the HNSW image header carries an arithmetic field (formerly a reserved `u32` that
  had to be 0), holding the code of the path resolved at build time; decode refuses a
  code that is not one of the index type's own, and a re-resolved path that differs
  from the recorded one is a named refusal;
- the HNSW profile declaration folds the arithmetic identifier, so the profile
  digest binds the law;
- `HnswSpace::evidence()` and `LOSS_EVIDENCE` carry the arithmetic-specific text;
- the kNN relation's ranked declaration folds the identifier, and a reassociated
  relation declares a perturbed order fidelity with the evidence text;
- the fusion trailer (`FusionTrailer::fidelities`, `RankFidelity`) carries that
  fidelity into any fused ranking.

Two records deliberately do **not** change. `DistanceMetric` names the metric's
semantics, which are unchanged; PURREMB §7.4 permits a kernel to optimize the
evaluation as long as it preserves the metric and row-number tie-breaking, so the
family-contract digest is the same for both arithmetics and a test asserts it.
`IndexLossContract` stays `transforms_vectors: false`: an arithmetic does not
transform the stored vectors, and `purrdf-core` requires `loss_encoding: None` in
that case, so the choice lives in the image field and the profile instead.

### 3.6 Identity paths are exact

Content identity, canonical serialization, GTS and RDFC-1.0 are exact by contract.
A kernel on those paths is regime 3 or bit-exact integer code, never reassociated.
This is enforced statically: `algebraic_add` and its siblings, and the
`Reassociated` arithmetic, may appear only under `crates/rdf-core/src/distance/`,
`crates/sparql-eval/src/knn/`, `crates/hnsw/src/` and those crates' tests and
benches. A hit anywhere else fails `make simd-asm`.

The PURREMB norm is the one float fold on an identity path. PURREMB §13.2 makes its
written order normative (no FMA, sequential), so `norm_fold` is never reordered and
has no reassociated sibling.

### 3.7 The float-environment precondition

Both arithmetics assume IEEE round-to-nearest with subnormals preserved. A process
that has set flush-to-zero or denormals-are-zero (MXCSR on x86_64, FPCR on aarch64)
would compute different bits from the same code. Resolving an arithmetic reads that
register and refuses such an environment with a named error; wasm always preserves
subnormals.

## 4. Inventory

### 4.1 Site table

One row per site. `crate` is the workspace member the row belongs to; `fn` and
`path` locate the source; `covers` names the minimum-coverage roster entries the row
answers for; `class` is **I** (integer or byte code), **FI** (float whose bits are
identity or normative) or **FR** (float used for ranking). The verdicts:

- **covered**: the site already compiles to vector work, or deliberately to a
  SWAR or popcount path; its manifest entry carries floors and proof mnemonics;
- **rewrite**: the site is reformulated (§2.3) so LLVM vectorizes it;
- **regime-3**: a float fold that moves to the fixed-lane exact law, with dispatch
  inside `Exact`;
- **fast-variant**: a site that gains a separate reassociated entry point;
- **leave**: nothing vector-shaped is left to take, for the stated reason.

Each configuration cell is generated: per measured symbol, `v` vector operations
(the minimum over the symbol's copies), `f` fused multiply-adds and `r` `relaxed_`
wasm instructions (the maxima), and `req✓` where the required mnemonics are present.
A `leave` or `rewrite` entry has a floor of 0 and requires no mnemonic, so its cells
are a record of what the site compiles to today, subject to the whole-symbol caveat
of §2.4. A crate-level row names no function and has no cells.

## 5. MSRV decision

**The rule.** The MSRV moves from 1.96 to 1.98 if and only if two things hold: the
reassociated arithmetic (regime 2) takes a real win the exact law cannot, and §3 can
express that arithmetic as a separate contract without weakening the exact one.

**Both hold.** Regime 3 already vectorizes the exact fold, but it cannot reassociate
across its fixed tree and it can never fuse a multiply into an add: FMA and free
reassociation are exactly what the exact contract forbids (§2.4). The only stable way
to grant them for one operation is the `algebraic_*` family, stable from Rust 1.98.
That win is taken by the reassociated distance kernels, and nowhere else: the
reassociated `dot` and `squared_euclidean` behind `Kernel::distance_reassociated`,
the reassociated kNN relation, and the reassociated HNSW build and search. §3 expresses
them as the `Reassociated` implementation of `Arithmetic`, with their own names,
their own evidence and their own recorded identifiers, and the static scan keeps
them off every identity path. The MSRV therefore moves to 1.98.
