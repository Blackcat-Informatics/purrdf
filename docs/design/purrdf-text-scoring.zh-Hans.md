# PurRDF 文本评分与排序

`purrdf-text` 为冻结的 RDF 1.2 数据集中的字面量建立内存倒排索引，并据此回答排序检索查询。本文记录一些容易被误认为疏漏的接口决策——没有提供的调节项、没有输出的列、不可配置的常量——并说明各项保证的边界。

所有示例 IRI 均使用 `example.org`。PurRDF 不生成词汇表 IRI；查询用来调用此 crate 的每个谓词都由调用方配置。

---

## 1. 精确运算是正确性要求

每个分数都用十进制定点数计算：带符号整数按固定小数位数缩放，并在每项指定运算处截断。必要时，排序过程的中间值会从已检查的 i128 提升到工作区的精确 Integer／BigInt；算术法则不变，也无须预设输入上限。最终值绝不回绕或饱和。评分和排序完全不使用浮点运算；其根部禁止 `clippy::float_arithmetic`。

这并非偏好整数的风格选择。BM25 需要自然对数；不同的 libm `ln` 实现可以在最低有效位相差一个单位。这个差异足以颠倒两份近乎并列的文档。相同引擎、相同数据、相同查询于是可能在原生构建与 `wasm32-unknown-unknown` 构建中返回不同的行序。两份答案都合乎格式，后续层无法识别哪一份有误。

因此，对数由整数级数按**固定迭代次数**求值，而不是执行收敛测试。收敛测试的迭代次数取决于正在检验的算术结果，会把要消除的目标架构差异重新引入。固定次数使结果在每个目标架构上仅由输入决定，排序也逐字节可复现。

由于运算是精确的而非近似的，文档的逐项贡献之和与其分数**严格相等**。解释接口报告等式，而不是容差。

修订版 2 的排序身份绑定了不设选定输入上限的算术和原有舍入法则。每个预备查询按实际语料和 IDF 证明自己的分数区间；纯函数结果及原生排序结果均携带上界及其位宽。宿主自行决定键的表示方式。查询项数量、字段长度、语料大小、权重及字段数量，都不会仅为预留宿主的并列排序键空间而被拒绝。物理表示与证明见[完整排序法则](../../crates/text/RANKING.md)。

## 2. `k1` 固定；排序配置拥有字段归一化规则

`K1`（1.2）固定。`B`（0.75）是显式单字段配置的默认值；不可变的排序 profile `RankingProfile` 将各命名字段的权重与长度归一化、谓词路由及评分法则绑定到其指纹。不同配置具有不同的排序身份。

PurRDF 是数据载体，因此排序选择必须属于索引声明的身份，而不能成为查询时隐含的调节项。查询同一索引的两个调用方使用相同的不可变配置。改变字段权重、归一化或谓词路由，会产生排序身份不同的索引；这些选择可能改变分数及作为答案顺序的 `?rank`。

这与被索引谓词 IRI 的规则不同。谓词由调用方提供，因为 PurRDF 不生成词汇表：如果数据载体自行选择 IRI，就等于发明某个本体的项，而且该 IRI 会进入使用者的 RDF 图。检索文献中的饱和常量并非词汇表，不会进入图，也不命名任何项。两条规则在这里指向不同选择，应明确各自适用的对象。

固定的 `k1` 与单字段默认 `b` 使用通常的 Okapi 数值。其他字段归一化值是显式、经验证的配置输入，并计入配置指纹；系统不会暗中为其他字段选择默认值。

## 3. 统计量和 `?rank` 都以分区为单位

一个**分区**是 `(graph, language)` 对。描述*语料*而非单篇文档的每项 BM25 输入——文档数 `N`、平均文档长度 `avgdl`、某项的文档频率 `df`——都在各自分区内计算，绝不跨分区汇总。

跨分区汇总不仅杂乱，还会改变结果。英语检索词的逆文档频率会取决于同一数据集中恰好放了多少日语文本；只在另一种语言中添加无关文档，也可能无声地重排英语答案。不同词汇表上的文档分数还会被并列展示，仿佛彼此可比。

`?rank` 也遵循这一界限。分数仅*相对于一个语料*有意义，因此跨分区名次会把按不同语料计算的数值排在一起——那只是排列，不是排序。`?rank` 是文档在**所属分区内**从 1 开始的位置；排序器进行的每次比较也都留在同一分区。需要单一排序列表的查询应绑定 `?lang`（相关时还要绑定图），或者使用单分区索引；单语言语料通常属于后者。

在排序*之前*限制分区是正确的，因为名次本来就是分区内名次：移除整个分区不会改变任何保留行的名次，它们从未与被移除的行比较。

这个性质也使限制分区成为真正的**性能**机制，而不只是过滤器。已绑定语言可直接找到其分区；已绑定文档可通过 `TextIndex::partitions_holding_subject` 找到主体所在的分区，因为文档键是 `(graph, subject, language)`，一个主体在每个分区最多占一篇文档。两种限制都在排序前执行。否则，按左侧每一行驱动一次关系的求值器，会为每一行给整个索引排序，再丢弃几乎全部结果。

### 字段名指明分区，因为数值本身无法指明

Rust 接口把该字段命名为 `Scored::partition_rank`，而不是 `rank`。这一区别只能由名称表达：英语分区的 `1` 与法语分区的 `1` 都是普通整数；下游行、`xsd:integer` 单元及两者之间的比较，均不记录其语料来源。因此，对三语言索引执行 SPARQL 查询，会得到**三个**名次为 1 的行；`LIMIT 10` 取得按分区优先排列的输出的前十行，而非全局最优的十份文档。同时限定图和语言，或使用单分区索引，才成为一份列表。

在一个分区内，顺序为 `(score DESC, document id ASC)`。文档 ID 在全部文档按 `(graph, subject, language)` 排序后才分配，所以 ID 升序*就是*规范项顺序升序。并列规则有明确含义，而且在独立构建的索引之间可复现，而不仅在同一个索引内稳定。ID 互不相同，所以这是严格全序，任意两行都不会并列；有界堆与完整排序因而能得到完全相同的结果。

## 4. 输出行中没有 `?graph` 位置

图是文档键的一部分，因此不同图的文本绝不合并：同一个主体 IRI 在两个命名图中是两篇文档；限制到某个图的搜索也不会根据另一个图的文本评分。

图却**不是**输出行的一列。原因来自 RDF，而非此 crate：属性函数的行宽固定，每个单元都必须装入 RDF 项；但 RDF 没有表示默认图的项，默认图是*没有图名*，而不是某个名称。若固定宽度行包含图单元，就必须为默认图文档填入某种值，候选只剩生成的哨兵 IRI 或空字符串字面量。哨兵 IRI 明确被禁止：PurRDF 不生成词汇表，它还会作为数据进入使用者的图。空字符串则与合法地以空字符串字面量命名的图相冲突，导致答案偏离原查询。

按图搜索改由索引的 `GraphSelector` 配置表达：它在值空间中用 IRI 命名图，再根据当前数据集解析。只需要一个图的调用方可以只索引该图。

## 5. 行数上限有条件提供；测量的边界如下

上限是求值器授予关系的许可：只有 `k` 行会影响答案。有此许可时，排序使用容量为 `k` 的二叉堆，而不是对所有候选行完整排序；它确实减少了工作量，而非完整排序后的提前停止。输出顺序为 `(partition ASC, rank ASC)`，所以输出位置 `i` 的行在所属分区中的名次至多为 `i + 1`。任何分区中名次超过 `k` 的行，都不可能进入输出的前 `k` 行；这个界限是精确的，不是启发式规则。

上限是**优化**：是否提供、是否遵守都不改变答案。因此下表记载的是观测到的行为，而非要求。必须满足且直接断言的条件只有一个：`LIMIT k` 下的答案必须严格等于无限制答案的前 `k` 个完整行，不能只比较行数。

| 查询形态 | 是否提供上限 |
| --- | --- |
| 单独的 `LIMIT k` | 是——该节点的输出就是答案的前缀 |
| `ORDER BY … LIMIT k` | **否** |
| 一个变量在两个参数位置重复出现 | **否** |
| `Lateral` 下的相关调用 | 是，但每次调用都会缩小 |

`ORDER BY … LIMIT k` 不提供上限，因为排序使它成为没有已认证下界的 top-k 问题：排序第一的行可能最后才被产生。节点的任意输出前缀都不能保证是最终答案前缀，计划因此没有授予提前停止的许可。

变量重复时也不提供上限：关系看到的是两个自由位置，不知道两者必须相等。若允许输出 `k` 行就停止，会把随后由引擎因变量不一致而丢弃的行算进限额。

在 `Lateral` 下，每个驱动行都会打开一次关系；各次调用间提供的上限会**递减**：求值器扣除已处理驱动行对结果多重集的贡献，再提供节点剩余的许可。若三个驱动行各贡献一行，上限依次是 `3`、`2`、`1`，不会发生第四次调用。

实际后果值得直说：输出已按名次排序，分区内名次也按分数排序，所以 `ORDER BY DESC(?score) LIMIT k` 既支付不必要的排序成本，又失去下推机会。表达「前 `k` 项」应直接使用 `LIMIT k`。

### `ORDER BY ?rank` 可重现原顺序

分数以固定小数位数的 `xsd:decimal` 呈现给使用者。因此两篇文档可能报告*相同*的 `?score`，却拥有不同的 `?rank`：精确分数可能确实相等，此时由文档 ID 决定顺序；也可能只是呈现时的小数位数不足以区分两者。

因此，`ORDER BY DESC(?score)` 对输出行**不是**全序，可能与 `ORDER BY ?rank` 不同。`ORDER BY ?rank` 表达排序器已经计算的顺序，而不是从舍入后的数值重新推断；在一个分区内它是全序，也是不受呈现舍入影响的写法。

## 6. 分析管线

进入索引的每个字面量和进入查询的每个检索词，都经过同一个分析器，且不经过其他分析器。检索引擎按相等性匹配查询项与索引项；两条只是相似的管线会让搜索返回空结果，却没有错误可报。无声失败是检索的失效模式，因此两端必须使用同一份代码。

分析器是显式解析、不可变的配置，供索引与查询共用。无大小写兼容规范化采用完整 Unicode 法则 `NFD → fold → NFKD → fold → NFKD → NFC`。标准配置折叠符合条件的拉丁、希腊和西里尔变音符号，要求五套固定的完整词典工件，每个最终词元的名义长度上限为 128 个 Unicode 标量值。英语词干提取需显式选择。Unicode 17 字素与 emoji 数据保护应作为整体处理的连接形式。

词法投影拥有评分统计量和连续的短语位置。表层词保留提取词干前的拼写与正字法控制；子串跨度保留标点。独立汉字检索检索结果生成器拥有自己的单字／双字频率、长度和排序语料。其项绝不改变词法 BM25F 或短语位置。融合参数由调用方选择。

工件身份、有效词典成本、每个阶段与参数以及 Unicode 数据摘要都属于分析器身份。空词典必须明确命名，对没有空格的文字使用字素回退。完整的顺序、来源对齐、输入解释、域与拒绝契约见[分析与辅助检索](text-analysis.md)。

## 7. 一个 Unicode 版本，源内生成

分析器依赖大小写折叠、规范化、词界和字母数字属性表。工作区的 `purrdf-lex` Unicode 管线提供规范化版本及生成表；文本 crate 的大小写折叠与边界数据使用同一份存于 `crates/iri/unicode/` 的 Unicode Character Database 生成。工作区固定版本为 17.0.0，不随构建工具链变化。分析器分别记录相关版本，因此未来重新生成时若其中一项变化，就不会被概括信息掩盖。

答案之所以确定，是因为这些表以源码提交：在任意目标架构、任意工具链下，同一检出版本都会把同一个字面量分析成固定的词元向量。风险因此在于**重新生成**：词元化改变会改变项词典，继而改变查询找到的文档。引擎仍返回行，只是行已不同，变化不会自行暴露。

以下机制使变化显性化：

1. **词元向量黄金测试。** 精确预期向量覆盖拉丁大小写折叠、希腊词尾 sigma、西里尔文字、从右向左的阿拉伯文字、带元音符号的希伯来文字、带附属元音符号的天城文、汉字词典和字符投影、混合假名、谚文、数字、兼容呈现形式及标点。因此，即便只改变其中一种文字，也会触发断言。该失败不是随手更新测试的理由，而是在报告此 crate 即将建立的项词典已变化；必须先理解并有意接受，再改写向量。
2. **四项版本均写入索引指纹**，并绑定分析器配置标识，因此采用不同表构建的索引可以区分。
3. **冻结差分向量**以表为参照，重放每个 Unicode 标量值的大小写折叠与规范化形式，以及 100,000 条带种子的混合文字字符串的分词和分析形式。

## 8. 确定性的精确边界

文档 ID 在全部文档按 `(graph, subject, language)` 排序后才分配，因此 ID 由内容决定，而非由数据集碰巧驻留各项的顺序决定。项词典按分析后的项文本排序，倒排记录按文档 ID 排序，位置升序。对于相同内容，两个独立构建的索引连同两个摘要在内，逐字节一致。

**此保证的精确边界。** 空节点标签是解析产物，不是内容：两个同构数据集可以把同一个空节点分别标为 `b0` 和 `b17`；而空节点的项身份包含其标签。因此，空节点主体的标签进入排序键、文档表和两个指纹。**从标签不同的来源解析出的同构数据集，会产生不同的文档 ID 和指纹。**

此 crate 不对空节点做规范化。RDFC-1.0 规范化位于 `purrdf-core`，成本高得多，并有自己的契约；在此处无声调用会使索引构建未经请求就支付那笔成本。准确的说法是：ID 和摘要仅由数据集的*项*决定；对空节点而言，项包含其标签。对抗性测试直接固定这一行为，使边界不仅写在文档中，也由可执行断言记录。

保留两个摘要，因为它们回答不同问题。**索引指纹**覆盖一切可能改变答案的内容：配置、四项 Unicode 表版本、文档表、词典、带位置的每条倒排记录和每个分区的统计量。**来源指纹**覆盖所遍历的 `(graph, subject, predicate, literal)` 行。第二个摘要用于发现索引与错误数据集配对，否则会无声地产生错误答案：关系输出格式正确的文档项，这些项随后与从未包含它们的数据集进行基本图模式连接，最终得到零行，没有任何一层会报告错误。针对当前数据集重新计算来源摘要，就能检测这种配对错误。

## 9. 短语与邻近条件在 SPARQL 中组合

此 crate 暴露两种关系，而不是内嵌的查询方言。排序检索为每份匹配文档输出一行；**项出现位置**关系则为一个项的每次出现输出一行，并携带词元位置。

位置使调用方能在已有查询语言中表达短语与邻近匹配。相邻条件就是过滤器：

```sparql
SELECT ?doc WHERE {
  ?doc <https://example.org/pf#occurs> ( "quick" ?l ?p1 ) .
  ?doc <https://example.org/pf#occurs> ( "brown" ?l ?p2 ) .
  FILTER(?p2 = ?p1 + 1)
}
```

窗口内邻近匹配使用同样的形态，只需改变过滤条件。这里完整写出可执行示例，而不是留下无法运行的片段：

```sparql
SELECT ?doc WHERE {
  ?doc <https://example.org/pf#occurs> ( "quick" ?l ?p1 ) .
  ?doc <https://example.org/pf#occurs> ( "brown" ?l ?p2 ) .
  FILTER(ABS(?p2 - ?p1) <= 3)
}
```

两种关系可以组合：短语约束可与排序搜索求交，同时仍按分区内名次排序。

上述谓词 IRI 都是测试夹具。两种关系都不自行命名 IRI；查询调用各关系所用的谓词由调用方在注册时提供。配置中一个都不提供是配置错误，而不是让系统猜测。

合取检索也通过相同方式表达，无须另建布尔方言：排序行携带 `?matched`，即文档中存在的**不同**检索项数量；若要求三个检索项全都出现，可写 `FILTER(?matched = 3)`。

位置在文档拼接的全部字面量之间连续编号，而不是在每个字面量中重新开始。因此，短语可以跨越同一主体的两个字面量，就像跨越一个字面量中的两个句子。
