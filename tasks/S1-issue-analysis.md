## Caller map and wiring risks

- `cose::sign_id` is called by `GtsWriter` when appending frames (`writer.rs:1111`). `GtsWriter::sign_with` (`writer.rs:903`) and its `signer` field are Ed25519-only. A separate composite helper that no writer invokes would leave the actual authoring path unchanged. Writer-side signing errors must propagate through actual append callers without panicking or falling back.
- `cose::verify_signatures` (`cose.rs:125`) resolves only `VerifyingKey`; `verify.rs::verify_against_keyring` (`verify.rs:312`) feeds it from an Ed25519 keyring. `verify_file_with_keyring` is the caller-supplied-key public path, distinct from transport-key discovery. Demonstrate a writer-produced composite file verifies through this path and counts a tampered signature as invalid. Malformed/unsupported composite envelopes must not become valid or be mislabeled as cryptographically checked merely because their `kid` is unavailable.
- `CompactionParams::packaging_signer` (`compact.rs:961`) is an Ed25519 tuple and `compact_streamable` forwards it into the writer (`compact.rs:1154`). Carried authorship COSE bytes remain detached provenance. Changes to shared key types must preserve mandatory packaging signatures and byte-exact retained authorship evidence. If composite authoring is exposed for compaction, verify both new packaging and carried source signatures.
- RDF `gts_certify.rs::signatures_verify_ok` (`:642`) calls `cose::parse` and `verify_sig` for carried detached signatures; `compact_and_certify` (`:999`) and its keyring/packaging types currently constrain this to Ed25519. Update concrete affected consumers when changing shared APIs; do not leave a composite signature silently unverifiable through an advertised algorithm-aware certification path.
- RDF `gts_compose.rs` signs through `writer.sign_with` (`:1505`) after demanding Ed25519 secret/kid/OpenPGP armor together. Existing OpenPGP import is outside the requested composite key-discovery work. Supporting caller-supplied composite authoring in GTS does not imply a requirement to invent composite OpenPGP transport keys or new binding/CLI key discovery.

## External prerequisites and blocker assessment

The [IETF JOSE/COSE composite draft-04](https://www.ietf.org/ietf-ftp/internet-drafts/draft-ietf-jose-pq-composite-sigs-04.html) §§4.2–5.3 supplies a usable construction: prehash the COSE message with SHA-512, apply its prefix and pairing-specific label, pass that label as ML-DSA context, sign the resulting representative with both algorithms, and concatenate ML-DSA then Ed25519. It requests algorithm -58, still marked TBD. The [live IANA COSE registry](https://www.iana.org/assignments/cose) leaves -256 through -54 unassigned; registered standalone ML-DSA-65 (-49) does not identify this composite pairing. These live sources were inspected on 2026-10-06.

Inference: missing shared GTS vectors alone blocks a claim of shared GTS interoperability, not all implementation work. The issue expressly says “when the specification publishes them”; it does not require waiting for future publication before implementing anything. Native ML-DSA/FIPS primitive qualification, actual strict algorithm dispatch, deterministic versus hedged API contracts, caller wiring and all local refusal tests are concrete work independent of the corpus. The existing GTS spec is algorithm-agile rather than an exclusive Ed25519 allowlist.

The unresolved wire decision is whether this repository may ship the pinned IETF draft's requested -58 mapping before formal registration/upstream profile publication. Do not invent a private production value, silently use standalone ML-DSA's value, or pretend draft/registered semantics are identical. Establish authority from current GTS governance/upstream evidence and the issue's authorization before declaring this an external brick wall. A decision to implement a clearly identified draft profile can be compatible with the request; the absence of vectors is not itself evidence that such implementation is forbidden. If the chosen authoritative profile genuinely cannot be established, record the exact unresolved field/revision and evidence, rather than a broad “everything blocked” assertion.

New external crypto dependencies are another concrete decision point: the first-party design and existing dependency ledger constrain what may be added. Their absence today does not prove impossibility; either implement a qualified native primitive or establish authorization for a suitable pure-Rust dependency. Hedged signing likewise does not require OS RNG in the wasm core: caller-owned randomness is an available architecture, with explicit failure semantics.
