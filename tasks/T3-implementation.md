## Implemented construction and cryptographic contract

`cose::composite` implements exactly the ML-DSA-65 + Ed25519 pairing in pinned
LAMPS draft-19 and JOSE/COSE draft-04. COSE application context is empty:
`M' = CompositeAlgorithmSignatures2025 || COMPSIG-MLDSA65-Ed25519-SHA512 ||
0x00 || SHA512(Sig_structure)`. Both components sign that same 127-byte
representative; pure ML-DSA additionally receives the fixed 30-byte label as
its FIPS context. Standard-mandated prefix/label spellings are each declared
once through `purrdf_hash::Domain` beside the construction. No custom SHA-512,
Keccak, lattice, Ed25519, constant-time byte comparison or secret-clearing
body was added; all use qualified existing homes. Native source is original,
with no external implementation bodies or coefficient arrays imported.

Typed composite keys enforce exact public 1984-byte and private 64-byte seed
encodings. Public decoding refuses noncanonical Ed25519 encodings and weak
keys; ML-DSA has its specified complete fixed-length public encoding space.
Private encoding is ML-DSA seed then Ed25519 seed. Two fresh independent
component seeds and dedicated keys are a caller generation policy; import
cannot detect external reuse or infer entropy quality, so the legal all-zero
IETF fixture is admitted. Guarded owned seeds and both component secrets clear
on drop through their existing shared discipline; exported/caller copies remain
caller-owned. Debug is public-only; Clone explicitly duplicates owned secrets.
No formal certification or whole-operation constant-time claim is made.

Composite signature encoding is exactly 3309 ML-DSA bytes then 64 Ed25519
bytes, with canonical ML-DSA decoding and strict RFC 8032 verification in the
existing primitive. Verification evaluates both components and accepts their
conjunction. `sign_deterministic` is explicitly the fixture variant;
`sign_hedged` consumes caller-provided 32-byte randomness and returns typed
failure without output. No host entropy/clock lookup or deterministic failure
fallback exists. Writer/provider integration belongs to approved Task 4.

COSE authenticated Algorithm distinguishes Ed25519 (-8) from the requested
composite (-58). The latter is the pinned draft's provisional allocation,
not a final IANA registration, and never substitutes standalone ML-DSA -49.
Borrowed typed signing/verification keys prevent cross-algorithm fall-through.
`sign_id_hedged`, `sign_id_deterministic`, `verify_sig_with_key` and validated
`Sign1::verify` are public entry points. Existing `sign_id`, `verify_sig`,
`parse` and signature-kid conveniences route through this same core; there is
no second compatibility parser. Existing Ed25519 bytes remain exact.

## Strict envelope and optional/opaque identifier contract

`parse_sign1` decodes exactly one complete tag-18 or untagged four-field
Sign1, requires a protected supported integer alg, map headers, detached null
payload and exact fixed-length signature encoding. It rejects trailing bytes,
wrong/nested tags, COSE_Sign/two signers, attached payload, wrong field/header
types, missing/unsupported alg, duplicate integer/text labels in either map,
any cross-bucket duplicate/ambiguity, and unprotected alg/crit. Required
critical labels must be present in protected headers, unique and understood;
the GTS signing core processes alg/kid, rejects unsupported critical extensions
and counter-signature layers, and retains valid noncritical extension metadata.
IV/Partial-IV coexistence is refused under the RFC common-header rule.
Received protected bytes are preserved exactly, including legal non-shortest
encodings; preimages never normalize received headers. Parsed protected and
signature buffers move out of the decoder rather than copying the full values.

Parent source review correctly challenged two inherited parser assumptions.
The original parser required UTF-8 kid and presence; neither is a GTS signing
constraint. Captured RFC 9052 §3.1 describes kid as an opaque key hint and
explicit optional `? 4 => bstr` (raw lines 710–721 and 775–785); GTS §9.2
delegates COSE without adding either restriction. The corrected typed parser
preserves `Option<Vec<u8>>`: absence, present-empty, text and opaque binary are
distinct. Supplied-key verification requires no discovery or kid. Legacy
tuple/String helpers stay text-only through the same parser, with no fabricated
hex/string fallback. The existing text resolver does not invoke lookup for an
absent or binary kid; supported unresolved envelopes remain Unverified.
Malformed/unsupported envelopes are Invalid BEFORE lookup, even with no key.

RFC source URL: https://www.rfc-editor.org/rfc/rfc9052.txt ; captured SHA-256
`01eecd7f646537600e7aad665b1fa581ce6ec33dae4ef4add0997aaf38cd0a45`.
Encrypt0's independently specified opaque/header rules and implementation
were not weakened or unified with signing policy.
