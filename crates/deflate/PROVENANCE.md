# Provenance of `purrdf-deflate`

Everything under `src/`, `tests/` and `benches/` is first-party, written from
the specifications below. No third-party DEFLATE, inflate, gzip or zlib
implementation was read, ported or consulted, in any language.

## Specifications

- **DEFLATE** — RFC 1951: §2 (the window), §3.1.1 (bit packing), §3.2.2
  (canonical codes from code lengths), §3.2.3–§3.2.7 (block header, stored
  blocks, the length and distance alphabets, the fixed codes, dynamic block
  headers and the code-length code) and the §4 prose on hash chains and lazy
  matching. The length and distance tables are derived from the §3.2.5 rule at
  compile time and their end points asserted. The encoder's block splitting,
  level parameters and length-limited Huffman construction are this crate's
  own design.
- **gzip** — RFC 1952 §2.2–§2.3.1.2 (member layout, `FLG` bits, `FHCRC`,
  CRC32 and `ISIZE`, decoder compliance). The §8 sample code was not read; the
  CRC-32 is `purrdf-hash`'s.
- **Zstandard framing** (used by `purrdf-gts`'s transport over this crate's
  sibling decoder) — RFC 8878 §3.1 and §3.1.2, magic numbers only.
- **Instruction semantics** — the Rust `core::arch` reference
  (doc.rust-lang.org) for the SSE2, AVX2, NEON and wasm simd128 intrinsics.

## Test inputs

Round-trip inputs are generated by `purrdf_testkit::rng::Xoshiro256`; the
refusal streams are built bit by bit in the test file. The one external input
is the frozen `vectors/tar/gzip-basic.tar.gz`, decoded as a black box.
